# 版本记录：v2.1.7-market-claw-ai-sandbox-agent-advisors

## 1. 本轮目标

本轮目标是在 V2.1.5 / V2.1.6 已具备 AI Provider 配置与安全调用框架的基础上，新增 Market Claw 的 AI 测试沙盒，快速形成：

- 输入客户问题
- 选择业务线 / Provider / 专家视角 / 客户阶段
- 生成内部销售建议
- 合并风险分级
- 保存为训练样本草稿

这一轮属于功能补充和可用性增强，优先解决“AI Provider 已经能配，但还没有真正进入 Market Claw 业务测试场景”的问题。

## 2. 背景与上下文

承接记录：

- `custom/notes/v2.1.5-ai-provider-deepseek-config.md`
- `custom/notes/v2.1.6-ai-provider-doubao-support.md`

V2.1.5 解决的是租户级 AI Provider 配置、测试连接、安全日志和降级框架；V2.1.6 继续补齐了豆包 / 火山方舟 Provider 标识与 OpenAI-compatible 接入。

但到 V2.1.6 为止，AI Provider 仍主要停留在配置层，尚未真正进入 Market Claw 的业务测试闭环。当前最值得优先补的是一个独立、低风险、内部使用的 AI 测试沙盒，而不是直接改正式客户回复主链路。

## 3. 问题分析

表面问题是“已经支持多个 AI Provider，但业务侧还没有可用入口”。

更核心的矛盾是：

1. 直接把 AI 接到正式客户回复主链路风险太高；
2. 只停留在配置页又无法验证 Provider 在真实业务语境下是否可用；
3. 销售建议如果没有风险分级、使用模式和知识治理边界，很容易越界；
4. 训练样本和正式知识之间必须继续保留人工审核缓冲层。

所以本轮不能直接“让 AI 帮客户回复”，而应该先做一个内部测试工作台，让管理员和运营把 AI 真正跑起来，同时继续把边界收紧在训练草稿层。

## 4. 候选方案比较

### 方案一：直接把 AI 接到客户详情页正式回复主链路

核心思路：

- 在客户详情页替换或优先走 AI 回复生成。

优点：

- 用户感知最强。

缺点：

- 风险最大；
- 会改正式主链路；
- 容易破坏 V2.1.2 的风险分级边界；
- 一旦 Provider 配置错误或返回不稳定，直接影响销售日常工作。

本轮放弃。

### 方案二：新增独立 AI 测试沙盒页

核心思路：

- 新增 `/app/[tenantSlug]/market-claw/sandbox`
- 独立输入问题并生成内部建议
- 结果可保存为训练样本草稿，但不进入正式知识库

优点：

- 边界清楚；
- 不污染正式业务链路；
- 可直接复用 V2.1.5 / V2.1.6 的 Provider 调用能力；
- 便于做 MOCK 和 Playwright 自动化验证。

缺点：

- 需要多一页专门入口；
- 首轮结果主要服务管理员和运营，销售不能直接用这页。

本轮采用。

### 方案三：直接做复杂 Agent 系统

核心思路：

- 建一套独立 Agent 编排框架，让多个专家 Agent 互相调用。

优点：

- 扩展性看起来更强。

缺点：

- 明显超出本轮目标；
- 引入额外复杂度；
- 不利于尽快形成可测闭环。

本轮明确放弃。

## 5. 最终决策

最终采用：

- 新增独立 Market Claw AI 测试沙盒页；
- 用轻量 expert profile 实现“专家视角”；
- 真实 Provider 继续复用统一 `callAiJsonCompletion`；
- MOCK 单独在沙盒里生成结构化测试结果；
- 风险等级通过“AI 结果 + 系统规则”合并，系统规则优先；
- 保存结果时只落成训练样本草稿，不进入正式知识库。

关键设计决策：

1. 不改正式客户回复主链路；
2. 不改资料投喂主链路；
3. 不改正式训练生成主链路；
4. 不新增 schema，优先复用现有 `MarketClawTrainingCase`；
5. 沙盒生成与保存均走独立 Server Actions；
6. 权限只开放给 `TENANT_ADMIN` 和 `OPERATOR`。

具体实现点：

### 6.1 专家视角说明

本轮新增 7 个轻量专家视角：

- 销售教练
- 成交策略顾问
- 客户发现顾问
- 方案表达顾问
- 风险边界顾问
- 知识治理顾问
- 综合建议

每个视角都包含：

- `id`
- `name`
- `description`
- `focus`
- `outputSections`
- `systemPrompt`

它们不是复杂独立 Agent，只是用于拼装 Prompt 和页面选择的轻量配置。

### 6.2 页面结构说明

新增页面：

- `/app/[tenantSlug]/market-claw/sandbox`

页面包含：

1. 客户问题输入框
2. 业务线选择
3. AI Provider 选择
4. 专家视角选择
5. 客户阶段选择
6. 生成按钮
7. MOCK 测试按钮
8. 结果展示区
9. 最近沙盒调用摘要
10. 保存为训练样本草稿按钮

并明确显示边界说明：

- AI 输出只是建议
- 不会直接写入正式知识库
- 不会替销售对外回复
- 客户回复仍需销售确认
- 风险等级仍以系统规则和人工确认优先

### 6.3 AI Prompt 和输出结构说明

Prompt 中包含：

1. 客户问题
2. 业务线名称
3. 客户阶段
4. 专家视角名称与重点
5. 风险分级原则
6. 使用模式原则
7. 必须输出合法 JSON
8. 不得绝对承诺
9. 不能绕过人工确认

JSON 目标结构包括：

- `agentId`
- `agentName`
- `summary`
- `suggestedReply`
- `wechatShortReply`
- `followUpQuestions`
- `riskLevel`
- `sendMode`
- `riskReasons`
- `nextActions`
- `knowledgeSuggestion`
- `internalNotes`

### 6.4 风险分级合并规则

本轮新增并复用了以下 helper：

- `detectRiskFromQuestion`
- `normalizeAiRiskResult`
- `mergeAiRiskWithRuleRisk`

规则说明：

1. 普通业务问题默认 `MEDIUM`
2. 价格、效果、周期、责任、政策等边界默认 `HIGH`
3. 绝对化承诺默认 `BLOCKED`
4. AI 可以把风险抬高，但不能把系统规则识别出的风险降下去
5. `sendMode` 会按最终风险等级自动收紧

### 6.5 保存训练样本草稿说明

沙盒结果保存时：

- 不新建正式知识项
- 不自动采纳候选知识
- 只创建 `MarketClawTrainingCase`
- `reviewStatus` 设为 `DRAFT`
- 在 `salesNote` 中明确标记“来源：AI 测试沙盒”

保存内容包含：

- 客户问题
- 推荐回复
- 微信简短回复
- 专家视角
- 风险等级
- 使用模式
- 风险原因
- 下一步动作
- 知识沉淀建议
- 创建人

### 6.6 权限说明

- `TENANT_ADMIN`：可访问沙盒、生成建议、保存训练样本草稿
- `OPERATOR`：可访问沙盒、生成建议、保存训练样本草稿
- `SALES`：不显示入口，直接访问被拒绝
- `PLATFORM_ADMIN`：本轮不扩大租户侧业务权限

### 6.7 调用日志说明

继续复用 `AiCallLog`，`purpose` 使用：

- `MARKET_CLAW_SANDBOX`

记录内容保持最小必要范围：

- tenantId
- provider
- model
- purpose
- status
- latencyMs
- token 信息
- createdById
- errorMessage

不记录：

- 完整 Prompt
- 完整 AI 输出
- API Key

## 7. 本轮优点

1. 真正把 AI Provider 从“配置层”推进到了“业务测试层”；
2. 没有破坏正式客户回复、资料投喂和训练主链路；
3. 继续保留 V2.1.2 的风险分级边界；
4. 通过 MOCK 可以稳定做本地和 Playwright 自动化验证；
5. 保存训练样本草稿后，仍保留人工审核缓冲层；
6. 专家视角轻量可扩展，后续可以继续加行业视角而不需要重做架构。

## 8. 本轮缺点与代价

1. 本轮没有做复杂多 Agent 协同，只是轻量 expert profile；
2. 真实 Provider 仍依赖租户已保存的单套 AI 配置，不能同时并排维护多套真实密钥；
3. `MarketClawTrainingCase` 只是被复用为草稿承载层，暂时没有单独的“沙盒结果历史页”；
4. 客户阶段在沙盒页使用轻量阶段映射，和正式 `LeadStage` 不是一一对应；
5. 页面主要面向管理员和运营，销售仍然不能直接通过这页自助测试。

## 9. 验证与结果

本轮验证命令：

1. `npx.cmd tsc --noEmit`
2. `npm.cmd run prisma:generate`
3. `npm.cmd run lint`
4. `npm.cmd run build`
5. `npx.cmd playwright test tests/v217-market-claw-ai-sandbox-agent-advisors-e2e.spec.ts --workers=1 --reporter=list`

说明：

- 本轮没有修改 schema / migration / seed，因此不需要额外执行 PostgreSQL 迁移验证脚本作为强制项；
- Playwright 继续优先使用 MOCK Provider，避免依赖真实外部接口。

## 10. 本轮结论

本轮最重要的结论是：

AI Provider 不应该一上来就直接接进正式客户回复链路，先通过“内部测试沙盒 + 风险收紧 + 训练草稿保存”形成闭环，更稳，也更符合当前系统边界。

被验证的判断：

1. Provider 配置层与业务测试层可以解耦；
2. 风险规则优先于 AI 建议是必须保留的硬约束；
3. 训练样本草稿是 AI 建议进入系统的合适缓冲层；
4. MOCK Provider 足以支撑大部分本地验证与自动化回归。

## 11. 下一轮建议

1. 增加沙盒历史记录页或最近测试记录筛选，方便运营复盘不同专家视角输出差异。
2. 在不破坏边界的前提下，把沙盒里验证过的 Prompt 逐步迁移到资料投喂预览或训练预览场景。
3. 继续补 API Key 正式加密存储与 Provider 测试沙盒对比能力，再考虑更深的行业专家视角。
