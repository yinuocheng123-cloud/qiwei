# 版本记录：v1.8-real-customer-import

## 1. 本轮目标

本轮目标是在 V1.7.1 已完成角色化导航与权限收口的基础上，新增一套所有租户通用、但优先服务 `zhengmu-platform` 真实自用的客户导入能力。

这轮优先级高的原因有三点：

1. 到 V1.7.1 为止，系统已经能承载样板客户、业务线、智能跟进助手和智能标签建议，但还停留在“演示数据”阶段。
2. 真正让整木网开始自用，第一步不是接企业微信 API，也不是做自动消息，而是让已有客户和新增客户能稳定导入系统。
3. 用户明确要求本轮只解决“真实客户导入与自用准备”，不提前开发企业微信消息提醒、不做自动回复、不做自动打标签、不做复杂 AI。

本轮目标类型属于：功能补充、可用性提升、真实使用准备。

本次迭代与上一轮的关系是“延续与扩展”，不是推翻。系统原有的租户隔离、任务、智能建议、审计和角色菜单都被保留。

## 3. 问题分析

表面问题是“没有客户导入入口”，但核心矛盾并不只是缺一个上传按钮，而是系统从演示阶段进入真实使用阶段时缺少一条可追踪、可回看、可控风险的导入链路。

真正要解决的点包括：

1. 导入前要能看清字段映射，而不是盲写数据库。
2. 导入前要能识别重复客户，否则真实自用会立刻把数据做脏。
3. 导入时要能同时处理负责人、标签、业务线和首次跟进任务，否则导入后仍然要大量人工补录。
4. 导入后要有批次记录、行级结果和审计，避免以后无法追溯“这批客户是怎么进来的”。

本轮的关键约束有四个：

1. 不接企业微信 API。
2. 不新增复杂前端交互状态管理，优先复用当前系统的服务端表单模式。
3. 不大改 `Lead` 数据结构，避免把“真实导入”变成一次模型重构。
4. 不破坏 V1.7.1 已经收口好的角色菜单和权限边界。

## 4. 候选方案比较

### 方案一：直接上传后立刻导入

核心思路：
上传 CSV 后直接写 `Lead`、`LeadTag` 和 `FollowTask`，不做批次预览。

优点：

1. 页面最简单。
2. 实现速度最快。

缺点：

1. 字段映射不可见，真实客户导入风险很高。
2. 无法在导入前提示重复客户和失败原因。
3. 一旦导错，很难回溯每一行的结果。

放弃原因：
不符合“真实自用准备”的稳妥要求，风险太高。

### 方案二：服务端批次预览 + 确认导入

核心思路：

1. 上传 CSV 后先解析为 `ImportBatch` + `ImportRow` 预览记录。
2. 页面展示字段映射、失败原因、重复识别和默认设置。
3. 用户确认后再真正写入客户、标签和任务。

优点：

1. 保持当前项目一贯的服务端表单模式，前端复杂度低。
2. 可以把预览结果、失败原因和重复识别完整落库，方便追踪。
3. 能自然接入 AuditLog 和后续批次回看。

缺点：

1. 比直接导入多一层批次和行记录模型。
2. 页面会比单步上传稍复杂。

最终选择：
采用方案二。

### 方案三：新增复杂客户端映射向导

核心思路：
做多步前端向导、拖拽字段映射、行内即时编辑，再提交最终 payload。

优点：

1. 交互更炫。
2. 理论上更接近专业导入工具。

缺点：

1. 远超当前仓库的交互复杂度。
2. 要额外处理大量客户端状态和边界情况。
3. 不符合“先把基础系统能力做扎实”的本轮边界。

放弃原因：
过重，不符合最小改动原则。

## 5. 最终决策

本轮最终采用以下实现思路：

1. 数据层新增 `ImportBatch` 和 `ImportRow` 两个模型。
2. 导入格式优先支持 CSV，不额外引入 Excel 依赖。
3. 导入入口为 `/app/[tenantSlug]/imports`，只对 `TENANT_ADMIN` 和 `OPERATOR` 开放。
4. 上传后先生成预览批次，允许调整字段映射和默认设置。
5. 重复客户识别规则按同租户内：
   - `phone` 相同；
   - 否则 `wechat` 相同；
   - 否则在 `phone` 和 `wechat` 都为空时，用 `name + company`；
   - 默认跳过重复，不覆盖已有客户。
6. 业务线继续采用本项目当前最稳的轻量方案：
   - 校验导入值是否为当前租户 `ACTIVE` 业务线；
   - 确认导入后把业务线写成 `LeadTag`，分组为 `BUSINESS_LINE`；
   - 不额外改 `Lead` 关联结构。
7. 标签导入继续用 `LeadTag`，默认分组为 `IMPORTED`，并做同名同组去重。
8. 如启用“自动生成首次跟进任务”，则只对已分配负责人的客户生成 `FIRST_FOLLOW` 任务。
9. 通过 `import_batch_created`、`import_batch_completed`、`import_batch_failed` 记录批次级审计。

## 7. 本轮优点

1. 沿用了当前系统最稳定的服务端表单模式，没有引入重前端状态。
2. 从演示数据走向真实客户导入时，先补足了“预览、去重、批次追踪”三件最关键的底座能力。
3. 业务线、标签、负责人和首次任务在导入环节一次性打通，减少导入后的二次补录成本。
4. 角色边界清晰，销售既看不到菜单，也无法直接访问导入页。
5. 导入批次与行级记录都可回看，后续更容易排查问题。

## 8. 本轮缺点与代价

1. 本轮只优先支持 CSV，没有进一步支持 `.xlsx`。
2. `Lead` 仍然没有独立 `note` 字段，因此“需求说明 + 备注”最终合并进 `message`。
3. 业务线仍然通过标签表达，而不是 `Lead` 与 `BusinessLine` 的正式中间表关联。
4. 重复客户策略当前只做“识别并跳过”，还没有做“只更新备注和标签”之类的高级合并。
5. 页面仍然是单页大表单，先保可用性，没有做更细的多步向导体验。

本轮 Playwright 收口补充说明：

1. 初次失败不是导入主链路断裂，而是测试环境里的临时 PostgreSQL 在验证脚本结束后被关闭，导致 Playwright 启动 dev server 时无法连接数据库。
2. 在修正环境后，实际暴露的问题主要是测试定位器过宽与断言过脆，例如：
   - 把预览页中“高意向，品牌增信关注”的整句断言改为行级分项断言；
   - 把客户详情里的标签断言收窄到“标签”卡片；
   - 把任务断言从全局 `todos` 页收窄到当前客户详情任务区；
   - 在登录后补充 `networkidle` 等待，避免紧接着 `goto` 时触发导航中断。
3. 本轮未发现必须修改导入业务逻辑的真实 bug，最终只调整了 V1.8 Playwright 用例与等待方式。

## 10. 本轮结论

本轮最重要的结论是：

在当前项目的技术边界下，客户导入最稳妥的落地方式不是一口气做复杂向导，而是先把“CSV 预览批次 + 行级去重 + 批次级导入结果”这条服务端链路跑通。

被进一步确认的判断有三点：

1. 从“样板数据演示”切向“真实自用准备”，最先要补的是导入而不是消息能力。
2. 当前业务线能力足以在导入里复用，不需要为导入再发明第二套业务归类机制。
3. V1.7.1 的角色化导航与权限收口让导入入口天然更安全，适合继续沿用。

## 11. 下一步建议

1. 如果 V1.8 验证稳定，下一步可以考虑补“导入失败行导出”或“重复客户单独列表”，收益高且风险低。
2. 如果整木网开始真实自用后反馈大量历史 Excel 文件，再评估是否补 `.xlsx` 支持。
3. 如果未来确实需要更强的数据治理，再考虑把业务线关联和导入合并策略升级为正式中间表和多策略导入规则。
