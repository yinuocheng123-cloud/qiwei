# 版本记录：v2.0.1-local-demo-startup-fix

## 1. 本轮目标

本轮目标是修复《企业微信业务增长中台》本地演示环境“前端能打开、登录时报数据库连接失败”的启动不稳定问题。

这次不开发新业务功能，不修改麻虾 Market Claw 业务逻辑，不接企业微信 API，不接电话录音系统，也不做自动发送客户消息。

本轮目标类型属于：

- 可维护性提升
- 本地演示环境稳定性修复
- 启动流程收口

## 3. 问题分析

表面现象是：Next.js 页面已经可以打开，但登录时报：

`Can't reach database server at 127.0.0.1:55432`

真正的核心问题不是登录页逻辑有 bug，而是本地 PostgreSQL 没有稳定常驻，导致 Prisma 在查询用户时无法连接数据库。

当前启动体验存在几个断点：

1. 用户容易直接运行 `npm run dev`，但没有同时拉起数据库。
2. 现有验证脚本会在任务完成后回收 PostgreSQL，不适合日常演示。
3. PostgreSQL 数据目录初始化、端口检查、迁移、seed 和 dev server 启动没有被收口成一条命令。

## 4. 候选方案比较

### 方案 A：只补 README 说明

核心思路：

- 仅在 README 里补充一段“先启动 PostgreSQL，再执行 migrate 和 seed”的说明。

优点：

- 改动最小。

缺点：

- 仍然要求用户手动拆多步执行。
- 无法自动处理数据目录初始化、端口占用、日志落盘和错误提示。
- 不能真正解决“本地演示环境启动不稳定”。

放弃原因：

- 这更像补文档，不是补可复用的一键启动方案。

### 方案 B：新增一键启动脚本

核心思路：

- 新增 `custom/experiments/start-local-demo.ps1`，把 PostgreSQL、Prisma 和 Next.js 启动流程全部收口。

优点：

- 用户只需要执行一条 PowerShell 命令。
- 可以把错误定位前移到脚本阶段，而不是等到登录页才暴露。
- 可以复用当前项目已有的 PostgreSQL 基线参数和 Prisma 迁移链路。

缺点：

- 需要额外维护一份脚本。
- Windows 本地 PostgreSQL 路径仍然依赖当前机器安装位置。

最终选择：

- 采用方案 B。

## 5. 最终决策

本轮最终采用“新增一键启动脚本 + README 明确入口 + 正式记录收口”的方案。

关键决策如下：

1. 保持现有业务代码不动，只补本地演示启动链路。
2. 脚本默认使用固定 PostgreSQL 路径和现有演示数据目录。
3. 端口 `55432` 已有 PostgreSQL 时不重复启动，只继续 migrate 和 seed。
4. 端口 `55432` 若被其他进程占用，立即报错并输出进程信息。
5. PostgreSQL 标准输出和错误输出统一写入 `custom/experiments/` 下的日志文件，方便排障。

## 6. 具体实现

本轮涉及文件如下：

1. `custom/experiments/start-local-demo.ps1`
   - 新增本地演示一键启动脚本。
   - 自动检查项目目录、PostgreSQL 可执行文件、数据目录、端口状态。
   - 自动初始化数据目录。
   - 自动启动 PostgreSQL。
   - 自动执行 Prisma generate、migrate deploy 和 seed。
   - 最后启动 `npm run dev`。

2. `README.md`
   - 新增“本地演示一键启动”说明。
   - 明确脚本命令、数据库报错时的处理方式、登录地址和测试账号。

3. `AGENTS.md`
   - 更新“最新一期路径”到本记录文件。

## 7. 新增脚本说明

新增脚本路径：

`custom/experiments/start-local-demo.ps1`

推荐执行方式：

```powershell
powershell.exe -ExecutionPolicy Bypass -File custom\experiments\start-local-demo.ps1
```

脚本会执行以下动作：

1. 自动切换到项目根目录。
2. 检查 `postgres.exe` 和 `initdb.exe` 是否存在。
3. 检查 `custom/experiments/postgres-data` 是否为已初始化的数据目录。
4. 若端口 `55432` 未被 PostgreSQL 占用，则自动后台启动 PostgreSQL。
5. 等待数据库端口可用。
6. 确保 `wecom_growth_hub_v11` 数据库存在。
7. 设置当前 PowerShell 进程的 `DATABASE_URL`。
8. 执行 `npm run prisma:generate`。
9. 执行 `npx prisma migrate deploy`。
10. 先尝试 `npm run prisma:seed`，失败时回退到 `npx prisma db seed`。
11. 输出登录地址和测试账号。
12. 以前台方式执行 `npm run dev`。

当前仍有一个工具环境相关现象：

- 在当前 Codex 命令环境里，把整份脚本隐藏到后台后，再继续做浏览器自动登录验证并不稳定。
- 因此本轮可以确认“一键启动脚本能把数据库、迁移、seed 和登录页拉起来”，但“隐藏后台脚本场景下的自动化登录跳转”没有作为稳定结论写死。
- 对用户本机直接执行该脚本而言，前台实跑已经确认能走到 `next dev Ready`，这是本轮最关键的启动闭环结果。

## 12. 风险与未完成项

当前已知风险：

1. 脚本默认 PostgreSQL 路径依赖当前本机安装位置，若机器路径不同，需要传参或改默认值。
2. 脚本会以前台方式启动 `npm run dev`，因此执行成功后终端会停留在 dev server，不会自动返回。
3. 如果数据目录已存在但内容损坏，脚本会按最保守方式报错或提示，而不会擅自清空目录。
4. 当前 Codex 工具环境对“后台隐藏 PowerShell + 持续浏览器自动化登录”不够稳定，这个现象更像工具运行方式限制，而不是项目脚本本身逻辑错误。

## 13. 下一步建议

1. 先用这份脚本完成本地人工演示和登录验证，确认不再出现数据库未启动导致的登录失败。
2. 如果后续仍然遇到个别机器 PostgreSQL 常驻不稳定，可以再补一份“停止本地演示环境”的配套脚本。
3. 如果未来需要给非开发同事使用，可再补一份更短的演示手册，但不建议和业务 README 混在一起过度膨胀。
