# 版本记录：v2.3.6-local-postgres-fallback-hardening

## 1. 本轮目标

本轮只修复本地开发启动链路中 PostgreSQL fallback 不稳定的问题，让 `scripts/start-local.ps1` 能稳定拉起本地数据库、Next dev，并让 `check-local.ps1` 与 `test-smoke.ps1` 给出可信结果。

本轮不改业务功能、不改销售路径、不接真实 AI、不接真实企业微信、不扩大 SALES 权限。

## 2. 背景与上下文

V2.3.5 已完成全局去行业化与平台化收口，当前系统定位为 `MarketClaw 销售助手`。本轮承接的是本地启动失败：`start-local.ps1` 可以找到 `.local/postgres-data` 并启动 `postgres.exe`，但 30 秒内未检测到 `55432 LISTENING`，同时 `.local/logs` 里的 PostgreSQL stderr 为空，脚本误判数据库不可用并停止。

## 3. 问题分析

表面现象是 `postgres.exe` 进程存在但 30 秒后端口未监听。实际排查发现：

- `.local/postgres-data` 已初始化，并非缺失目录。
- 后续观察到 PostgreSQL 最终可以监听 `127.0.0.1:55432` 并接受连接，说明 PGDATA 没有确认损坏。
- `postmaster.pid` 可能残留，旧脚本只在启动前做了有限清理，停止脚本在 `pg_ctl stop` 失败后也可能留下 stale pid。
- Windows 本地 PostgreSQL 在异常关闭后可能需要更久恢复和同步，旧的 30 秒端口等待过短。
- 旧脚本只读取 `.local/logs/postgres-start-local.stderr.log`，而 PostgreSQL 也可能把历史日志写在 PGDATA 内的 `postgres-start-local.log`，导致“Recent PostgreSQL error log 为空”。
- `/login` 检查只做一次，Next dev 首次编译期间容易被误判为不可打开。

## 4. 候选方案比较

方案一：继续使用 `pg_ctl -w -t` 启动。优点是 PostgreSQL 官方推荐；缺点是在当前 Windows 管理员环境下复现 `could not create restricted token: error code 87`，不可作为主流程。

方案二：删除并重建 `.local/postgres-data`。优点是能清空潜在损坏；缺点是会丢本地开发数据，而当前 PGDATA 已确认可以恢复并接受连接，因此不应默认执行。

方案三：保留直接启动 `postgres.exe`，但增强等待、显式监听、诊断和修复入口。优点是最小改动、符合当前机器实际可运行方式；缺点是仍依赖本机 PostgreSQL 可执行文件存在。

本轮选择方案三，并新增手动修复脚本作为兜底，不自动删除本地数据库。

## 5. 最终决策

`start-local.ps1` 继续使用 `postgres.exe` fallback，但启动时显式指定 `listen_addresses=127.0.0.1`，等待上限提升到 180 秒，并用 `pg_isready` 判断最终可用性。失败时输出 PGDATA、端口、pid、opts 和多处日志。

`check-local.ps1` 不再只看端口和一次 `/login` 响应，而是同时确认 PostgreSQL 接受连接，并对 `/login` 做轮询。

`stop-local.ps1` 在确认 55432 未监听后清理 stale `postmaster.pid`，避免下一次启动误判。

新增 `repair-local-postgres.ps1`，只在人工确认后备份并重建 `.local/postgres-data`。

## 6. 具体实现

- `scripts/start-local.ps1`：增加 PostgreSQL 诊断输出；启动参数增加 `listen_addresses=127.0.0.1`；等待时间提升到 180 秒；等待 ready 时检测 postgres 进程是否提前退出。
- `scripts/run-postgres-fallback.ps1`：手动排障入口也使用相同监听地址。
- `scripts/check-local.ps1`：新增 `pg_isready` 检查，并对 `/login` 做最多 60 秒轮询。
- `scripts/stop-local.ps1`：停止后清理 stale `postmaster.pid`。
- `scripts/repair-local-postgres.ps1`：新增本地 PGDATA 备份与重建脚本，仅限 `.local/postgres-data`。
- `README.md` 与 `custom/dev/local-env-setup.md`：补充 V2.3.6 本地 PostgreSQL fallback 排障说明。
- `AGENTS.md`：最新一期路径更新到本记录。

## 7. 本轮优点

本轮让本地启动从“短时间端口猜测”变成“数据库真正接受连接后才继续”，减少 false login failure。失败时能看到更多上下文，不再只有空 stderr。修复脚本也避免把“手动删除 PGDATA”变成口头操作。

## 8. 本轮缺点与代价

启动脚本在 PostgreSQL 慢恢复时最多会等待 180 秒，比旧流程更慢。`repair-local-postgres.ps1` 会重建本地开发库，因此必须显式传入 `-Force`，且仍需要用户理解这是本地数据重置。`pg_ctl` 在当前 Windows 环境下仍不可作为主路径，后续若换机器可以再评估。

## 9. 验证与结果

已完成验证：

- `scripts/start-local.ps1`：成功启动 PostgreSQL fallback，`55432 LISTENING`，并完成 `db:generate`、`db:push`、`db:seed`、`typecheck`、`lint`、`build`，随后启动 Next dev。
- `scripts/check-local.ps1`：输出 `Result: OPENABLE`。
- `scripts/test-smoke.ps1`：四组 smoke 全部通过。
  - V2.2：2 passed
  - V2.2.1：3 passed
  - V2.2.4：3 passed
  - V2.2.7 / V2.3.5 资料清单：3 passed

本轮没有重建 `.local/postgres-data`，因为现有 PGDATA 已确认可恢复并正常连接。

## 10. 本轮结论

根因不是业务代码，也不是 schema 问题，而是本地 PostgreSQL fallback 启动流程对 Windows 慢恢复、stale pid 和日志位置覆盖不足。脚本层增强后，本地启动、检查和 smoke 链路已跑通。

## 11. 下一轮建议

1. 后续若再次出现 PGDATA 损坏，再执行 `scripts/repair-local-postgres.ps1 -Force`，不要手动删除目录。
2. 可以考虑把本地脚本中的 PostgreSQL 工具路径集中成一个小型 helper，但当前没必要为了环境问题做大重构。
3. 若未来恢复 Docker Desktop，可保留 fallback 作为非 Docker 机器的稳定本地方案。
