# 版本记录：v2.1.6-ai-provider-doubao-support

## 1. 本轮目标

本轮目标是在 V2.1.5 已有 AI Provider 基础配置与安全调用框架上，增量支持豆包 / 火山方舟 Provider。它属于功能补充和可扩展性提升，优先解决“同一套 OpenAI-compatible 调用框架如何承接第二个真实 Provider”的问题。

本轮不做 Market Claw 主链路 AI 改造，不做客户自动回复，不做企业微信 API 真实接入，也不新增复杂 AI 自动化。

## 2. 背景与上下文

V2.1.5 已经建立了租户级 AI 配置页、`AiProviderConfig`、`AiCallLog`、统一调用服务、测试连接和审计记录。历史结论是：Provider 能力应先作为基础设施存在，业务侧仍以人工审核和规则版能力为主。

豆包 / 火山方舟同样可以按 OpenAI-compatible Chat Completions 形态接入，因此本轮不需要复制一套调用服务，只需要在 enum、页面选项、默认配置和文档中补齐 Provider 识别。

## 3. 问题分析

当前系统已有 `DEEPSEEK`、`OPENAI_COMPATIBLE` 和 `MOCK`，但没有单独的豆包 Provider。若只让用户选择 `OPENAI_COMPATIBLE`，后台日志和运营说明无法区分真实服务商，后续按 Provider 做成本、稳定性、错误统计时也不够清晰。

真正需要解决的是 Provider 标识、默认 Base URL 和页面说明，而不是新增一条独立请求链路。

## 4. 候选方案比较

方案一：只使用 `OPENAI_COMPATIBLE` 承接豆包。

优点是无需迁移，改动最小。缺点是日志中无法明确区分豆包，页面也不能给出火山方舟专属说明。考虑到后续可能要按服务商排查调用质量，本轮放弃。

方案二：新增 `DOUBAO` Provider，但复用 OpenAI-compatible 调用服务。

优点是 Provider 标识清晰，默认 Base URL 和说明可独立维护，同时不复制请求逻辑。缺点是需要扩展 Prisma enum 并新增迁移。最终选择该方案。

方案三：为豆包新增独立调用函数。

优点是可完全定制。缺点是当前没有必要，容易让服务层分叉并增加维护成本。本轮明确放弃。

## 5. 最终决策

最终采用“新增 `DOUBAO` Provider + 复用统一 Chat Completions 服务”的方案。

关键决策：

- Prisma enum 增加 `DOUBAO`。
- 默认 Base URL 使用 `https://ark.cn-beijing.volces.com/api/v3`。
- Chat Completions URL 仍由 `getChatCompletionsUrl` 统一拼接。
- 模型 ID 只提供默认参考值，实际以火山方舟控制台开通结果为准。
- 页面只补 Provider 选项和说明，不引入复杂 UI。

## 6. 具体实现

涉及文件：

- `prisma/schema.prisma`：`AiProvider` enum 增加 `DOUBAO`。
- `prisma/migrations/20260518040000_add_doubao_ai_provider/migration.sql`：为 PostgreSQL enum 增加 `DOUBAO`。
- `src/lib/ai-provider.ts`：增加豆包标签、默认 Base URL、默认模型参考值，调用链继续复用 Chat Completions。
- `src/lib/actions.ts`：保存配置时复用 Provider 默认值函数。
- `src/app/app/[tenantSlug]/ai-settings/page.tsx`：Provider 选项增加豆包 / 火山方舟，并补充接入说明。
- `README.md`：补充 V2.1.6 配置说明和验证入口。
- `AGENTS.md`：更新最新一期路径。
- `tests/v216-ai-provider-doubao-support-e2e.spec.ts`：新增专项浏览器端回归测试，覆盖登录、配置保存、测试连接、权限拒绝和主链路页面可访问性。

## 7. 本轮优点

本轮改动保持了最小范围，没有把豆包逻辑散落到业务页面，也没有改变 Market Claw 主链路。Provider 标识更清楚，页面能直接提示火山方舟接入地址和模型 ID 来源，后续日志统计也能按 `DOUBAO` 区分。

统一服务层继续负责请求拼接、调用日志和安全降级，可维护性比复制调用函数更好。

### DOUBAO Provider 说明

`DOUBAO` 表示豆包 / 火山方舟 Provider。它不是新的业务自动化能力，而是 AI Provider 配置层的一个明确服务商标识。默认参考 Base URL 为 `https://ark.cn-beijing.volces.com/api/v3`，但页面继续允许租户手动填写，避免把某个区域、账号或后续官方变更写死为唯一配置。

### OpenAI-compatible 调用说明

豆包 / 火山方舟继续复用 `getChatCompletionsUrl`、`callAiTextCompletion`、`callAiJsonCompletion` 和 `testAiProviderConnection`。服务层使用租户配置中的 `baseUrl`、`model` 和 API Key，不复制独立的 `callDoubao` 函数。这样 DeepSeek、豆包、通用 OpenAI-compatible 和 Mock 仍然走同一套失败记录与安全降级逻辑。

### 配置页面调整说明

`/app/[tenantSlug]/ai-settings` 的 Provider 下拉包含 `DEEPSEEK`、`DOUBAO`、`OPENAI_COMPATIBLE` 和 `MOCK`。页面增加豆包 / 火山方舟说明，提示参考 Base URL、模型 ID 来源和“不新增自动对外动作”的边界。Base URL 和 Model 都仍然是可编辑输入项。

### 调用日志说明

`AiCallLog.provider` 可以记录 `DOUBAO`，调用成功、失败或跳过仍然进入同一张日志表。日志继续不记录完整 API Key、不记录完整 prompt、不记录完整输出，只记录 provider、model、purpose、status、耗时、token 用量和 prompt hash 等排查所需信息。

### 权限说明

本轮不改变 V2.1.5 权限边界：`TENANT_ADMIN` 可以保存、清空和测试 AI Provider 配置；`OPERATOR` 可以查看状态和执行测试；`SALES` 不显示 AI 配置入口，直接访问配置页会被拒绝。`PLATFORM_ADMIN` 不因此获得租户侧业务配置写入入口。

### 安全降级说明

没有配置、未启用、缺少 API Key 或真实请求失败时，系统记录 `SKIPPED` 或 `FAILED`，页面不崩溃，业务主流程继续使用规则版能力。本轮仍然不让 AI 直接写业务数据、不自动采纳知识、不自动降低风险等级、不处理客户侧沟通内容。

## 8. 本轮缺点与代价

本轮需要新增 enum 迁移，旧库必须执行 migrate 后 Prisma Client 才能识别 `DOUBAO`。

页面没有做 Provider 切换后的前端自动填充联动。当前仍然是基础配置表单，用户选择豆包后需要确认 Base URL、Model 和 API Key 是否符合火山方舟控制台配置。这个妥协是为了避免本轮扩大到复杂交互。

API Key 仍沿用 V2.1.5 的占位存储字段，生产环境仍需要正式密钥加密或安全存储方案。

## 10. 本轮结论

豆包 / 火山方舟适合以独立 Provider 标识接入，但不需要独立调用链。后续新增其他 OpenAI-compatible 服务时，也应优先沿用“Provider enum + 默认配置 + 统一调用服务”的方式。

## 11. 下一轮建议

1. 增加 AI Provider 测试沙盒，用低风险 prompt 验证 DeepSeek、豆包和通用 OpenAI-compatible 配置。
2. 再考虑调用成本、失败率和延迟统计，不要先接业务自动化。
3. 生产部署前优先补 API Key 正式加密存储方案。
