# 版本记录：v1.9.1-communication-compliance-config

## 1. 本轮目标

本轮目标是在现有《企业微信业务增长中台》中新增一个“沟通素材合规采集配置中心”。

它不是去接真实企业微信会话存档、电话录音或 ASR，而是把未来自动采集能力的前置边界先做成：

1. 企业可选项；
2. 单独收费能力；
3. 必须申请才能开通；
4. 必须完成企业确认、员工告知、客户提示、采集范围和 AI 使用边界设置后才允许启用。

本轮目标类型属于：

- 功能补充
- 权限与合规边界收口
- 后续真实接口接入前置准备

## 4. 合规采集配置页面说明

页面标题：

- `沟通素材合规采集配置`

页面醒目文案明确说明：

1. 本系统不会默认自动采集沟通内容；
2. 本系统不会偷偷读取企业微信聊天；
3. 本系统不会偷偷读取电话录音；
4. 本系统不会自动发送客户消息；
5. 所有自动采集能力都必须由企业管理员主动开启，并完成合规确认。

同时，页面额外强调：

1. 这是单独收费功能；
2. 必须申请才能开通；
3. 当前版本只做配置中心，不接真实 provider。

## 5. CommunicationComplianceConfig 模型说明

本轮新增模型：

- `CommunicationComplianceConfig`

核心字段：

1. `tenantId`
2. `channel`
3. `status`
4. `provider`
5. `scopeConfig`
6. `noticeConfig`
7. `retentionConfig`
8. `aiConfig`
9. `confirmedById`
10. `confirmedAt`
11. `createdAt`
12. `updatedAt`

新增枚举：

1. `CommunicationComplianceChannel`
   - `WECHAT_ARCHIVE`
   - `PHONE_RECORDING`
   - `ASR_TRANSCRIPTION`

2. `CommunicationComplianceStatus`
   - `DISABLED`
   - `APPLYING`
   - `ENABLED`
   - `PAUSED`
   - `ARCHIVED`

3. `CommunicationComplianceProvider`
   - `MANUAL`
   - `WECHAT_ARCHIVE_PLACEHOLDER`
   - `PHONE_SYSTEM_PLACEHOLDER`
   - `ASR_PROVIDER_PLACEHOLDER`
   - `OTHER`

设计取舍：

1. 使用一张通用表 + 四个 JSON 字段，避免为单轮配置中心引入多张复杂明细表；
2. 通道和状态做成枚举，保证后续真实 provider 接入前就能统一判断；
3. `allowAutoSend` 不单独做数据库布尔列，而是放在 `aiConfig` 中并强制写成 `false`。

## 9. 合规确认说明

企业管理员启用前必须勾选以下六项：

1. 已了解该功能会涉及工作沟通内容处理；
2. 会依法完成员工告知；
3. 会依法向客户进行必要提示；
4. 仅在工作沟通、客户服务、风险留痕、销售跟进辅助范围内使用；
5. 不用于非授权监控或与业务无关用途；
6. AI 内容只作为辅助建议，最终发送和承诺由人工确认。

服务端约束：

1. 未提交收费开通申请，不能进入 `APPLYING` 或 `ENABLED`；
2. 未完成全部合规确认，不能进入 `ENABLED`；
3. `allowAutoSend` 始终强制为 `false`。

## 10. 采集范围说明

当前页面支持配置：

1. 员工范围
   - 全部员工
   - 指定员工
   - 暂不指定，仅占位

2. 业务线范围
   - 全部启用业务线
   - 指定业务线
   - 暂不指定，仅占位

3. 客户范围
   - 全部客户
   - 指定标签客户
   - 指定业务线客户
   - 指定来源客户

本轮实现方式：

1. 员工和业务线用轻量 checkbox；
2. 指定客户标签／来源／业务线先用文本多值输入；
3. 配置只落库，不驱动真实采集任务。

## 11. 数据保留说明

页面支持记录：

1. 是否保留原始聊天文本；
2. 是否只保留 AI 摘要；
3. 是否保留录音文件；
4. 是否只保留转写文本；
5. 数据保留天数。

默认建议：

1. `dataRetentionDays = 180`
2. 保留原文 = `false`
3. 保留摘要 = `true`
4. 保留录音 = `false`

本轮只保存策略，不执行自动清理任务。

## 12. AI 使用边界说明

页面支持配置：

1. 是否允许 AI 生成沟通摘要；
2. 是否允许 AI 生成标签建议；
3. 是否允许 AI 生成任务建议；
4. 是否允许 AI 生成回复建议；
5. 是否允许 AI 做沟通分析；

当前明确边界：

1. 自动发送客户消息暂未开放；
2. 即使页面存在该概念，服务端也会强制 `allowAutoSend = false`；
3. 本轮不做自动发送、不做自动回复、不做 AI 客服。

本轮实际完成的验证如下：

1. `npm run prisma:generate`：通过。
2. `npx tsc --noEmit`：通过。
3. `npm run lint`：通过。
4. `npm run build`：通过。
5. `powershell.exe -ExecutionPolicy Bypass -File custom\\experiments\\run-v11-postgres-check.ps1`：通过。
6. `npx.cmd playwright test tests/v191-communication-compliance-config-e2e.spec.ts --workers=1 --reporter=list`：通过，`3 passed`。

本轮专项测试的实际收口过程：

1. 最初 `prisma generate` 被残留 dev server 占用的 Prisma 引擎 DLL 阻塞；
2. 清理本地 `3000` 端口残留 `node` 进程后，Prisma 客户端生成恢复；
3. Playwright 首次失败点不是业务规则，而是内置 `webServer` 与临时 PostgreSQL 生命周期耦合，登录阶段偶发连不上 `127.0.0.1:55432`；
4. 最终改为“独立 PostgreSQL + 独立 dev server + `PLAYWRIGHT_SKIP_WEBSERVER=1`”的稳定方式；
5. 期间还修正了两个真实收口点：
   - 测试选择器过宽导致 strict mode 失败；
   - 合规前置校验原先直接抛服务端异常，会触发 Next 开发态错误覆盖层，现改为回到当前页面并展示业务提示。

## 16. 风险与未完成项

1. 当前范围配置仍是轻量表达，不是复杂员工树或客户分群配置器。
2. 现在只是“允许未来自动采集”的前置开关，还没有真正 provider 适配层。
3. `OPERATOR` 只读查看已落地，但未来如果企业希望运营参与申请流转，可能要再细分状态权限。
4. 自动发送字段虽然已保留为未来概念，但当前必须继续强制关闭，后续不要误把占位字段当成功能已开放。
5. Playwright 当前仍更适合在“常驻 PostgreSQL + 手动 dev server”模式下稳定运行；若后续继续扩浏览器回归，建议沉淀成统一测试脚本。

## 17. 下一步建议

1. 下一轮如果继续推进，可先补一个 `CommunicationMaterial` 的手动上传/手动粘贴标准化页面，再让本配置决定“未来能否自动写入”。
2. 如果将来接企业微信会话存档或电话系统，优先先做 provider 接口层与配置检查，不要直接在业务逻辑里散落判断。
3. 若进入真实售卖阶段，可增加“申请单号 / 收费状态 / 开通说明”字段，把“单独收费”从文案进一步沉淀成可追踪配置。
