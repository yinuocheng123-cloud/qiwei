# 版本记录：v2.2-pilot-workbench-consolidation

## 1. 本轮目标

本轮目标是把当前系统从“功能平台”继续收口为“销售试点工作台”。这一轮不是新增业务功能，而是按“关停并转”的思路，把不直接服务于客户跟进主线的入口降级、隐藏、合并或转入后台治理。

客户跟进主线固定为：

客户进入 -> 今日待跟进 -> AI 推荐回复 -> 保存沟通记录 -> 跟进沉淀

本轮优先解决的问题是：销售第一次打开系统时，不需要理解 AI Provider、训练审核、资料投喂、合规配置或企业微信配置，只需要知道今天该跟谁、客户说了什么、建议怎么回复、下一步做什么。

## 2. 背景与上下文

本轮承接 `custom/notes/v2.1.9-pilot-demo-path-simplification.md`。V2.1.9 已经把首页从“功能集合”调整为“试点工作台”叙事，并弱化了 AI、企微、合规等低频配置入口。

V2.2 进一步确认产品阶段：当前系统不是自助 SaaS，不适合继续加复杂功能；更适合熟客陪跑试点。系统应服务于一条可演示、可培训、可复盘的销售主路径。

## 3. 问题分析

修改前系统已经具备较多能力：客户管理、跟进任务、资料维护、Market Claw、AI Provider、企业微信提醒、合规配置、审计日志、训练审核和训练复盘。能力本身没有问题，但它们在销售视角里会造成认知负担。

核心矛盾不是“功能不够”，而是“销售路径被后台能力打断”。如果销售需要先理解知识库、Provider、Prompt、治理和配置，试点培训成本会超过 10 分钟目标。

因此本轮采用减法：销售侧只暴露跟进主线；运营和管理员仍可通过后台治理、资料维护和设置入口承接复杂能力。

## 4. 候选方案比较

方案一：继续保留完整功能入口，只在文案中说明推荐路径。

优点是改动小，风险低。缺点是用户第一眼仍会看到很多后台能力，试点演示时容易偏离主线。本轮放弃该方案。

方案二：删除低频功能页面。

优点是系统会变得非常轻。缺点是会破坏已有功能和验证结果，也不符合“能力没有删除，只是降级或转入后台治理”的要求。本轮放弃该方案。

方案三：保留能力，收口入口，把复杂内容转入设置和后台治理。

优点是销售路径变短，同时管理员和运营仍能维护资料、AI 治理和系统配置。缺点是导航和文案需要继续通过人工体验微调。本轮采用该方案。

## 5. 最终决策

本轮采用“主线外露、后台收纳”的策略：

- 首页定位为试点销售工作台。
- 主导航控制在工作台、客户、跟进、资料、设置五类以内。
- SALES 不显示设置和高权限治理入口。
- Market Claw 面向销售时只表达为 AI 推荐回复。
- AI Provider、企业微信、合规、审计、风险策略和 Prompt 归入设置或后台治理心智。
- 不接真实企业微信，不接真实 AI，不新增 Agent，不新增自动化。

## 6. 具体实现

本轮改动分为四类。

第一类：首页和销售路径收口。首页从数据看板和功能导航转为今日销售工作台，突出今日待跟进客户、新线索、高风险/超期客户、今日 AI 推荐回复、今日完成记录和快速新增客户。

第二类：导航收口。租户侧主导航收敛为工作台、客户、跟进、资料、设置。SALES 不显示设置类入口；TENANT_ADMIN 通过设置进入低频配置和后台治理；OPERATOR 聚焦客户导入、资料维护、知识维护和回复审核。

第三类：后台能力转移。AI 能力配置、企业微信提醒、合规配置、审计日志和权限说明收纳到 `/app/[tenantSlug]/settings`。这些能力没有删除，只是从销售主路径移走。

第四类：文档与验证补齐。新增演示脚本、演示数据准备说明、销售最短演示路径、V2.2 smoke checklist，并补充 `typecheck` 脚本。

## 7. 本轮优点

销售路径更短：销售只需要围绕工作台、客户、AI 推荐回复和保存跟进完成日常动作。

首页更像工作台：首屏聚焦今天要处理的客户和动作，而不是系统功能总菜单。

后台能力仍可用：知识维护、资料投喂、训练审核、AI 配置、企微提醒和合规配置仍保留给有权限角色。

演示口径更稳定：demo 文档只保留客户导入、今日跟进、客户详情、AI 推荐回复、人工修改和保存沟通记录。

## 8. 本轮缺点与代价

本轮没有删除复杂能力，只是隐藏和合并入口，因此系统内部复杂度仍然存在。后续如果试点反馈显示某些后台能力长期不用，才适合进一步关停或归档。

新增 `/settings` 是租户内的低频设置归口，但还不是完整系统设置中心。当前更像“收纳页”，不是新业务模块。

代码拆分目前以 re-export 边界为主，主要用于阻止后续继续把所有动作塞进单一文件；尚未彻底迁移所有 import，也没有做大规模重构。

## 9. 验证与结果

已知验证结果：

- `git pull --ff-only`：未执行拉取，原因是 `master` 没有 upstream。
- `npm run typecheck`：此前失败，原因是 `package.json` 没有 `typecheck` 脚本；本轮已补齐脚本。
- `npx.cmd tsc --noEmit`：通过。
- `npm run lint`：通过。
- `npm run build`：通过。

本轮完成后继续执行：

- `git status`
- `npm run typecheck`
- `npm run lint`
- `npm run build`

## 10. 本轮结论

V2.2 的核心结论是：当前项目应进入试点工作台模式，而不是继续扩展平台能力。销售主路径应该足够短，后台能力应该存在但不打扰销售。

企业微信当前仍以内部联系、提醒和配置预留为主，不描述为客户侧自动回复闭环。AI 当前仍是销售建议和后台治理能力，不做自动对外动作。

## 11. 下一轮建议

1. 用真实熟客试点数据跑一次完整演示，只演示客户导入、今日跟进和 AI 推荐回复三条路径。
2. 人工观察销售是否能在 10 分钟内学会从工作台进入客户详情并保存一次跟进。
3. 根据试点反馈决定哪些后台治理入口继续折叠、迁移或阶段性关停，不要先加新功能。
