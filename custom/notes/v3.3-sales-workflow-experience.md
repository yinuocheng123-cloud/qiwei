# 版本记录：v3.3-sales-workflow-experience

## 1. 本轮目标
本轮目标是完成 MarketClaw V3.3“销售工作流体验版”：让销售可以从“今日待跟”进入 Lead 详情，查看客户、最近跟进、智能建议、推荐资料和下一步任务，并完成“复制 / 采纳 / 采纳并创建任务 / 返回待办”的完整人工工作流。

本轮属于销售体验闭环与运行态 smoke 补强，不是接入大模型，不接入 Dify，不接入 LangChain / LangGraph，不自动发送企微，不新增外部官网跳转，不新增企业或业务线，不修改 V3.0 数据模型，不 push。

## 2. 背景与上下文
本轮承接以下历史记录：

- `custom/notes/v3.0-enterprise-businessline-contact-lead-foundation.md`
- `custom/notes/v3.1-lead-followup-copilot.md`
- `custom/notes/v3.2-followup-copilot-adoption-loop.md`

V3.0 已建立“平台 → 企业 → 业务线 → Contact → Lead”的底层归属模型。V3.1 已完成以 Lead 为中心的规则型智能跟进助手，并通过业务线隔离 smoke。V3.2 / V3.2.1 已完成智能建议采纳为 FollowUp / FollowTask 的写入闭环、测试数据清理和审计 metadata 断言。

本轮继续保留 V2.10 / V2.11 的老板端、运营端、销售端角色路径，不重做登录、权限或路由壳。`tenantSlug` 仍是现有路由壳，企业 / 业务线切换只作用于 MarketClaw 内部 scope 和数据库过滤，不影响 CNAS 官网、整木网官网、柚喜饰界官网等独立站点。

## 3. 问题分析
表面问题是 V3.2 已经能采纳建议并落库，但销售的一天工作路径还不够顺：销售需要从待办、高意向或逾期客户快速进入 Lead 详情，并在同一页看清“客户是谁、现在跟到哪里、上次说了什么、这次怎么回、下一步做什么”。

核心矛盾是：不能为了体验优化绕开真实查询，也不能把智能助手做成静态展示。所有入口必须保留当前 `enterpriseKey / businessLineKey`，所有写入仍必须以 Lead 自身 `enterpriseId / businessLineId` 为准。

主要风险点：

- 待办、dashboard、leads 页面链接如果不带 scope，容易切换后丢失企业 / 业务线上下文。
- Lead 详情页如果只展示通用信息，销售仍需要来回找最近跟进、资料和任务。
- 采纳成功如果没有页面反馈，销售无法确认 FollowUp / FollowTask 是否真实写入。
- 老板统计如果新增字段会越过本轮边界，因此只能先基于审计 metadata 做只读统计。

## 4. 候选方案比较
方案 A：新增一个独立“销售 Copilot 工作台”页面。

- 优点：可以完全围绕新体验设计。
- 缺点：会分叉现有 `dashboard / todos / leads / Lead详情` 路径，违背“不重做角色路径”和“最小改动”边界。
- 结论：放弃。

方案 B：只改文案，不改链接、反馈和 smoke。

- 优点：改动最小。
- 缺点：不能证明销售路径真实可跑，也不能防止 scope 丢失。
- 结论：放弃。

方案 C：复用现有页面，补 scope-aware 入口、Lead 详情销售动作卡、采纳后反馈和 smoke。

- 优点：延续现有架构，改动局部，可真实读取当前业务线数据，可用 Playwright 固化路径。
- 缺点：页面体验仍是渐进优化，不是完整重新设计。
- 结论：采用。

## 5. 最终决策
最终采用“现有角色路径 + scope-aware 链接 + Lead 详情动作聚合 + 审计只读统计”的方案。

关键决策：

- `todos / dashboard / leads` 里的任务、客户和高意向入口都保留当前 `enterpriseKey / businessLineKey`。
- Lead 详情页顶部补“下一步跟进卡”，集中展示当前范围、客户类型、阶段、最近跟进、智能助手入口、推荐资料和返回待办。
- `LeadReplyAssistant` 保持规则型建议，不接入真实 LLM，不自动发送企微。
- 采纳后通过页面刷新显示 FollowUp / FollowTask 已写入反馈，不走外部官网，不新增自动发送通道。
- 老板最小统计基于 `AuditLog.metadata.source = "copilot"` 和当前业务线做只读统计，不修改 schema。

## 7. 本轮优点
本轮相比 V3.2 的主要提升是把“能写入”变成“销售顺手能用”。

正向效果：

- 销售从今日待跟可以直接进入 Lead 详情，不需要手动搜索客户。
- 高意向、逾期、任务等入口都保留业务线 scope，降低串线风险。
- Lead 详情页把销售当天最需要的判断信息前置。
- 采纳成功后页面能看到新增跟进记录和新任务反馈。
- 老板端开始有最小可见性，可以看到智能助手是否被销售真实采纳。
- V3.1 / V3.2 smoke 继续作为防串线和写入归属基线。

## 8. 本轮缺点与代价
当前方案仍有以下缺点：

- 仍然是规则型助手增强版，不是真实 LLM Copilot。
- 老板统计依赖审计 metadata，不是正式业务字段；未来若要做经营分析，可能需要结构化字段或专门统计表。
- Lead 详情页的采纳反馈依赖页面刷新和已写入记录展示，还不是前端局部 optimistic update。
- FollowTask 的 copilot 来源仍主要通过 description 和审计 metadata 追溯，schema 没有正式 `source` 字段。
- V3.3 smoke 只覆盖张总整木网会员 Lead 的销售路径，没有扩大到所有业务线全路径。

这些代价是本轮刻意接受的：先保证销售工作流主线跑通，并继续保护不改 schema、不接外部模型、不自动发送企微的边界。

## 10. 本轮结论
V3.3 已把 V3.2 的采纳闭环推进为可运行的销售工作流体验：销售能从待办进入 Lead 详情，看上下文和建议，人工采纳，形成 FollowUp / FollowTask，再返回待办继续处理。

本轮继承的旧结论：

- 智能建议必须以 Lead 自身归属为准。
- URL 或表单 scope 不能覆盖 Lead 的 `enterpriseId / businessLineId`。
- MarketClaw 内部 scope 不影响独立官网。
- 当前阶段不接入 LLM / Dify / LangChain，不自动发送企微。

本轮新增结论：

- 销售体验优化应优先补入口、上下文和反馈，而不是新增复杂 AI 能力。
- 老板最小统计可以先基于审计 metadata 只读实现，避免为早期可见性修改 schema。
- V3.3 smoke 可以作为后续销售工作流体验回归基线。

## 11. 下一轮建议
1. 若继续优化销售体验，优先补柚喜饰界和 CNAS 的同路径 smoke，而不是新增功能。
2. 若 V3.3 smoke 未来进入 CI，可把 V3.2 / V3.3 的测试数据清理逻辑抽成共享测试 helper，减少重复实现。
3. 若未来要接入真实 LLM，先复用 V3.1 / V3.2 / V3.3 smoke，确保模型只影响建议文本，不影响归属、不自动发送企微、不跳外部官网。
