# 版本记录：v1.0-growth-hub-foundation

## 1. 本轮目标

本轮目标是从空目录建立《企业微信业务增长中台》V1.0 基础闭环，完成项目初始化、多租户数据结构、平台总后台、企业项目空间、线索承接、客户类型策略库、销售跟进、公开表单、基础看板、客户导出、企业微信配置预留、README 与开发记录。

本轮目标类型：功能补充、结构基线、可维护性提升。

该问题优先级最高，因为当前仓库没有可运行项目，也没有历史记录。需要先建立可继承的工程骨架，让后续迭代可以围绕真实模块继续推进。

## 2. 背景与上下文

本轮开始前执行了 `git pull --ff-only`，但目录不是 Git 仓库，因此无法拉取远端。仓库内未发现 `AGENTS.md`，也未发现 `custom/notes/` 历史记录，所以本轮作为首轮方案建立基线。

修改前系统状态：本地目录为空，没有 Next.js、Prisma、README、开发记录或数据库结构。

已知约束：

- 项目不是 OA、财务、人事、审批或完整企业微信管理系统。
- 核心不是普通 CRM，而是“不同客户类型匹配不同转化策略”。
- 必须采用 SaaS 多租户设计，企业后台查询必须基于 `tenantId` 过滤。
- V1.0 不做企业微信真实 API 调用，只预留配置结构。
- 客户可导出自己的客户基础数据，但不能导出源码、数据库结构、策略库底层模板、自动化规则和平台配置。

## 3. 问题分析

表面问题是需要一次性实现较多页面和模型；核心矛盾是要在 V1.0 范围内完成可运行闭环，同时不把项目做成泛 CRM 或复杂 OA。

主要瓶颈：

- 没有历史工程基础，需要同时建立项目结构、数据模型和页面路由。
- 真实登录与 RBAC 若完整实现会扩大范围，因此需要开发态身份模拟。
- 企业微信真实 API 需要密钥、安全回调、消息事件处理和线上验证，不适合 V1.0 强行接入。
- 数据库迁移依赖本地 PostgreSQL 连接，当前环境未提供 `.env` 和数据库服务。

## 4. 候选方案比较

方案一：一次性实现完整登录、权限、企业微信 API 和增长中台。

- 优点：更接近生产系统。
- 缺点：范围过大，容易牺牲多租户隔离、策略库质量和可验证性。
- 风险：需要密钥、回调域名、消息加解密、真实企业微信主体，当前本地阶段无法闭环。
- 结论：放弃，留到后续版本。

方案二：只做静态页面和 Prisma schema。

- 优点：速度快，展示效果容易完成。
- 缺点：无法验证公开表单自动生成 Lead、跟进记录、导出和看板统计。
- 风险：看起来完成，实际没有业务闭环。
- 结论：放弃。

方案三：使用 Next.js App Router + Prisma + PostgreSQL schema + Server Actions，先做开发态身份模拟。

- 优点：能覆盖 V1.0 业务闭环，保留真实数据模型和后续接入空间。
- 缺点：权限仍是开发态模拟，未达到生产安全标准。
- 风险：需要本地 PostgreSQL 才能执行迁移和真实表单入库。
- 结论：采用。

## 5. 最终决策

最终采用方案三。

关键决策：

- 用 `tenantSlug` 进入企业空间，但所有企业后台数据查询先解析为 `tenantId`，再用 `tenantId` 过滤。
- 平台后台放在 `/admin`，企业后台放在 `/app/[tenantSlug]/...`，公开表单放在 `/t/[tenantSlug]/...`。
- 使用 `CustomerTypeStrategy` 作为核心模块，在客户详情页自动匹配欢迎语、首发资料、3/7/15 天话术、人工介入条件和推荐下一步动作。
- 使用 Server Actions 完成 V1.0 写入操作，避免为了首版引入过多 API 层样板。
- 对企业微信只建立 `WeComConfig` 和占位页面，`secretEncrypted` 字段按加密值占位，不展示明文。

## 6. 具体实现

涉及文件：

- `package.json`：定义 Next.js、TypeScript、Tailwind、Prisma、PostgreSQL 相关依赖与脚本。
- `prisma/schema.prisma`：定义 Tenant、User、Lead、LeadTag、FollowUp、CustomerTypeStrategy、Material、IntakeForm、WeComConfig 等模型。
- `prisma/migrations/20260512000000_init/migration.sql`：基于 Prisma schema 生成初始化 SQL。
- `prisma/seed.ts`：写入示例租户、用户、四类整木行业策略、资料包和样例线索。
- `src/lib/prisma.ts`：提供 PrismaClient 单例。
- `src/lib/actions.ts`：集中处理租户创建、状态更新、公开表单提交、跟进记录、策略编辑、资料新增和企微配置。
- `src/lib/dashboard.ts`：按 `tenantId` 聚合看板指标。
- `src/lib/tenant.ts`：按 `tenantSlug` 获取租户，并作为企业后台隔离入口。
- `src/lib/options.ts`：集中维护枚举标签。
- `src/components/Shell.tsx`、`src/components/Ui.tsx`：后台页面壳与轻量 UI 组件。
- `src/app/admin/page.tsx`：平台总后台。
- `src/app/app/[tenantSlug]/dashboard/page.tsx`：企业数据看板。
- `src/app/app/[tenantSlug]/leads/page.tsx`：客户线索列表与筛选。
- `src/app/app/[tenantSlug]/leads/[id]/page.tsx`：客户详情、策略推荐、资料推荐和跟进记录。
- `src/app/app/[tenantSlug]/strategies/page.tsx`：客户类型策略库。
- `src/app/app/[tenantSlug]/materials/page.tsx`：资料包管理。
- `src/app/app/[tenantSlug]/wecom/page.tsx`：企业微信配置预留页面。
- `src/app/app/[tenantSlug]/export/page.tsx`、`src/app/app/[tenantSlug]/export.csv/route.ts`：客户基础数据导出。
- `src/app/t/[tenantSlug]/diagnosis/page.tsx`、`src/app/t/[tenantSlug]/material/page.tsx`、`src/app/t/[tenantSlug]/thanks/page.tsx`：公开表单闭环。
- `README.md`：安装、迁移、启动、测试账号、路径和后续计划。
- `AGENTS.md`：记录当前最新一期路径和仓库工作规则。

## 7. 本轮优点

当前方案相比空仓库形成了可运行、可迁移、可继续开发的工程基线。

正向效果：

- 多租户模型从第一版就明确，不需要后续大拆。
- 策略库不是附属字段，而是客户详情和销售动作的核心依据。
- 公开表单会同时生成 `IntakeForm` 与 `Lead`，并写入来源、客户类型、需求类型、意向等级和标签。
- 客户导出只输出基础字段，边界清晰。
- 企业微信配置提前预留，后续可逐步接入客户联系、外部联系人、标签、客户群、应用消息和回调事件。

质量改善：

- 可读性：页面、动作、模型职责分明。
- 可维护性：枚举选项集中维护，查询入口集中使用 `tenantId`。
- 可扩展性：策略库、资料包、表单和企微配置均可继续扩展。
- 调试便利性：种子数据提供 `muwood` 示例企业。

## 8. 本轮缺点与代价

当前方案仍是 V1.0 本地开发态，不是生产安全版本。

已知缺点：

- 没有真实登录、会话、密码校验和完整 RBAC；当前只是开发态身份模拟。
- 企业管理员、销售、运营的权限边界还没有在页面层完全拆分。
- 未接入真实企业微信 API，也没有消息回调验签、解密和重试机制。
- 表单提交后的自动识别主要来自用户选择和 URL source 参数，还不是智能识别。
- 页面样式刻意保持简单，没有复杂图表和高级交互。
- 当前环境没有 PostgreSQL 连接，未实际执行 `prisma migrate dev` 和 `prisma:seed`。

暂时接受的妥协：

- 先使用 Server Actions 形成闭环，后续再按生产需求拆 API、权限中间件和审计日志。
- 先用简单卡片和表格做看板，避免把 V1.0 变成图表系统。
- 先把 `secretEncrypted` 作为加密值占位字段，真实加密和密钥管理后续补。

## 10. 本轮结论

本轮最重要结论：V1.0 应先围绕“渠道来源 + 客户类型 + 转化策略 + 销售跟进 + 老板看板”建立闭环，而不是扩展成泛 CRM 或 OA。

被证实的假设：

- 使用 `tenantSlug` 做路由、`tenantId` 做查询过滤，可以兼顾 URL 可读性和数据隔离。
- `CustomerTypeStrategy` 放到客户详情页，能自然驱动推荐话术、资料和下一步动作。
- V1.0 使用开发态身份模拟，可以让核心业务闭环先跑起来。

以后应默认继承的经验：

- 所有企业后台查询必须先拿 `tenantId`。
- 任何导出功能都必须明确导出边界。
- 企业微信 API 接入前必须先完善密钥加密、回调安全和权限审计。

## 11. 下一轮建议

1. 优先接入真实登录与 RBAC，把平台管理员、企业管理员、销售、运营的权限边界落到中间件和服务层。
2. 配置本地 PostgreSQL，执行 `prisma migrate dev` 与 `prisma:seed`，再用公开表单做端到端入库验证。
3. 增加企业微信 API 适配层草案，先从客户联系、外部联系人和客户标签同步开始，不碰违规群发和聊天抓取。
