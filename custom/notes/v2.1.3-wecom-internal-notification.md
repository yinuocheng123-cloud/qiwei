# 版本记录：v2.1.3-wecom-internal-notification

## 1. 本轮目标

本轮目标是在现有客户管理、跟进任务、Market Claw、训练审核、资料投喂、候选知识和风险分级基础上，新增企业微信内部工作提醒的基础能力。

本轮目标不是做客户侧自动沟通，也不是做复杂消息中心，而是先验证“系统事件发生 -> 企业微信提醒内部人员 -> 人回到系统处理”的闭环。

## 2. 背景与上下文

本轮承接 V2.1.2 的回复风险分级与确认策略。V2.1.2 已明确 HIGH 是风险边界确认，不是主管审批阻断；V2.1.3 延续这个边界，只把内部人员拉回系统处理，不让系统替销售对客户做决定。

仓库此前已有 `WeComConfig` 预留模型和 `/app/[tenantSlug]/wecom` 页面，因此本轮优先复用旧入口，而不是新增重复配置页。

## 3. 问题分析

当前系统已经能产生很多待处理事项，例如逾期任务、训练待审核、候选知识待审核和高风险回复边界提醒，但这些事项主要停留在系统页面内。真实试用时，如果内部人员不回到系统，就会出现“系统知道有事，但人没有被拉回来”的断点。

核心矛盾是：需要内部提醒，但又不能误做成客户侧自动沟通，也不能为了提醒功能引入复杂生产级第三方接口封装。

## 4. 候选方案比较

方案一：直接接入真实企业微信应用消息 API。

优点是更接近最终生产效果。缺点是需要处理 token、secret 安全存储、网络失败、重试、限流和真实外部调用，超过本轮测试边界。本轮放弃。

方案二：只写文档，不落库。

优点是改动最小。缺点是无法验证成员绑定、提醒状态和失败原因，也无法审计。本轮放弃。

方案三：复用配置页，新增成员绑定和通知日志，发送动作先做安全降级。

优点是能验证内部提醒闭环，失败不影响业务主流程，也为后续真实 API 接入留下结构化数据。本轮采用。

## 5. 最终决策

本轮复用 `WeComConfig`，新增 `UserWecomBinding` 和 `WecomNotificationLog`。服务层新增 `src/lib/wecom.ts`，统一处理配置摘要、Secret 掩码、提醒结果判断、通知日志和审计日志。

当前提醒不调用真实企业微信 API。配置缺失、未启用、成员未绑定会记录 `SKIPPED`；配置不完整或未接真实发送 API 会记录 `FAILED`；业务主流程不被阻断。

## 6. 具体实现

具体改动包括：

- `prisma/schema.prisma`：新增通知状态、通知事件类型、成员绑定和通知日志模型，并扩展 `WeComConfig` 最近测试字段。
- `prisma/migrations/20260518020000_add_wecom_internal_notification/migration.sql`：新增数据库迁移。
- `src/lib/wecom.ts`：新增内部提醒服务、安全降级和日志写入。
- `src/lib/actions.ts`：新增配置保存、成员绑定、测试提醒、通用内部提醒动作，并补充审计日志。
- `src/app/app/[tenantSlug]/wecom/page.tsx`：重做为企业微信提醒配置页，展示配置、成员绑定、测试提醒和通知日志。
- 企业微信配置表单支持“留空保持敏感字段原值”和“显式清空 Secret / Token / EncodingAESKey”两种路径，避免误删配置。
- `src/components/Shell.tsx`、`src/app/app/[tenantSlug]/business-lines/page.tsx`：更新入口文案。
- `src/app/app/[tenantSlug]/leads/[id]/page.tsx`：新增客户跟进内部提醒入口。
- `src/app/app/[tenantSlug]/todos/page.tsx`：新增任务内部提醒入口。
- `src/app/app/[tenantSlug]/market-claw/training/review/page.tsx`：新增训练待审核提醒入口。
- `src/app/app/[tenantSlug]/market-claw/ingestion/page.tsx`：新增候选知识待审核提醒入口。
- `src/components/MarketClawAssistant.tsx`：HIGH 风险回复新增风险边界确认提醒入口。

## 7. 本轮优点

本轮用较小改动建立了内部提醒的配置、绑定、日志和审计基础。即使没有真实企业微信配置，系统也能安全记录失败或跳过原因，不会影响客户、任务和 Market Claw 主链路。

提醒入口覆盖了客户详情、逾期任务、训练审核、候选知识和高风险回复，能初步验证“事件把人拉回系统”的价值。

## 8. 本轮缺点与代价

本轮修改了数据库 schema 和 migration，需要执行 PostgreSQL migration/seed 验证。当前没有接入真实企业微信 API，因此 `SENT` 只作为后续可扩展状态保留，默认更常见的是 `FAILED` 或 `SKIPPED`。

当前没有复杂重试队列、限流、批量通知、消息模板和正式 secret 加密方案。`secretEncrypted` 仍沿用旧字段作为占位，生产环境必须接入正式安全存储方案。

## 10. 本轮结论

企业微信提醒应先定位为“内部工作提醒”，而不是客户沟通通道。系统可以提醒人回到系统处理，但不能替销售回复客户，也不能绕过 V2.1.2 的风险边界确认原则。

## 11. 下一轮建议

1. 在真实企业微信测试应用中验证 token 获取和应用消息发送。
2. 增加提醒重试队列、失败重发和批量处理能力。
3. 根据试点反馈决定哪些 HIGH 风险回复需要负责人确认流程。
