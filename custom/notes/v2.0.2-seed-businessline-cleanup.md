# 版本记录：v2.0.2-seed-businessline-cleanup

## 1. 本轮目标

本轮目标是修复《企业微信业务增长中台》本地启动时 `npm run prisma:seed` 在重复执行场景下可能失败的问题。

当前已知报错是：

- `PrismaClientKnownRequestError`
- `Invalid prisma.businessLine.deleteMany() invocation`
- `Foreign key constraint violated`

本轮只修复 seed 的租户清理顺序，不开发新业务功能，不修改麻虾业务规则，不接企业微信 API，不推送远程仓库。

本轮目标类型属于：

- Bug 修复
- 本地演示环境稳定性修复
- 可维护性提升

## 2. 背景与上下文

本轮开始前承接并读取了以下内容：

1. `AGENTS.md`
2. `custom/notes/v2.0.1-local-demo-startup-fix.md`
3. `custom/notes/v2.0-market-claw-sales-reply-assistant.md`
4. `custom/notes/v1.4.5-local-demo-runbook.md`
5. `custom/notes/v1.4.4-local-full-test.md`
6. `prisma/schema.prisma`
7. `prisma/seed.ts`

与本轮最相关的历史结论有四点：

1. 本地启动闭环依赖 `migrate + seed + dev server`，不是只跑 `npm run dev`。
2. `V2.0` 新增了 `MarketClawKnowledgeItem`、`MarketClawTrainingCase`、`MarketClawReplyDraft`、`MarketClawReplyFeedback`，它们和 `BusinessLine`、`Lead` 形成了新的外键链。
3. 现有 `seed.ts` 的租户清理顺序仍然停留在 V2.0 之前，只删除了 `Lead`、`BusinessLine`、`Material`、`TaskTemplate` 等旧表。
4. 当前仓库没有配置当前分支的 upstream，因此本轮开始前 `git pull --ff-only` 仍然失败，但这与本轮 bug 无关。

## 3. 问题分析

问题的表面现象是：

- `seed.ts` 在执行 `prisma.businessLine.deleteMany({ where: { tenantId: tenant.id } })` 时触发外键约束失败。

真正的核心矛盾不是 `BusinessLine` 本身删不掉，而是：

- 在 V2.0 之后，`BusinessLine` 已经被 `MarketClawKnowledgeItem`、`MarketClawTrainingCase`、`MarketClawReplyDraft` 直接引用；
- 同时 `MarketClawReplyDraft` 又会被 `MarketClawReplyFeedback` 和 `FollowUp.marketClawReplyDraftId` 间接引用；
- `Lead` 也会被 `LeadSourceAttribution`、`ImportRow`、`MarketClawReplyDraft`、`MarketClawReplyFeedback` 等表继续引用；
- 旧清理顺序没有先删这些下游记录，所以“租户被实际使用过后，再重复 seed”时就会在清理阶段炸掉。

本轮额外确认了一点：

- 当前空库或刚 seed 完但尚未产生麻虾数据时，`npm run prisma:seed` 可能暂时还能通过；
- 但只要租户里出现了业务线下游数据，再重复 seed 就会暴露这个顺序问题。

## 4. 候选方案比较

### 方案 A：只在 `businessLine.deleteMany` 前补删 Market Claw 三张直接子表

核心思路：

- 只补 `MarketClawKnowledgeItem`
- `MarketClawTrainingCase`
- `MarketClawReplyDraft`

优点：

- 表面改动更少。

缺点：

- `MarketClawReplyDraft` 还会被 `MarketClawReplyFeedback` 和 `FollowUp` 继续引用；
- `Lead` 还会被 `LeadSourceAttribution`、`ImportRow` 等表引用；
- 只补一层仍然可能在下一张下游表上继续报外键错误。

放弃原因：

- 这属于修一半，不能保证“重复执行 seed 成功”。

### 方案 B：按真实外键链重排租户清理顺序

核心思路：

- 以 `schema.prisma` 为准，把会阻断 `Lead` / `BusinessLine` 删除的下游表全部前置删除；
- 按“最下游子表 -> 上游主表”执行。

优点：

- 能覆盖直接和间接依赖；
- 能让 seed 更接近“租户重置”语义；
- 不需要改 schema、迁移、页面或业务逻辑。

缺点：

- 删除区块会比之前更长；
- 需要小心顺序，避免又引入新的反向依赖问题。

最终选择：

- 采用方案 B。

## 5. 最终决策

本轮最终采用“只改 `seed.ts` 租户清理顺序”的最小修复方案。

关键设计决策如下：

1. 不修改 `schema.prisma`，因为问题不在建模，而在清理顺序落后于最新模型结构。
2. 不碰麻虾规则、页面、权限和迁移，只在 `seed.ts` 的删除区块补足下游表。
3. 按真实关系链删除：
   - 先删 `MarketClawReplyFeedback`
   - 再删 `FollowUp`
   - 再删 `MarketClawReplyDraft`
   - 先删 `MarketClawTrainingCase`
   - 再删 `MarketClawKnowledgeItem`
   - 最后再删 `Lead` 和 `BusinessLine`
4. 对 `LeadSourceAttribution`、`ImportRow`、`ImportBatch`、`CommunicationComplianceConfig` 一并清理，避免下一轮 seed 被其它租户侧残留数据卡住。

## 6. 具体实现

本轮实际修改文件如下：

1. `prisma/seed.ts`
   - 在租户清理区块新增中文注释，明确“最下游子表 -> 上游主表”的清理原则。
   - 在 `businessLine.deleteMany` 前补删：
     - `communicationComplianceConfig`
     - `marketClawReplyFeedback`
     - `leadSourceAttribution`
     - `importRow`
     - `importBatch`
     - `marketClawReplyDraft`
     - `marketClawTrainingCase`
     - `marketClawKnowledgeItem`
   - 保留原有业务数据生成逻辑不变。

2. `custom/notes/v2.0.2-seed-businessline-cleanup.md`
   - 新增本轮正式记录。

3. `AGENTS.md`
   - 更新“最新一期路径”到本记录文件。

## 7. 本轮优点

当前方案相比旧实现，有几个明显优点：

1. 不改 schema、不改迁移，风险集中且可控。
2. 清理顺序与当前真实模型结构重新对齐，不再停留在 V2.0 之前。
3. 不只修 `BusinessLine` 的一层外键，还把 `Lead` 和 `Import`、`Attribution`、`MarketClaw` 的间接依赖一起收口。
4. 继续保持 seed 的“可重复执行”目标，不需要跳过 seed，也不需要粗暴清空整个数据库。

## 8. 本轮缺点与代价

这一版也有明确代价：

1. 租户清理区块比之前更长，阅读成本更高。
2. 当前仍是“手工维护删除顺序”，未来如果再新增引用 `Lead` 或 `BusinessLine` 的模型，seed 仍然需要同步更新。
3. 本轮没有顺手重构成通用依赖拓扑删除器，因为那会超出“最小改动修复”的边界。

## 10. 本轮结论

本轮最重要的结论是：

- 当前 bug 的根因不是 Prisma schema 错了，而是 `seed.ts` 的租户清理顺序没有跟上 V2.0 的新外键链。

同时确认了三个继承结论：

1. 对 `BusinessLine` 的重复 seed 清理，至少要前置删除：
   - `MarketClawReplyFeedback`
   - `FollowUp`
   - `MarketClawReplyDraft`
   - `MarketClawTrainingCase`
   - `MarketClawKnowledgeItem`
2. 对 `Lead` 的重复 seed 清理，也要同步前置删除：
   - `LeadSourceAttribution`
   - `ImportRow`
   - `ReplySuggestion`
   - `FollowTask`
   - `FollowUp`
   - `LeadTag`
   - `IntakeForm`
   - `MarketClawReplyDraft`
   - `MarketClawReplyFeedback`
3. `start-local-demo.ps1` 当前主闭环仍然成立，本轮修复后它能继续走完 `migrate + seed + next dev`。

## 11. 下一轮建议

下一步最值得做的 3 件事是：

1. 如果后续还会持续新增引用 `Lead` 或 `BusinessLine` 的模型，建议把 seed 清理区块补一份“依赖更新提醒”注释，避免未来再漏删。
2. 若本地演示经常是在已有 PostgreSQL 常驻进程的机器上执行，可考虑后续单独修补 `start-local-demo.ps1` 对日志文件占用的容错，但这不属于本轮范围。
3. 如果未来要做更强的 seed 回归，可单独补一条“先写入下游外键数据，再重跑 seed”的自动化验证脚本，把这次踩过的坑固定下来。
