# 版本记录：v2.3.1-local-script-convenience

## 1. 本轮目标

本轮目标是新增三个本地开发效率脚本：`scripts/start-local.ps1`、`scripts/test-smoke.ps1` 和 `scripts/stop-local.ps1`。它们用于把 V2.3 已经验证过的本机 PostgreSQL fallback、Next dev、Playwright smoke 流程固化下来，减少后续人工反复输入命令。

本轮属于开发体验和验证流程收口，不改业务功能、不改销售路径、不接真实 AI、不接真实企业微信、不提交、不推送。

## 2. 为什么新增三个脚本

V2.2 到 V2.3 的验证过程中，本地环境的主要成本不在业务代码，而在重复处理旧 node 进程、`.next` 构建缓存、`test-results`、PostgreSQL fallback 和 Playwright webServer 收尾问题。手动执行命令容易漏步骤，尤其是 build 后如果不清理 `.next`，Next dev 可能和生产构建缓存混用。

因此本轮把“停止清理 -> 启动并检查 -> 另开窗口跑 smoke”固化成三个脚本。这样后续试点验收前可以直接复用同一套流程，而不是依赖临时记忆。

## 3. start-local.ps1 做什么

`scripts/start-local.ps1` 从项目根目录运行，负责启动本地开发环境：

1. 检查当前目录是否为项目根目录。
2. 停止旧 node / Next dev 进程。
3. 清理 `.next`。
4. 读取并检查 `.env` 中的 `DATABASE_URL`。
5. 检查 `127.0.0.1:55432` 是否可用。
6. 如果端口不可用，尝试启动本机 PostgreSQL fallback。
7. 数据库可用后执行 `npm.cmd run db:generate`、`db:push` 和 `db:seed`。
8. 继续执行 `typecheck`、`lint` 和 `build`。
9. build 后再次清理 `.next`，避免 Next dev 与 build 缓存混用。
10. 最后执行 `npm.cmd run dev`，进入持续运行状态。

## 4. test-smoke.ps1 做什么

`scripts/test-smoke.ps1` 设计为在另一个 PowerShell 窗口运行。它不会自行启动 Next dev，而是先检查 `127.0.0.1:3000` 是否可用。

脚本会设置：

1. `PLAYWRIGHT_SKIP_WEBSERVER=1`
2. `APP_URL=http://127.0.0.1:3000`

然后依次执行四组 smoke：

1. `tests/v22-pilot-workbench-smoke-e2e.spec.ts`
2. `tests/v221-hide-ai-complexity-smoke-e2e.spec.ts`
3. `tests/v224-stability-smoke-e2e.spec.ts`
4. `tests/v227-materials-checklist-smoke-e2e.spec.ts`

最后输出 `git status --short --branch`，方便直接确认当前工作区状态。

## 5. stop-local.ps1 做什么

`scripts/stop-local.ps1` 用于停止本地开发服务和清理测试缓存：

1. 检查当前目录是否为项目根目录。
2. 停止 node / Next dev 进程。
3. 清理 `.next`。
4. 清理 `test-results`。
5. 检查 3000 端口是否仍有占用。

该脚本不修改业务数据，也不处理 PostgreSQL 数据目录。

## 6. 验证结果

本轮已验证：

1. `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\stop-local.ps1`
2. `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\start-local.ps1`
3. 在另一个 PowerShell 中执行 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\test-smoke.ps1`

实际结果：

1. `scripts\stop-local.ps1`：通过，能够停止 node / Next dev 进程，清理 `.next` 和 `test-results`，并区分 3000 端口的 `LISTENING` 与 `TIME_WAIT` 状态。
2. `scripts\start-local.ps1`：通过，前台运行时已完成 `db:generate`、`db:push`、`db:seed`、`typecheck`、`lint`、`build`，build 后再次清理 `.next`，并进入 `Next dev Ready`。该脚本最后持续运行 dev server，因此在自动化工具里会保持不退出，这是预期行为。
3. `scripts\test-smoke.ps1`：通过。在已有 dev server 条件下，四组 smoke 均通过：V2.2 为 2 passed，V2.2.1 为 3 passed，V2.2.4 为 3 passed，V2.2.7 为 3 passed。

补充的稳定性修正：`scripts/start-local.ps1` 现在会优先复用 `.local/postgres-data`、`tmp/postgres-data`、`custom/experiments/postgres-data` 中已经初始化完成的 PGDATA；如果都没有，就自动在 `.local/postgres-data` 执行 `initdb`，再用 `pg_ctl -D <PGDATA> -o "-p 55432" -l <log> start` 启动。脚本还会在启动前清理残留 `postmaster.pid`，避免 `pg_ctl` 把旧异常状态误判成已有实例。若 `pg_ctl` 仍受 Windows restricted token 影响无法真正监听，脚本会再通过 `scripts/run-postgres-fallback.ps1` 打开一个独立 PowerShell 窗口，直接运行 `postgres.exe` 作为最后兜底。

本轮补充验证结果：

1. `scripts/start-local.ps1`：通过。脚本自动使用 `.local/postgres-data`，在 `pg_ctl` 因 Windows restricted token 失败后启用 `run-postgres-fallback.ps1` 兜底，成功创建 `wecom_growth_hub_demo`，并完成 `db:generate`、`db:push`、`db:seed`、`typecheck`、`lint`、`build`，最后进入 `Next dev Ready`。
2. `scripts/test-smoke.ps1`：通过。脚本新增 `/login` 页面就绪等待，避免只检测端口导致 404 误判；四组 smoke 结果为 V2.2 `2 passed`、V2.2.1 `3 passed`、V2.2.4 `3 passed`、V2.2.7 `3 passed`。
3. `.gitignore`：已补充 `.local/` 和 `tmp/postgres-data/`，避免本地 PGDATA 被误提交。

补充说明：为了模拟“另开一个 PowerShell 窗口执行 smoke”，本轮验证时先在当前会话临时启动 PostgreSQL fallback 和 Next dev，再运行 `test-smoke.ps1`。`test-smoke.ps1` 本身不启动 dev server，只检查 `127.0.0.1:3000` 并执行 smoke。

## 7. 风险与下一步

当前脚本为了贴合本地开发机环境，默认 PostgreSQL fallback 路径为 `D:\tools\pgsql17\pgsql\bin`，数据目录为 `D:\ceshi\qiwei\custom\experiments\postgres-data`。如果换机器，需要同步调整本机 PostgreSQL 路径或改为 Docker Desktop。

`start-local.ps1` 会停止所有 `node` 进程，适合当前项目本地验收使用；如果同一台机器同时运行多个 Node 项目，执行前需要确认不会误停其它开发服务。

下一步建议是在人工验收稳定后，把 V2.1.9 到 V2.3.1 的连续收口改动整理成一次本地提交，但本轮不提交。
