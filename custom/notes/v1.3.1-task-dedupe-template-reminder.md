# 版本记录：v1.3.1-task-dedupe-template-reminder

## 1. 本轮目标

本轮目标是在 V1.3 已完成 `FollowTask` 任务模型、销售工作台、批量操作和平台级审计日志的基础上，补强任务去重、手动任务创建、任务模板和提醒队列基础模型。

这个问题值得优先处理，是因为 V1.3 已经把待办升级为任务驱动，但重复分配、重复阶段更新、重复设置下次跟进时间都可能制造多条同类任务。若不先解决任务质量和提醒边界，后续接企业微信内部应用消息提醒时会放大重复通知和误提醒风险。

本轮属于功能补充和可维护性提升，不做企业微信 API 真实接入，不做智能客服，不做复杂 AI，也不做大规模 UI 重构。

## 2. 背景与上下文

本轮承接 `custom/notes/v1.3-task-workbench-bulk-audit.md`。V1.3 的结论是：任务模型是提醒、销售 SLA、团队复盘和企业微信消息提醒的必要基础，但当时仍明确留下三个缺口：手动创建任务、任务模板配置、任务去重和提醒队列。

修改前系统已经具备真实登录、RBAC、多租户隔离、middleware、AuditLog、客户分配、销售工作台和批量操作。所有新增能力必须延续这些边界，不能把权限只放在前端隐藏里。

## 3. 问题分析

表面问题是工作台可能出现重复任务，运营也缺少主动创建任务的入口。核心矛盾是：任务已经是业务对象，但任务的生产规则还没有统一入口，也没有把“后续提醒”作为任务生命周期的一部分。

主要瓶颈有三个：

1. 自动任务生成分散在分配、跟进、阶段更新和批量操作里，如果没有统一去重入口，很容易重复创建。
2. 运营和企业管理员需要主动安排销售动作，仅依赖客户状态自动生成任务不够。
3. 后续企微应用消息提醒不能直接从页面逻辑触发，需要先有一个可审计、可取消、可重试的队列模型。

## 4. 候选方案比较

### 方案 A：在每个 Server Action 内分别去重

核心思路是在分配、跟进、批量操作等动作里各自查询是否已有任务。

优点是改动小，短期容易补丁式实现。缺点是规则会散落在多个文件，后续新增任务来源时容易漏掉去重和提醒同步。最终放弃该方案。

### 方案 B：把任务创建、去重和提醒同步集中到 `src/lib/tasks.ts`

核心思路是所有自动和手动任务都走 `createTaskWithAudit`。该函数先按租户、客户、负责人、任务类型、开放状态和同一天到期时间查重，命中则更新原任务并同步提醒，未命中才新建。

优点是规则集中、可复用、后续接消息队列时边界清晰。缺点是手动任务也会受同类同日去重影响，用户如果确实想创建两个同类任务，需要未来增加“强制新建”能力。本轮选择该方案。

### 方案 C：直接接入真实消息发送

核心思路是创建任务后直接发送企微应用消息。优点是可立即看到提醒效果，缺点是违反本轮“不做企业微信 API 真实接入”的边界，也会在任务去重未稳定前制造外部副作用。最终放弃。

## 5. 最终决策

最终采用集中式任务服务方案：

- `src/lib/tasks.ts` 统一处理任务查询、去重、创建、自动规则和提醒队列同步。
- 新增 `TaskTemplate` 模型，作为手动创建任务时的快速填充模板。
- 新增 `ReminderQueue` 模型，只生成 `IN_APP` 提醒队列记录，不真实发送消息。
- 任务完成或取消时取消未发送提醒，避免后续消息发送器处理已经无效的任务。
- 页面权限继续通过 `requireTenantAccess`、`requireLeadAccess` 和 `requireTaskAccess` 执行服务端校验。

## 6. 具体实现

- `prisma/schema.prisma`：新增 `TaskTemplate`、`ReminderQueue`、`ReminderChannel`、`ReminderStatus`，并补齐与 Tenant、User、Lead、FollowTask 的关系。
- `prisma/migrations/20260512031000_add_task_template_reminder_queue/migration.sql`：新增模板表、提醒队列表、枚举和索引。
- `src/lib/tasks.ts`：重写为统一任务服务，增加同日同类任务去重、提醒队列创建/更新、提醒取消和自动任务规则。
- `src/lib/actions.ts`：新增手动任务创建、模板创建、模板编辑、模板停用；任务完成/延期/取消会同步提醒队列；所有关键动作写入 AuditLog。
- `src/app/app/[tenantSlug]/task-templates/page.tsx`：新增任务模板管理页面，企业管理员和运营可用，销售不可访问。
- `src/app/app/[tenantSlug]/leads/[id]/page.tsx`：客户详情页新增“创建任务”表单，可选择模板，销售仅能给自己负责的客户创建任务。
- `src/app/app/[tenantSlug]/todos/page.tsx`：销售工作台增加状态、类型、优先级和负责人筛选，并保留任务操作。
- `src/app/app/[tenantSlug]/audit-logs/page.tsx` 与 `src/app/admin/audit-logs/page.tsx`：补充任务模板、提醒队列和去重相关动作筛选。
- `prisma/seed.ts`：补充基础任务模板，并在重复 seed 时先清理提醒队列再清理任务。
- `tests/v131-task-template-reminder-e2e.spec.ts`：新增 V1.3.1 浏览器端验证流程。
- `README.md` 与 `AGENTS.md`：补充 V1.3.1 功能说明和最新记录路径。

## 7. 本轮优点

任务去重从分散判断变成统一入口，减少后续新增任务来源时遗漏去重的概率。

提醒队列虽然暂不发送消息，但已经具备任务、客户、用户、渠道、状态、计划发送时间、重试次数、payload 和错误信息字段，后续接企业微信内部应用消息时不需要重写任务生命周期。

模板能力让运营可以把高频销售动作标准化，客户详情页可以快速创建任务，不再只依赖自动规则。

AuditLog 覆盖了手动任务、模板、去重、提醒创建和提醒取消，方便后续排查重复任务和提醒异常。

## 8. 本轮缺点与代价

当前去重规则是保守的“同租户、同客户、同负责人、同类型、同一天、开放状态”判断。它能减少明显重复，但不能表达“同一天确实要做两个不同目的的同类型任务”的场景。

模板应用没有做复杂前端自动填充，只在服务端创建任务时用模板补齐空白字段。这降低了前端复杂度，但用户在提交前不能直观看到模板最终填充后的完整内容。

提醒队列目前只有写入、更新和取消，没有后台查询页面，也没有真实发送器、重试调度和失败处理流程。

任务模板页面是基础表单式实现，没有版本管理、复制模板、批量启停和模板使用统计。

## 10. 本轮结论

V1.3.1 的关键结论是：任务驱动工作台要继续演进，必须先把任务生产规则集中化，并把提醒作为任务生命周期的附属对象，而不是页面上的临时行为。

本轮没有接企业微信 API，但已经为后续企微应用消息提醒留下了可查询、可取消、可审计的队列基础。

## 11. 下一轮建议

1. 增加提醒队列查询页面和最小发送器抽象，先支持站内提醒状态流转，再接企微应用消息。
2. 增加任务模板复制、按客户类型推荐模板、模板使用次数统计。
3. 为任务去重增加“强制新建”或“重复任务合并提示”，处理同日多个同类任务的真实业务例外。
