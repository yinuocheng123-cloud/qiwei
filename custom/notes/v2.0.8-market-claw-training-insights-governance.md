# 版本记录：v2.0.8-market-claw-training-insights-governance

## 1. 本轮目标

本轮目标是在 V2.0.5「销售自我训练与审核」、V2.0.6「资料投喂与候选知识生成」、V2.0.7「候选知识去重与合并」已经成立的前提下，新增一页轻量、实用的 Market Claw 训练复盘与知识治理入口。

这一轮优先解决的问题不是“继续增加训练功能”，而是让企业能看清：

- 哪些客户问题被反复训练
- 哪些风险问题最多
- 哪些业务线知识最缺
- 哪些候选知识被采纳、合并或驳回
- 哪些销售持续贡献高价值话术
- 企业当前知识成熟度大致处在什么阶段

本轮目标类型属于：

- 功能补充
- 现有链路治理增强
- 可维护性提升

## 2. 背景与上下文

本轮承接以下正式记录：

1. `custom/notes/v2.0.5-market-claw-sales-self-training-review.md`
2. `custom/notes/v2.0.6-market-claw-knowledge-ingestion.md`
3. `custom/notes/v2.0.7-market-claw-candidate-dedupe-merge.md`

承接下来的关键约束有四条：

1. 训练、资料投喂、候选知识审核都已经是人工边界明确的链路，V2.0.8 不应推翻这些链路。
2. 本轮重点是“看清治理状态”，不是继续增加外部接入或新业务流程。
3. 用户明确要求避免复杂 BI、大屏、复杂语义模型、向量检索和新数据库结构。
4. 页面文案不能绑定某个行业，必须适用于不同企业与业务线。

修改前系统已经具备：

- 销售个人训练、保存个人话术、提交审核
- 管理侧训练审核
- 资料投喂、候选知识生成、采纳入库
- 候选知识相似提示、合并、追加、重复驳回、来源追踪

缺的主要不是“功能按钮”，而是“能不能快速看清整个知识治理状态”。

## 3. 问题分析

表面问题是“功能已经不少了，但运营和管理员仍然很难判断下一步该补什么”。真正的核心矛盾有五个：

1. 高频客户问题已经散落在训练、回复草稿、候选知识和正式知识里，但没有统一视图。
2. 风险问题虽然已经被规则识别和审核，但缺少一个总览层去看“哪类边界最容易被反复问到”。
3. 候选知识已经支持采纳和合并，但如果没有复盘页，运营无法判断哪些业务线一直在重复、哪些内容一直被驳回。
4. 销售贡献的高价值话术已经存在，却没有一个轻量入口能提示管理员“应该优先升级谁的内容”。
5. 不同企业知识成熟度不同，如果所有企业都被迫使用同一套复杂治理方式，会带来过度设计。

所以这一轮真正要补的不是新主链路，而是：

- 统计视图
- 角色分层视图
- 轻量治理建议
- 企业阶段判断

## 4. 候选方案比较

### 方案 A：新增独立统计表与离线聚合

核心思路：

- 新增统计表或快照表
- 定时聚合训练、候选知识和知识库数据
- 复盘页直接读聚合结果

优点：

- 查询会更轻
- 后续扩展复杂看板更方便

缺点：

- 本轮会变成“新增 schema + 新增维护逻辑 + 新增一致性风险”
- 与用户要求的“轻量、最小增量”不符
- 当前数据量下属于过早优化

放弃原因：

- 这轮目标是先建立治理视图基线，不值得为此引入额外数据结构和同步负担

### 方案 B：基于现有表服务端聚合

核心思路：

- 直接读取 `MarketClawTrainingCase`、`MarketClawReplyDraft`、`MarketClawKnowledgeItem`、`MarketClawIngestionBatch`、`MarketClawKnowledgeCandidate`
- 在服务端 helper 中做轻量统计和规则判断
- 页面按角色展示全局治理视图或个人复盘视图

优点：

- 改动集中
- 不改 schema
- 直接复用现有训练、候选、知识来源数据
- 与 V2.0.5/V2.0.6/V2.0.7 的设计边界一致

缺点：

- 统计逻辑会集中在 helper 中
- 高频问题和成熟度阶段判断仍然是规则版，不是精确语义分析
- 后续如果数据量显著增长，仍可能需要升级到更稳定的统计层

最终选择：

- 采用方案 B

## 5. 最终决策

本轮最终采用“服务端聚合 helper + 角色分层复盘页 + 通用治理文案”的增量方案。

关键设计决策如下：

1. 不改数据库 schema，不新增统计表。
2. 在 `src/lib/market-claw.ts` 中新增 `getMarketClawTrainingInsights`，由服务端直接聚合现有数据。
3. 新增 `/app/[tenantSlug]/market-claw/insights` 页面：
   - 管理侧显示全局治理
   - 销售只显示个人训练表现
4. 高频客户问题、风险问题、知识缺口和成熟度阶段全部采用轻量规则，不引入复杂模型。
5. 页面文案保持通用，不把复盘页写成行业专属看板。
6. 不新增审计写入动作，避免只读页面导致日志膨胀。

## 7. 本轮优点

相比之前，这一轮的正向效果主要有：

1. 训练、候选知识和知识库不再是三个分散模块，而是第一次被放进统一治理视图。
2. 管理员和运营可以直接看到高频客户问题、风险问题和知识缺口，不必自己在多个页面来回翻。
3. 销售也有自己的复盘入口，但不会看到全租户治理数据，权限边界更清晰。
4. 企业成熟度阶段把“现在该补什么”说清楚了，减少过早追求复杂治理的风险。
5. 整个方案建立在现有数据之上，没有引入额外表结构，改动风险较低。

## 8. 本轮缺点与代价

这轮也有明确的取舍和妥协：

1. 高频问题与风险问题仍然是规则归类，不是真正的语义聚类。
2. 成熟度阶段判断是轻量启发式规则，不是绝对准确的企业诊断。
3. 当前知识缺口判断偏“治理提示”，不能替代真正的业务负责人判断。
4. 复盘页暂时不做导出、不做趋势图、不做月度横向对比。
5. 由于坚持不改 schema，某些统计口径只能依赖现有字段推导，精细度有限。

## 9. 验证与结果

本轮实际验证结果如下：

- `npm run prisma:generate`：通过
- `npm run lint`：通过
- `npm run build`：通过
- `npx tsc --noEmit`：通过
- `npx.cmd playwright test tests/v208-market-claw-training-insights-governance-e2e.spec.ts --workers=1 --reporter=list`：通过，`4 passed`

本轮有两个环境侧说明需要保留：

1. 第一次执行 `npx tsc --noEmit` 时，因为当前 `tsconfig` 包含 `.next/types/**/*.ts`，而这些类型文件需要先由 `next build` 生成，所以第一次 `tsc` 报的是本地生成物缺失，不是业务代码类型错误；在 `build` 成功后重跑 `tsc` 已通过。
2. 第一次执行 V2.0.8 专项 Playwright 时，当前本地数据库缺少前几轮 Market Claw 相关表和字段，页面被 Prisma 运行时报错打断；执行 `npx prisma migrate deploy` 和 `npm run prisma:seed` 后，专项 Playwright 已正常通过。

本轮没有修改 schema、seed 或 migration 文件本身，因此没有额外新增数据库结构验证动作。

## 10. 本轮结论

本轮最重要的结论有三条：

1. Market Claw 到了 V2.0.8，最值得补的不是新链路，而是治理视图。
2. 训练、资料投喂、候选知识和正式知识已经足够支撑一页轻量复盘，不需要立刻引入复杂统计层。
3. 销售、运营、管理员对复盘信息的需求明显不同，角色分层视图比“所有人看同一页”更稳妥。

## 11. 下一轮建议

下一步最值得继续推进的方向有三件：

1. 如果 V2.0.8 使用稳定，可以继续细化高频问题解释，例如展示“命中了哪些关键词、为什么建议补知识”。
2. 如果候选知识与训练量继续增长，再考虑是否增加更稳定的统计层或月度治理节奏。
3. 如果企业阶段判断被证明有帮助，后续可以补“按月复盘”和“业务线质量评分”，但仍应保持轻量治理思路。
