## 3. 问题分析
表面问题：
- 本地数据库最初未启动，`prisma seed` 无法连接
- 旧演示库结构与新 schema 不一致
- 本地 `dev` 页面请求不稳定，业务页运行态难以直接验收

核心矛盾：
- 数据结构已经切到 V3.0，但本地演示库仍停留在旧状态
- 页面侧的切换/隔离依赖真实落库，不能只靠代码判断

## 4. 候选方案比较
方案 A：直接重试 seed
- 优点：最快
- 缺点：旧库结构不匹配，必失败

方案 B：重置本地演示库后再同步 schema
- 优点：能把 schema 与 seed 真正对齐
- 缺点：需要确认只针对本地演示库

方案 C：只跑代码检查，不做落库
- 优点：风险最低
- 缺点：无法证明 V3.0 真正可运行

最终选择：B。

## 5. 最终决策
采用本地安全重置链路：
- 手动启动本地 PostgreSQL fallback
- 执行本地安全 `db:reset`
- 再执行 `prisma db push --accept-data-loss`
- 再执行 `prisma:seed`
- 再执行 `typecheck`

运行态页面验收则优先尝试本地 `dev`，但若工具链不稳定，记录实际阻塞。
