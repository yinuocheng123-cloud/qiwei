# 版本记录：v2.5-marketclaw-platform-boundary

## 1. 本轮目标

本轮目标是进入 V2.5「MarketClaw 平台化与 CNAS 试点并行阶段」，把平台底座和行业模板的边界收口清楚。优先处理的原因是：V2.3/V2.3.5 已经完成平台化表达，但 CNAS 历史记录仍容易被理解为“项目接入”或“新系统”，需要在不扩展复杂功能的前提下，用最小结构标注说明“平台是底座，CNAS 是模板”。

目标类型：可维护性提升、边界定义、轻量数据结构补充。

## 2. 背景与上下文

本轮承接 `custom/notes/v2.3.6-local-postgres-fallback-hardening.md`。V2.3.6 的核心约束是：不改业务功能、不改销售路径，只修复本地 PostgreSQL fallback 与 smoke 稳定性；AI、企业微信和 SALES 权限边界不变。

更早的 `custom/notes/cnas-project-growth-center-integration.md` 已经说明 CNAS 不应单独新开系统，而是复用现有客户、标签、任务、资料和公开表单能力。V2.3/V2.3.5 又把系统整体收口为 MarketClaw 通用销售工作台。因此本轮只补一层轻量租户模板标识，不引入模板系统。

## 3. 问题分析

当前核心矛盾不是功能缺失，而是产品边界表达不够稳定：平台能力、演示样板和 CNAS 试点内容混在同一个租户/seed 语境中，后续代理容易误以为要新增模板中心、CNAS 独立后台、真实 AI、真实企业微信或 Agent。

Schema 里 `Tenant` 只有 `industry`，无法表达“这个租户当前使用哪个样板”。如果继续只靠 `industry`，它会把行业属性、模板属性和租户业务定位混在一起。最小解决方式是在 `Tenant` 上增加可选 `templateKey/templateName`，只做标注，不驱动复杂运行时逻辑。

## 4. 候选方案比较

方案 A：新增完整模板系统。

核心思路是新增 Template 表、模板配置、模板物料和模板管理后台。优点是未来扩展能力强；缺点是当前需求远未到这个阶段，会增加迁移、权限、后台入口、测试和维护成本，也容易打破销售主路径。本轮放弃。

方案 B：继续只用 `industry` 表达模板。

优点是零 schema 改动；缺点是 `industry` 只能说明行业或业务领域，不能清楚表达通用样板、CNAS 试点模板这类产品边界，后续记录和 seed 也缺少可追踪字段。本轮放弃。

方案 C：在 `Tenant` 上增加可选 `templateKey/templateName`。

优点是改动小、可追踪、兼容现有租户；缺点是它只是标注，不提供模板生命周期、复制、版本管理或差异合并能力。本轮选择该方案，因为它正好匹配 V2.5 的边界收口目标。

## 5. 最终决策

采用方案 C。MarketClaw 仍是平台底座；CNAS 是挂在平台底座上的试点模板。`templateKey/templateName` 只用于标注当前租户样板，不参与权限判断、不改变路由、不改变销售工作流、不新增模板后台。

## 6. 具体实现

- `prisma/schema.prisma`：在 `Tenant` 增加可选 `templateKey`、`templateName`。
- `prisma/migrations/20260528010000_add_tenant_template_metadata/migration.sql`：补充两个可空文本列。
- `prisma/seed.ts`：为 `SeedTenantInput` 增加模板字段，并在三个 seed 租户中标注通用销售样板或 CNAS 认可试点模板。
- `src/app/app/[tenantSlug]/dashboard/page.tsx`：轻量调整工作台描述，说明平台承接统一能力，模板只决定样板数据和业务语境。
- `src/app/app/[tenantSlug]/materials/page.tsx`：轻量调整资料页描述，说明资料管理属于平台能力，模板只提供默认资料结构和试点内容。
- `src/app/app/[tenantSlug]/leads/[id]/page.tsx`：轻量调整客户详情页描述，说明客户跟进能力属于平台，模板只提供行业语境。
- `README.md`：补充 V2.5 平台 / 模板边界说明。
- `AGENTS.md`：更新最新一期路径和当前 V2.5 原则。
- `custom/demo/cnas-template-overview.md`：新增 CNAS 模板说明。

## 7. 本轮优点

本轮把平台能力和模板内容拆清楚了：平台继续负责客户、跟进、资料、任务、权限、MarketClaw 辅助和治理边界；模板只负责 seed 数据、业务线、资料包、任务模板、问卷和行业话术。这样后续继续做 CNAS 或其它试点时，不需要重复争论是否要重开系统。

同时，`templateKey/templateName` 是低成本元数据，不会影响已有路由、权限、销售主路径或 AI/企微边界。

## 8. 本轮缺点与代价

当前方案不提供完整模板生命周期。它不能完成模板复制、模板升级、模板差异对比、模板权限、模板版本回滚或多模板组合。如果后续真的要做行业模板市场，本轮字段只能作为早期标注，不能替代正式模板模型。

页面文案只做轻量提示，没有新增模板切换入口，因此用户不会在 UI 中管理模板。这是刻意接受的妥协，避免把 V2.5 变成复杂模板系统。

- `npm.cmd run db:seed`：通过，三个 seed 租户已写入模板标注。
- `npm.cmd run typecheck`：通过。

验证结论：新增租户模板标识没有破坏销售主路径、AI 复杂度隐藏、稳定性兜底和资料清单权限边界。

## 10. 本轮结论

V2.5 的关键结论是：MarketClaw 平台底座与 CNAS 试点模板可以并行，但不能混淆。平台负责通用工作流和权限边界；CNAS 负责专业服务语境和试点数据。当前只需要轻量模板标注，不需要模板系统。

## 11. 下一轮建议

1. 如果后续新增第二个行业试点，继续先用 `templateKey/templateName` 和 seed 差异验证，不急着做模板后台。
2. 如果多个模板开始需要升级、复制或版本管理，再设计独立模板模型。
3. CNAS 试点下一步更适合优化问卷转化和销售资料质量，而不是扩展底层平台能力。
