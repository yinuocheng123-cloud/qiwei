# 版本记录：v1.4.1-demo-guide-page

## 1. 本轮目标

本轮目标是在不新增复杂业务能力、不调整现有 RBAC 主体结构、不破坏 seed 和既有 Playwright 基线的前提下，为 `zhengmu-demo` 样板企业补一个系统内“演示说明页”。

这个页面的优先级高，是因为 V1.4 已经把整木行业样板数据准备完整，但演示仍依赖 README 或口头说明，缺少系统内统一入口。V1.4.1 的任务就是把“如何讲这套系统”也产品化，方便企业管理员、运营和销售在演示前快速进入同一讲解路径。

## 2. 实际完成内容

1. 新增租户页 `/app/[tenantSlug]/demo-guide`，页面标题为“整木行业演示说明”，副标题突出“按客户类型驱动跟进策略的企业微信业务增长中台”定位。
2. 页面内补齐系统一句话说明、推荐演示顺序、四类客户路径卡片、老板视角、销售视角和产品边界。
3. 在租户后台导航中增加“演示说明”入口，保证演示账号登录后可直接进入。
4. 新增 demo-guide 专项 Playwright 测试，覆盖企业管理员访问、销售访问、未登录跳转登录、跨租户拒绝和核心文案存在。
5. 更新 README，把演示说明页加入默认访问路径和整木行业演示路径说明。

## 3. 页面结构

页面结构延续 V1.4 样板数据的讲解顺序，避免新增复杂交互：

1. 系统一句话说明：用四句话讲清“客户来源识别、客户类型识别、系统提醒、老板看板”。
2. 推荐演示顺序：按 dashboard、客户列表、四类客户详情、销售工作台、审计日志的顺序组织成 8 步。
3. 四类客户路径卡片：分别展示业主客户、经销商客户、设计师客户、工厂客户的关心点、推荐资料、推荐话术方向、推荐下一步动作和建议查看的样板客户链接。
4. 老板视角：突出来源、负责人、跟进阶段、高意向、逾期任务和待激活客户。
5. 销售视角：突出今日任务、逾期客户、高意向客户、下一句话、下一份资料和下一步动作。
6. 产品边界：明确本系统只做企业微信业务增长中台，不覆盖财务、人事、行政、审批、OA，也不接管企业微信主体。

## 4. 权限说明

本轮没有重写原有租户权限模型，只做了一个最小的窄口扩展：

1. `TENANT_ADMIN`、`OPERATOR`、`SALES` 仍然只能访问自己租户下的 `demo-guide`。
2. 未登录访问 `/app/[tenantSlug]/demo-guide` 仍然跳转 `/login?next=...`。
3. 跨租户访问仍然进入 `/forbidden`。
4. `PLATFORM_ADMIN` 仅对 `/app/[tenantSlug]/demo-guide` 增加了页面级访问能力，用于平台方进入租户空间做演示讲解；这个例外没有扩展到其他租户业务页。

## 5. 测试结果

本轮新增 `tests/v141-demo-guide-page.spec.ts`，实际覆盖并验证了以下断言：

1. 企业管理员可访问 `/app/zhengmu-demo/demo-guide`。
2. 页面显示“整木行业演示说明”。
3. 页面显示四类客户：业主客户、经销商客户、设计师客户、工厂客户。
4. 页面包含“推荐演示顺序”与第一步说明。
5. 销售账号可访问本租户 demo-guide。
6. 未登录访问跳转 `/login`。
7. 跨租户访问仍被拒绝。

实际验证结果如下：

1. `npm.cmd run prisma:generate`：通过。
2. `npx.cmd tsc --noEmit`：通过。
3. `npm.cmd run lint`：通过。
4. `npm.cmd run build`：通过，构建结果中已出现 `/app/[tenantSlug]/demo-guide` 动态路由。
5. `powershell.exe -ExecutionPolicy Bypass -File custom\\experiments\\run-v11-postgres-check.ps1`：通过，说明迁移、seed 和 V1.4 样板数据闭环未被本轮页面改动破坏。
6. `npx.cmd playwright test tests/v141-demo-guide-page.spec.ts --workers=1 --reporter=list`：在“临时 PostgreSQL + 单独 seed + 手动 dev server”环境下 4/4 通过。

补充说明：

- Playwright 首轮失败并不是页面真实缺陷，而是测试里对“业主客户”使用了过宽的 `getByText("业主客户")`，同时命中了“推荐演示顺序”里的步骤文案和客户路径卡片标题。
- 这一点延续了 V1.3.2 的经验：复合页面应优先使用 `heading`、表单或区块级定位，不要用会命中多个重复文本的宽泛断言。
- 将断言收窄为 `getByRole("heading", { name: "业主客户" })` 后，V1.4.1 单 spec 稳定通过。

## 6. 风险与未完成项

1. 页面内容目前以整木行业样板数据为主，其他租户虽然可以进入并看到通用结构，但示例讲解仍然偏向 `zhengmu-demo`。
2. 本轮没有新增更细的视觉状态区分，例如“推荐老板演示”或“推荐销售演示”按钮，只保留静态说明，优先保证最小改动和稳定性。
3. Playwright 仍依赖本地 PostgreSQL、seed 和 dev server，可运行性仍受本地环境约束。

## 7. 下一步建议

1. 如果后续继续强化演示体验，可以给 demo-guide 增加“推荐打开样板客户”快捷跳转后的高亮提示，但这不属于本轮范围。
2. 如果后续扩展到更多行业样板，可以把 demo-guide 的文案来源逐步配置化，而不是继续写死在页面里。
3. 如果要让平台方更顺滑地带看多个租户，可再评估是否需要平台侧的“租户演示入口索引页”，但不应在没有明确需求前提前扩张。
