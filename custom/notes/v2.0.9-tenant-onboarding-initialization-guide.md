# 版本记录：v2.0.9-tenant-onboarding-initialization-guide

## 1. 本轮目标

本轮目标是在现有客户管理、业务线配置、Market Claw、资料投喂、销售训练和训练复盘基础上，新增一页“企业开通与初始化向导”。

这一轮要解决的不是日常使用问题，而是新企业第一次启用系统时最容易卡住的问题：

- 第一天先做什么
- 先建哪些业务线
- 先导哪些客户
- 先准备哪些资料
- 什么时候让销售开始用
- 老板怎么判断系统是不是已经真正跑起来

本轮目标类型属于：

- 功能补充
- 首次开通引导增强
- 可维护性提升

## 2. 背景与上下文

本轮承接以下正式记录：

1. `custom/notes/v2.0.6-market-claw-knowledge-ingestion.md`
2. `custom/notes/v2.0.7-market-claw-candidate-dedupe-merge.md`
3. `custom/notes/v2.0.8-market-claw-training-insights-governance.md`

承接下来的关键约束有五条：

1. 不扩展外部沟通接入，不处理客户侧消息，不处理音频素材。
2. 不做复杂 SaaS 计费，不做复杂租户开通后台。
3. 不改现有核心业务逻辑，不破坏 V2.0.5～V2.0.8 已有链路。
4. 页面文案必须通用，不能强绑定某个行业。
5. 用户明确要求第二阶段完成后先不要提交。

修改前系统已经具备：

- 客户导入与来源归因
- 业务线 / 产品配置
- Market Claw 知识库、资料投喂、训练审核、训练复盘
- 销售侧跟进工作台、客户列表、我的训练和回复记录

缺的不是“功能是否存在”，而是“新企业第一次启用时该按什么顺序把这些功能跑起来”。

## 3. 问题分析

表面问题看起来像“少一个引导页”，但核心矛盾其实有四个：

1. 系统已经有很多模块，但首次启用顺序不清楚，容易让企业一上来就迷失在配置里。
2. 企业发展阶段不同，初始化路径不应该完全一样。
3. 管理员、运营和销售在初始化阶段的任务不同，需要明确边界。
4. 如果没有上线检查清单，企业很难判断自己现在到底是“还没准备好”还是“已经可以试运行”。

所以这一轮要补的不是更多功能，而是：

- 七步初始化结构
- 企业阶段判断
- 推荐初始化路径
- 上线检查清单
- 角色分层入口

## 4. 候选方案比较

### 方案 A：新增独立开通配置模型并保存全部步骤进度

核心思路：

- 新增 `TenantOnboardingProfile`
- 为每个步骤存状态、跳过记录和备注
- 后续再扩成更完整的租户开通后台

优点：

- 进度持久化更完整
- 后续继续扩展更方便

缺点：

- 本轮会引入 schema、迁移和更多维护逻辑
- 与用户要求的“轻量初始化向导”不一致
- 当前还没有足够证据说明必须先持久化每一步状态

放弃原因：

- 本轮优先目标是先建立初始化基线，而不是先建复杂的开通状态机

### 方案 B：基于现有数据动态判断 + 轻量入口

核心思路：

- 直接读取租户、业务线、客户、导入、Market Claw 相关数据
- 动态判断企业当前阶段和初始化建议
- 不保存复杂步骤状态，只在页面中给出当前状态和推荐动作

优点：

- 不改 schema
- 改动集中
- 能直接复用 V2.0.8 的训练复盘思路
- 更符合首次上线的轻量指引定位

缺点：

- 不会记住“某一步被手动跳过”
- 某些基础信息只能展示当前系统已有数据，不能完整沉淀成开通档案
- 阶段判断仍然是规则版，不是正式评分体系

最终选择：

- 采用方案 B

## 5. 最终决策

本轮最终采用“动态判断 + 首页引导入口 + 七步初始化结构 + 上线检查清单”的最小增量方案。

关键设计决策如下：

1. 不新增 schema，不新增 `TenantOnboardingProfile`。
2. 新增 `/app/[tenantSlug]/onboarding` 页面，供 `TENANT_ADMIN`、`OPERATOR` 使用。
3. `SALES` 不显示初始化向导入口，也不参与初始化后台。
4. 入口放在首页引导卡片和首页导航子入口中，不单独扩一级导航。
5. 阶段判断继续采用轻量规则，并复用 V2.0.8 的治理视角。
6. 页面只做引导和跳转，不改客户管理、业务线配置或 Market Claw 的既有业务逻辑。

## 6. 具体实现

本轮主要改动如下：

1. `src/lib/auth.ts`
   - 新增 `canAccessTenantOnboarding`
   - 只允许 `TENANT_ADMIN`、`OPERATOR` 访问初始化向导

2. `src/components/Shell.tsx`
   - 在首页导航组中为高权限角色补充“初始化向导”子入口
   - `SALES` 仍不显示该入口

3. `src/app/app/[tenantSlug]/dashboard/page.tsx`
   - 新增首页引导卡片“初始化向导”
   - 只对 `TENANT_ADMIN`、`OPERATOR` 展示

4. `src/app/app/[tenantSlug]/onboarding/page.tsx`
   - 新增初始化向导页面
   - 页面结构分为 7 个步骤：
     1. 企业基础信息
     2. 企业发展阶段判断
     3. 业务线初始化
     4. 客户数据准备
     5. Market Claw 资料投喂准备
     6. 销售使用准备
     7. 上线检查清单
   - 每一步都提供：
     - 当前说明
     - 推荐动作
     - 完成状态
     - 去配置按钮
     - 先跳过按钮
     - 风险提醒
     - 下一步建议

5. `README.md`
   - 补充 V2.0.9 初始化向导说明

6. `AGENTS.md`
   - 更新最新一期记录路径

7. `tests/v209-tenant-onboarding-initialization-guide-e2e.spec.ts`
   - 新增专项 Playwright 回归

## 7. 本轮优点

相比之前，这一轮带来的直接收益主要有：

1. 新企业第一次启用系统时终于有了明确顺序，不必自己在多个页面之间猜。
2. 初始化向导不会改写已有业务链路，只负责告诉用户“先做什么”。
3. 企业阶段判断和初始化路径建立了联系，不再强迫所有企业走同一套开局。
4. 首页就能看到入口，管理员和运营不容易错过。
5. SALES 继续保持轻量工作入口，不会被初始化后台打扰。

## 8. 本轮缺点与代价

这轮也有明确取舍：

1. 当前不保存完整初始化进度，所以“跳过步骤”只是页面导航行为，不是持久化状态。
2. 某些企业基础信息只能展示当前已有系统数据，不能像正式档案那样完整保存。
3. 企业阶段判断仍是轻量规则，不适合作为正式评分体系。
4. 上线检查清单当前只做静态阈值判断，不做历史趋势和分阶段记忆。
5. 如果后续要做复杂租户开通后台，这一轮的动态判断方案可能需要再升级。

## 10. 本轮结论

本轮最重要的结论有三条：

1. 当前系统最缺的不是更多后台功能，而是“新企业第一次怎么跑起来”的清晰路径。
2. 基于现有数据动态判断，已经足够支撑第一版初始化向导，不需要立刻引入复杂开通模型。
3. 初始化向导和训练复盘形成了自然衔接：前者负责“怎么开始”，后者负责“跑起来之后怎么看清和怎么治理”。

## 11. 下一轮建议

下一步最值得继续推进的方向有三件：

1. 如果初始化向导被频繁使用，再考虑是否增加轻量持久化进度。
2. 如果企业阶段判断被证明有帮助，可以继续补“按路径推荐具体动作包”。
3. 如果要继续深化开通体验，优先补“初始化模板与样板数据引导”，而不是先扩复杂后台。
