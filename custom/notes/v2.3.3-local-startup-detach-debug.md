# 版本记录：v2.3.3-local-startup-detach-debug

## 1. 本轮目标
本轮目标是继续修复本地启动链路，让 PostgreSQL fallback 和 Next dev 能稳定打开，供人工试用使用。

## 2. 背景与上下文
V2.3.2 已经把本地启动脚本收口为前台 `start-local.ps1` + 独立 `check-local.ps1` / `stop-local.ps1` 的结构，但在自动化会话里，脱离当前 shell 后进程常会被回收。

## 3. 问题分析
表面现象是 `55432` / `3000` 不能稳定常驻。

真正的问题有两层：
1. PostgreSQL fallback 之前通过 `Start-Job` 绑定在父 PowerShell 生命周期上，父进程结束后数据库会掉。
2. 自动拉起 `start-local.ps1` 时，进程在当前工具会话里可以跑到 Ready，但脱离会话后又会被回收，导致不能形成真正的常驻试用状态。

## 4. 候选方案比较
### 方案 A：继续用 PowerShell Job
优点：实现简单。
缺点：生命周期绑定父进程，不适合常驻。

### 方案 B：改成 `pg_ctl` / 独立 `postgres.exe`
优点：更接近真正常驻的本地数据库进程。
缺点：在当前权限环境里 `pg_ctl` 会报 `could not create restricted token`，直接可用性不稳定。

### 方案 C：用独立启动器脱离当前 shell
优点：理论上最接近用户手工在窗口中保持启动器打开的方式。
缺点：在当前自动化会话里仍然会遇到被回收的问题，无法百分之百验证持续存活。

## 5. 最终决策
本轮保留并增强本地脚本，优先让脚本更可观测、更明确地判定端口状态。
同时补充了一个自动化启动器思路，但没有把它作为正式依赖路径纳入最终收口。

## 6. 具体实现
修改了：
1. `scripts/start-local.ps1`
2. `scripts/stop-local.ps1`

核心调整：
1. 启动脚本不再无差别停止所有 `node`，改为只处理占用 3000 的旧 Next。
2. PostgreSQL fallback 改成更明确的 `pg_ctl` 启停思路，并保留日志输出与端口验证。
3. 停止脚本同步补齐了 `pg_ctl stop` 和端口级兜底停止逻辑。

## 7. 本轮优点
1. 脚本边界更清楚了。
2. 端口检查更直接。
3. 不会再轻易误杀整个 `node` 生态。

## 8. 本轮缺点与代价
1. 当前自动化会话里，脱离 shell 后进程仍然可能被回收。
2. `pg_ctl` 在这台机器的当前权限环境下曾报过 token 错误。
3. 自动化启动器思路还没有达到“完全稳定可复现”的程度。

## 9. 验证与结果
验证过的事实：
1. `start-local.ps1` 前台执行时，能完成数据库准备、生成、push、seed、typecheck、lint、build，并到达 Next Ready。
2. `/login` 与 smoke 的可用性在前台执行路径下曾短暂成立。

未完全达成的部分：
1. 还没把“脱离当前工具会话后的常驻”彻底做稳。

## 10. 本轮结论
本轮最重要的结论是：本地启动问题不在业务，而在“进程生命周期”。
脚本层已经更清晰，但当前自动化执行环境仍会把脱离会话的进程回收掉。

## 11. 下一轮建议
1. 如果继续做，优先把 PostgreSQL 和 Next 的真正常驻方式做成可复用的独立启动器。
2. 再补一层明确的日志文件，让启动失败能一眼看出卡在哪一步。
3. 若要人工试用，优先用前台 `start-local.ps1` 窗口模式，不要再让启动链路依赖会被回收的后台 Job。
