# 版本记录：v2.0.5-market-claw-sales-self-training-review

## 1. 本轮目标

本轮目标是在 V2.0 已有 `Market Claw` 知识库、回复训练场、客户详情页智能回复、回复记录和跟进建议的基础上，补齐“销售自我训练 + 后台训练审核 + 优秀话术升级”的闭环。

本轮明确不接企业微信 API、不接会话存档、不自动读取聊天、不自动发送客户消息、不接电话录音、不接 ASR、不开发 AI provider。

## 2. 背景与上下文

本轮承接以下记录：

1. `custom/notes/v2.0-market-claw-sales-reply-assistant.md`
2. `custom/notes/v2.0.3-navigation-information-architecture.md`
3. `custom/notes/v2.0.4-page-experience-role-paths.md`

延续的关键结论：

1. `Market Claw` 定位不变：不是 AI 客服，而是懂业务的销售智能助手。
2. 销售的主要工作入口仍然是客户详情页，不是后台管理页。
3. 一级导航和角色路径不能被破坏。
4. 服务端权限边界不能放松。
5. 不能承诺事项、价格边界、效果边界必须高优先级。

## 3. 当前问题

V2.0 到 V2.0.4 已经解决了知识投喂、训练、回复草稿和页面路径问题，但仍有几个明显缺口：

1. 训练素材仍偏后台集中维护，一线销售遇到的真实客户问题无法顺手沉淀。
2. 销售无法先把自己的高频回复保存为个人常用话术。
3. 后台没有专门的“训练审核”入口，难以统一判断哪些销售回复值得升级。
4. 训练结果没有按企业、部门、业务线、个人进行分层，长期容易把企业知识库污染成杂乱经验池。
5. 客户详情页虽然可以生成回复，但“保存为个人话术 / 提交审核”的路径不完整。

## 4. 为什么要做销售自我训练

销售每天遇到的真实问题，是最接近成交现场的训练素材。只靠后台管理员模拟问题，容易遗漏一线表达方式、客户顾虑和异议类型。

因此本轮新增“我的训练”，让销售可以：

1. 输入客户真实问题；
2. 选择业务线、客户类型和客户阶段；
3. 生成三种回复版本；
4. 保存为个人常用话术；
5. 再决定是否提交审核。

这样既能积累一线经验，又不会让个人经验直接污染企业标准。

## 5. 为什么要做后台训练审核

个人训练如果没有审核，就会出现两个风险：

1. 销售把临时可用但边界不稳的话术当成标准。
2. 企业知识库逐渐混入未经校验的效果承诺、价格承诺和过度表达。

因此本轮增加后台训练审核页面，要求管理侧在采纳前确认：

1. 回复边界是否安全；
2. 是否符合业务线口径；
3. 是否适合升级为团队标准或企业标准；
4. 如果不适合，必须给出驳回原因。

## 6. 部门和业务线分层说明

本轮采用轻量实现方案，不新增 `Department` 独立模型，而是在 `Market Claw` 相关表中先保留 `departmentName` 字段。

训练和知识的分层原则如下：

1. 企业级：统一边界、统一口径、统一禁止表达。
2. 部门级：适合部门协作内部复用的话术。
3. 业务线级：适合某条产品或服务线的知识。
4. 个人级：销售自己的常用话术，仅自己可见。

这样可以先以最小改动承接“部门维度”，后续如果系统真的需要 Department 模型，再平滑升级。

## 7. 训练结果状态说明

本轮训练状态扩展为：

1. `DRAFT`
2. `GENERATED`
3. `PERSONAL_SAVED`
4. `PENDING_REVIEW`
5. `TEAM_APPROVED`
6. `ENTERPRISE_APPROVED`
7. `REJECTED`
8. `DISMISSED`

对应的产品语义：

1. 个人草稿或已生成结果先停留在销售自己视角；
2. 保存为个人常用后，只供自己反复使用；
3. 提交审核后，才进入管理视角；
4. 采纳为团队标准或企业标准后，才真正升级为可共享知识。

## 13. 权限说明

本轮没有放松服务端权限。

继续保持：

1. `TENANT_ADMIN` / `OPERATOR` 才能进入训练审核；
2. `TENANT_ADMIN` / `OPERATOR` 才能进入知识库管理；

5. `SALES` 的训练页只查询自己的训练内容；
6. `PLATFORM_ADMIN` 不新增租户业务权限。

## 17. 本轮优点

1. 销售终于可以把真实问题快速沉淀，不必完全依赖后台集中训练。
2. 个人话术、待审核训练、团队标准、企业标准之间的边界更清楚。
3. 管理侧有了明确审核入口，闭环更完整。
4. 客户详情页和 Market Claw 模块之间的路径更顺。
5. 训练、知识、回复记录之间开始共享同一套分层语义。

## 18. 本轮缺点与代价

1. 部门维度仍是轻量字段方案，不是完整 Department 模型。
2. 训练审核页目前仍以轻量表单为主，暂时没有更细颗粒度的权限范围配置。
3. 个人话术和企业知识仍共享同一张知识表，虽然靠层级字段区分，但后续若能力继续扩大，可能需要拆分视图或查询层。
4. 本轮为了快速闭环，训练审核和知识采纳仍偏“逐条处理”，暂未做批量处理能力。

## 20. 本轮结论

本轮最重要的结论是：`Market Claw` 只有补齐“销售自训 -> 提交审核 -> 管理采纳 -> 知识升级”闭环，才算真正进入可持续迭代状态。

同时也验证了另一件事：部门维度在当前系统里先用轻量字段方案就足以落地第一轮产品验证，没有必要为这轮闭环强行引入完整 Department 模型。

## 21. 下一步建议

1. 下一轮可继续细化“审核范围”，例如按部门负责人或业务线负责人限定可见训练提交。
2. 如果个人话术和团队知识继续增长，可考虑把“个人话术库”拆成更独立的视图，减少与全局知识管理页的查询语义耦合。
3. 如果后续要继续增强训练闭环，可以补充批量审核、采纳对比和更细粒度的审核意见模板，但这些不属于本轮必须范围。
