# 版本记录：v3.2-followup-copilot-adoption-loop

## 1. 本轮目标
本轮目标是完成 MarketClaw V3.2“销售采纳闭环版”：在不接入真实 LLM、不接入 Dify、不接入 LangChain / LangGraph、不自动发送企微的前提下，让销售可以在 Lead 详情页对智能建议执行三种动作：

- 复制建议回复。
- 采纳为 FollowUp 跟进记录。
- 采纳并创建下一步 FollowTask。

本轮属于功能补充与数据隔离验证，重点不是扩展新 AI 能力，而是让 V3.1 已有规则型智能跟进助手形成可落库、可审计、可验收的人工采纳闭环。

## 2. 背景与上下文
本轮承接以下历史记录：

- `custom/notes/v3.0-enterprise-businessline-contact-lead-foundation.md`
- `custom/notes/v3.1-lead-followup-copilot.md`

V3.0 已确认 MarketClaw 的底层结构从旧 tenant 混合业务升级为“平台 → 企业 → 业务线 → Contact → Lead → 跟进任务 / 资料 / 话术 / Insights”。V3.1 已建立以 Lead 为中心的智能跟进助手基线，回复建议、资料、任务模板、知识和 MarketClawReplyDraft 都必须按当前 Lead 的 `enterpriseId / businessLineId` 读取。

本轮继续保留 V2.10 / V2.11 的老板端、运营端、销售端角色路径，不重做 UI，不新增企业或业务线，不改 V3.0 数据模型。

## 3. 问题分析
表面问题是：V3.1 已能生成可复制的回复建议，但销售采纳后还没有完整闭环，尤其缺少“采纳并创建下一步任务”的动作。

核心矛盾是：采纳动作是写入动作，必须比生成建议更严格地保护归属边界。URL 参数或表单参数可能伪造 `enterpriseKey / businessLineKey`，但 FollowUp / FollowTask 的真实写入必须来自当前 Lead 自身归属，不能让前端 scope 覆盖 Lead。

本轮还确认了一个 schema 约束：当前 `FollowUp` 没有独立 `contactId / source / ownerUserId` 字段，`FollowTask` 没有独立 `contactId / source / nextFollowAt` 字段。因此本轮不改 schema，而是通过 Lead 关系追溯 Contact，通过审计日志 metadata 记录 `source: "copilot"`、`contactId`、`enterpriseId`、`businessLineId`。

## 4. 候选方案比较
方案 A：修改 Prisma schema，给 FollowUp / FollowTask 新增 `contactId / source` 字段。

- 优点：字段语义最直接。
- 缺点：违反本轮“不改 V3.0 数据模型”的边界，需要迁移与更多回归验证。
- 结论：放弃。

方案 B：只改按钮文案，不新增真实写入逻辑。

- 优点：改动很小。
- 缺点：不能形成销售采纳闭环，也无法满足数据库落库验收。
- 结论：放弃。

方案 C：复用现有 ReplySuggestion 与 FollowUp 链路，新增采纳并创建任务 action，归属从 Lead 读取，来源写入审计 metadata。

- 优点：最小改动、可真实落库、符合 V3.0/V3.1 scope 约束。
- 缺点：`source/contactId` 暂时不是 FollowUp / FollowTask 的直接业务字段，需要通过审计和 Lead 关系追溯。
- 结论：采用。

## 5. 最终决策
最终采用“规则型助手 + 人工采纳 + Lead scope 锁定”的方案。

关键设计决策：

- 复制建议仍然只在前端复制文本，不写库。
- “采纳为跟进记录”写入 FollowUp，并更新 Lead `lastFollowAt`。
- “采纳并创建下一步任务”同时写入 FollowUp 和 FollowTask，并更新 Lead `lastFollowAt / nextFollowAt`。
- FollowUp / FollowTask 的 `enterpriseId / businessLineId / leadId / ownerId` 全部来自当前 Lead，不读取、不信任 URL 或表单 scope。
- 不自动发送企微，不调用外部官网，不接入外部 AI 工作流。

## 7. 本轮优点
本轮相比 V3.1 的主要提升：

- 销售建议从“可看、可复制”推进到“可采纳、可沉淀、可派发下一步任务”。
- FollowUp / FollowTask 写入归属与 V3.0 数据模型保持一致。
- 错误 URL scope 覆盖被正式 smoke 固定下来，后续改动不容易意外回退。
- 不需要修改数据库结构，降低了本轮落地风险。
- V3.1 smoke 继续通过，说明原有业务线隔离能力未被破坏。

## 8. 本轮缺点与代价
当前方案仍有以下缺点：

- `FollowUp` 和 `FollowTask` 没有直接 `source` 字段，`source: "copilot"` 只能记录在审计日志 metadata 和任务 description 中。
- `FollowUp` 和 `FollowTask` 没有直接 `contactId` 字段，只能通过 Lead 的 `contactId` 追溯客户主体。
- “采纳并创建下一步任务”的到期时间暂时固定为次日 18:00，没有从不同客户类型策略中动态取值。
- 新增 V3.2 smoke 会真实写入本地数据库，重复执行会增加 FollowUp / FollowTask 测试记录；这是 smoke 验收可接受的代价，但未来进入 CI 前需要考虑测试数据清理策略。
- 任务创建为保证“新增任务可见”，本轮直接创建 FollowTask，没有走 `createTaskWithAudit` 的同日去重更新逻辑。

## 10. 本轮结论
V3.2 已完成销售采纳闭环的本地实现和 smoke 沉淀。

## 12. V3.2.1 smoke 稳定化补充：2026-06-18

### 本轮目标
本轮目标是对 V3.2 采纳闭环 smoke 做稳定化，并补齐审计 metadata 只读断言。

本轮不是新增功能，不接入 LLM / Dify / LangChain / LangGraph，不自动发送企微，不新增外部官网跳转，不新增企业或业务线，不改 V3.0 数据模型，不 reset 数据库，不 push。

### smoke 数据清理策略
V3.2 smoke 会真实点击页面并写入本地数据库。为避免重复执行持续污染本地库，本轮为测试写入增加固定标识：

- `testRun = "v32-followup-copilot-adoption-loop-smoke"`
- 测试问题前缀：`[v32-followup-copilot-adoption-loop-smoke]`
- 测试 FollowUp 内容前缀：`[v32-followup-copilot-adoption-loop-smoke]`
- 测试 FollowTask 描述中包含：`testRun：v32-followup-copilot-adoption-loop-smoke`
- 审计 metadata 中包含：`testRun`

清理逻辑放在 `tests/v32-followup-copilot-adoption-loop-smoke.spec.ts` 的 `beforeAll` 和 `afterAll` 中。清理范围严格限制在固定测试标识内：

- 通过审计 metadata 的 `testRun` 收集测试 FollowUp / FollowTask / ReplySuggestion。
- 通过 FollowUp content、FollowTask description、ReplySuggestion customerQuestion 的固定标识兜底收集测试数据。
- 删除顺序为 ReminderQueue、AuditLog、FollowTask、FollowUp、ReplySuggestion。
- 不使用 reset，不删除未带测试标识的真实业务数据。

### 采纳 action 的兼容处理
`src/lib/actions.ts` 新增了对可选 `testRun` 表单值的兼容：

- 普通用户界面不会传 `testRun`，生产采纳行为不变。
- smoke 在点击采纳按钮前动态向当前表单插入隐藏 `testRun` input。
- server action 只在收到 `testRun` 时，把该值写入审计 metadata、FollowUp 内容前缀和 FollowTask 描述。

该处理是为了测试数据可追踪、可清理，不改变 V3.0 数据模型，也不新增业务能力。

### 审计 metadata 只读断言覆盖内容
V3.2 smoke 已新增审计 metadata 只读断言，覆盖：

- 采纳为 FollowUp 后，`followup_created` 审计 metadata 包含 `source = copilot`、`testRun`、`leadId`、`contactId`、`enterpriseId`、`businessLineId`。
- 采纳为 FollowUp 后，`reply_suggestion_saved_as_followup` 审计 metadata 同样包含上述字段。
- 采纳并创建 FollowTask 后，`copilot_task_created` 审计 metadata 包含 `source = copilot`、`testRun`、`leadId`、`contactId`、`enterpriseId`、`businessLineId`、`followUpId`、`suggestionId`、`ownerId`、`dueAt`。
- 采纳并创建 FollowTask 后，`reply_suggestion_adopted_with_task` 审计 metadata 同样可以追溯 Lead 归属。
- 当 URL 传入错误 scope 时，FollowUp 与 FollowTask 仍断言写入张总 GEO Lead 自身的整木网业务线归属。
