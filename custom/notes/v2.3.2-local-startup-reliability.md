# 版本记录：v2.3.2-local-startup-reliability

## 1. 本轮目标

本轮目标是修复本地启动链路不稳定的问题，让开发环境真正做到“可检查、可判断、可停止”。

这轮属于本地开发体验与环境可靠性修复，不改业务功能、不改销售路径、不接真实 AI、不接真实企业微信。

## 2. 背景与上下文

V2.3.1 已经把本地启动、smoke 测试和停止清理固化成脚本，但实际运行时仍出现“页面打不开”的问题。

核心现象有两个：

1. PostgreSQL fallback 偶尔没有稳定进入 `55432 LISTENING`。
2. `Next dev` 被放进 worker / 后台流程后，前台和后台的生命周期关系变得不直观，用户容易误关窗口，导致本地页面再次掉线。

因此，本轮需要把启动方式收回为更简单的前台稳定模式。

## 3. 问题分析

表面现象是登录页打不开，实质上是本地启动链路缺少一个硬判断点：

1. 数据库是否真的已经监听 `55432`。
2. `Next dev` 是否真的还在运行。
3. `/login` 是否真的可访问。

旧方案的问题在于把“启动成功”和“长期运行”混在了一起，尤其是 worker 窗口方式会让用户误判当前哪一个窗口才是实际会话。

这不是业务代码错误，而是本地启动流程的可观测性和生命周期设计问题。

## 4. 候选方案比较

### 方案 A：继续使用 worker 窗口

思路：保持之前的 worker 启动模式，让后台窗口继续跑 `npm run dev`。

优点：

- 启动步骤看起来完整。
- 能把数据库检查、构建和 dev 放在一起。

缺点：

- 窗口生命周期不直观。
- 用户容易关闭错误窗口。
- 在这个环境里，Next dev 的 worker 保活不够稳定。

结论：放弃。

### 方案 B：前台启动 `Next dev`，数据库 fallback 仍后台常驻

思路：`start-local.ps1` 只负责前置检查、数据库确认和构建，最后直接在当前 PowerShell 前台运行 `npm.cmd run dev`。

优点：

- 生命周期最清楚。
- 用户一眼知道哪个窗口不能关。
- 不再依赖 worker 窗口保活。

缺点：

- 启动窗口必须一直保留。
- 如果用户想同时做检查或 smoke，需要另开窗口。

结论：采用。

### 方案 C：Windows 任务或系统服务

思路：把 dev 或数据库做成系统任务 / 服务。

结论：不采用。这个方案复杂化太多，也不符合本轮“只修脚本和文档”的目标。

## 5. 最终决策

本轮最终方案是：

1. `scripts/start-local.ps1` 以前台方式运行 `npm.cmd run dev`。
2. PostgreSQL fallback 仍可独立后台常驻，但必须先验证 `55432 LISTENING`。
3. `scripts/check-local.ps1` 负责判断当前环境是否可打开。
4. `scripts/test-smoke.ps1` 只负责测试，不负责启动 dev server。
5. `scripts/stop-local.ps1` 负责停止 node、停止本项目识别得到的 PostgreSQL fallback，并清理缓存。

这意味着本地开发固定为“两窗口工作流”：

- 窗口一：`start-local.ps1`，保持打开。
- 窗口二：`check-local.ps1` / `test-smoke.ps1`。

## 6. 具体实现

本轮修改了这些文件：

1. `scripts/start-local.ps1`
2. `scripts/check-local.ps1`
3. `scripts/test-smoke.ps1`
4. `scripts/stop-local.ps1`
5. `README.md`
6. `custom/dev/local-env-setup.md`

关键改动点：

1. `start-local.ps1` 删除了 worker 启动入口，最后一行直接运行 `npm.cmd run dev`。
2. `start-local.ps1` 在 PostgreSQL fallback 启动失败时会立即停止流程，不再继续后续步骤。
3. `check-local.ps1` 输出 `Result: OPENABLE` / `Result: NOT OPENABLE`，并明确提示是否需要保持 `start-local.ps1` 所在窗口运行。
4. `test-smoke.ps1` 只做测试，不再尝试拉起 dev server。
5. `stop-local.ps1` 增加了对本项目相关 postgres 进程的识别和停止。
6. 文档统一改成两窗口工作流，避免继续引用 worker 窗口。

## 7. 本轮优点

1. 启动方式更直接，用户心智负担更低。
2. 可观察性更好，`55432`、`3000` 和 `/login` 都能被单独验证。
3. `check-local.ps1` 和 `test-smoke.ps1` 的职责边界更清楚。
4. 不再依赖 worker 窗口保活，减少“窗口关了但用户没意识到 dev 已停”的问题。

## 8. 本轮缺点与代价

1. `start-local.ps1` 必须一直开着，不能关闭。
2. 需要另开一个窗口做检查或 smoke，操作上比单窗口稍微多一步。
3. `stop-local.ps1` 只能停止能识别到的本项目 postgres 进程，如果用户手工启动了别的数据库实例，脚本不会越权乱停。

## 9. 验证与结果

本轮完成的是脚本和文档收口，重点是把启动方式从 worker 模式改回前台稳定模式。

当前仍需要在实际机器上再跑一轮：

1. `scripts\stop-local.ps1`
2. `scripts\start-local.ps1`
3. `scripts\check-local.ps1`
4. `scripts\test-smoke.ps1`

验证目标是：

1. `55432 LISTENING`
2. `3000 LISTENING`
3. `/login` 可访问
4. smoke 四组通过

## 10. 本轮结论

本轮最重要的结论是：本地启动链路不应该再把 `Next dev` 交给 worker 窗口。

对于当前环境，最稳妥的方式不是更复杂的后台守护，而是更简单的前台运行：

1. 数据库先稳定。
2. 构建先完成。
3. `Next dev` 直接跑在当前窗口。
4. 另开窗口专门做检查和 smoke。

## 11. 下一轮建议

1. 实际跑一遍两窗口工作流，确认 55432 和 3000 都能长期维持。
2. 如果用户后续仍想“一键关停 PostgreSQL”，再单独补一个明确的数据库停止脚本。
3. 如果未来还要继续减少手工操作，再考虑把检查脚本输出做得更显眼，但不要回到 worker 复杂化方案。
