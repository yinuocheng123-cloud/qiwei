# 版本记录：v2.7.1-cnas-wecom-real-config-checklist

## 1. 本轮目标

本轮目标是不新增业务功能，只把 V2.7 已完成的 CNAS 企业微信真实轻接入整理成可实际配置、可测试、可排错的落地流程。

目标类型：可维护性提升、配置指引补齐、试点落地排错。

## 2. 背景与上下文

本轮承接 `custom/notes/v2.7-cnas-wecom-real-intake.md`。V2.7 已完成企业微信回调接口、签名校验、AES 解密、`WecomCallbackEvent` 日志、外部联系人新增事件承接、来源归因和 CNAS 跟进任务。

V2.7.1 不改变业务链路，只解决真实配置时“字段在哪里找、URL 怎么验证、客户添加事件怎么测、失败去哪里看”的落地问题。

## 3. 问题分析

V2.7 的技术链路已经可用，但真实企业微信联调涉及多个后台字段：CorpID、AgentID、Secret、Token、EncodingAESKey、回调 URL、成员 UserID 和客户联系权限。若页面只显示字段输入框，操作者仍然不知道当前是未配置、待验证还是已收到回调。

因此本轮核心不是新增接口，而是把已有配置与已有事件状态转成检查清单和排错提示。

## 4. 候选方案比较

方案 A：新增一个主动调用企业微信 API 的“测试连接”按钮。

优点是即时反馈；缺点是会扩大本轮功能范围，也可能引入真实网络、IP 白名单、权限错误和外部依赖。本轮明确不选。

方案 B：只新增文档，不改页面。

优点是改动最小；缺点是实际操作者仍要在日志和字段之间来回查，无法一眼判断接入状态。本轮不选为唯一方案。

方案 C：新增文档，并在现有配置页展示真实接入检查清单和回调自检说明。

优点是复用已有配置和 `WecomCallbackEvent`，不新增业务功能；可以让配置人员直接看到字段完整度、最近事件、错误信息和当前接入状态。本轮选择。

## 5. 最终决策

采用方案 C。页面只展示本地已保存配置与已有回调事件，不主动调用企业微信 API；文档补齐企业微信后台配置路径、字段来源、URL 验证、扫码测试和常见失败原因。

继续保持边界：只做客户进入系统，不同步聊天、不自动回复、不采集会话、不做 AI Agent、不扩大 SALES 权限。

## 6. 具体实现

- `custom/demo/cnas-wecom-real-config-checklist.md`：新增企业微信真实配置检查清单。
- `src/app/app/[tenantSlug]/wecom/page.tsx`：新增“真实接入检查清单”和“回调自检说明”，展示必要字段是否已填、回调 URL、最近回调事件、最近错误信息和当前接入状态。
- `AGENTS.md`：更新最新一期路径与 V2.7.1 边界。
- `custom/notes/v2.7.1-cnas-wecom-real-config-checklist.md`：沉淀本轮思路、取舍和验证结果。

## 7. 本轮优点

本轮把真实企微接入从“工程能力”推进成“配置人员可操作流程”。页面状态不依赖外部网络，不会因为企业微信临时不可达导致系统误判；配置人员可以先看字段完整度，再看是否收到可解密回调，最后进入客户详情确认承接结果。

## 8. 本轮缺点与代价

页面状态仍然基于已保存配置和已有事件日志，不代表企业微信后台当前一定配置正确。若企业微信后台之后改了 Token、EncodingAESKey、Secret 或回调 URL，MarketClaw 只能在下一次 URL 验证或事件回调失败时反映问题。

本轮没有做主动探测，也没有新增重试、补偿或错误码解释表，这些可以放到真实联调后继续补。

## 9. 验证与结果

已完成验证：

- `npm.cmd run typecheck`：通过。
- `npm.cmd run lint`：通过。
- `npm.cmd run build`：通过。
- `npx.cmd playwright test tests/v27-cnas-wecom-real-intake-smoke-e2e.spec.ts --workers=1 --reporter=list`：通过，1 个用例通过。

验证过程中发现，V2.7 smoke 原本用全页 `PROCESSED` 文本断言回调事件状态；V2.7.1 新增“真实接入检查清单”和“回调自检说明”后，页面上会合理出现多个 `PROCESSED` 文本。该问题不是业务失败，而是测试定位过宽。最终在真实回调事件项上增加 `data-testid="wecom-callback-event"`，并把断言收窄到包含本次 `external_userid` 的事件卡片，确保测试仍然验证客户承接链路本身。

## 10. 本轮结论

V2.7.1 不需要新增客户承接能力；最有价值的是把 V2.7 的真实回调能力变成可配置、可验证、可排错的操作流程。页面检查清单和文档清单应成为后续真实联调的默认入口。

## 11. 下一轮建议

1. 真实企微联调后，把企业微信错误码和实际失败样例补入排查清单。
2. 增加按 `processedStatus` 过滤回调事件的轻量视图。
3. 若需要主动探测，先设计只读连接测试，并继续禁止聊天同步、自动回复和会话存档。
