# 版本记录：v1.5-smart-followup-assistant

## 1. 本轮目标

本轮目标是在不接企业微信 API、不引入外部大模型、不改变现有权限边界的前提下，为客户详情页补上一层“智能跟进助手基础版”。

优先级高的原因有三点：

1. V1.4 已经具备完整演示样板数据，但销售在客户详情页仍然需要自己临时组织回复。
2. 当前系统已经有客户类型策略、资料包、任务模板和跟进记录，具备做“规则型建议回复”的条件。
3. 这轮目标是销售辅助，不是自动回复，因此可以在现有闭环上做增量补强，不需要引入高风险新基础设施。

本轮目标类型属于：功能补充、可用性增强。

## 3. 问题分析

表面现象是：客户详情页已经能看到客户类型、策略、资料和任务，但销售在面对客户提问时，仍然需要自己临时组织一段回复。

真正的核心矛盾不是“系统没有 AI”，而是“系统知道客户该怎么跟，但还没有把这个知识收口成可直接使用的话术建议”。

当前瓶颈主要有四个：

1. 客户类型策略与资料包已经存在，但没有面向销售的即时回复生成入口。
2. 不同客户类型的资料和跟进方向不同，销售容易临场说偏。
3. 即使生成了建议，如果没有审计与落库，后续就无法追踪“生成过什么、谁保存成了跟进记录”。
4. 如果直接接外部模型，会带来不稳定性、额外依赖和验证复杂度，不符合本轮“基础版”的目标。

## 4. 候选方案比较

### 方案一：直接接外部大模型

核心思路：
在客户详情页输入客户问题后，实时调用外部大模型生成回复建议。

优点：

1. 文案变化更多。
2. 理论上可以更贴近自然语言表达。

缺点：

1. 稳定性受外部接口、密钥、网络和提示词影响。
2. 当前项目还没有为模型调用准备额外的故障处理与缓存策略。
3. 这会把本轮从“销售辅助基础版”升级为“复杂 AI 集成”，超出用户边界。

放弃原因：
不符合本轮“先做规则模板生成，避免不稳定”的明确要求。

### 方案二：规则模板生成

核心思路：
基于客户类型、客户阶段、策略库、资料包和客户问题关键词，生成固定三种风格的建议回复，并把结果落库。

优点：

1. 无外部依赖，稳定可控。
2. 和现有策略库、资料包、RBAC、AuditLog 能直接拼接。
3. 验证成本低，适合当前演示样板阶段。

缺点：

1. 灵活度不如真实模型。
2. 规则覆盖面有限，复杂问题仍然需要销售自行判断。

最终选择原因：
这是当前最小、最稳、最符合版本目标的实现方案。

## 5. 最终决策

本轮最终采用“规则型智能跟进助手”方案，具体决策如下：

1. 新增 `ReplySuggestion` 模型存储建议记录，不新增复杂关联层。
2. 每次固定生成三条建议，分别对应 `DIRECT`、`WARM`、`PROFESSIONAL`。
3. 问题分类先支持价格类、合作类、案例类、交付类、系统对比类和不明确类。
4. 页面统一使用“智能跟进助手”文案，不使用“AI 客服”。
5. 建议回复只做辅助，不自动发送；销售可以复制，也可以保存为跟进记录。
6. 所有生成动作和保存动作都进入 `AuditLog`。

## 7. ReplySuggestion 模型说明

模型字段如下：

1. `id`
2. `tenantId`
3. `leadId`
4. `userId`
5. `customerQuestion`
6. `suggestionText`
7. `recommendedMaterialIds`
8. `recommendedNextAction`
9. `style`
10. `warning`
11. `createdAt`

设计说明：

1. `tenantId`、`leadId`、`userId` 共同保证租户隔离和生成归属。
2. `recommendedMaterialIds` 用 `Json` 数组保存，先满足展示与审计需要，避免现在引入新中间表。
3. 同一次生成的三条建议共用同一个 `createdAt`，便于按批次取回。

## 8. 生成规则说明

本轮没有调用外部 AI。

生成逻辑完全基于规则：

1. 先根据客户问题关键词判断问题类型。
2. 再根据 `customerType` 选择对应的回答方向、推荐资料、下一步动作和注意事项。
3. 结合 `LeadStage` 给出阶段提示。
4. 按三种风格包装成：
   - 直接型
   - 温和型
   - 专业型

输出约束如下：

1. 每条建议控制在 150 字以内。
2. 先回答问题，再自然追问。
3. 不出现自动发送、保证成交、绝对承诺等表达。

## 9. 权限说明

本轮沿用现有权限体系，没有扩大平台管理员权限。

具体边界如下：

1. `TENANT_ADMIN`
   可为本租户任意客户生成建议并保存为跟进记录。
2. `OPERATOR`
   可为本租户任意客户生成建议并保存为跟进记录。
3. `SALES`
   只能为 `ownerId` 等于自己的客户生成建议和保存记录。
4. `PLATFORM_ADMIN`
   不直接进入租户业务建议生成路径。

权限实现上直接复用了 `requireLeadAccess`，避免新逻辑与旧逻辑分叉。

## 10. AuditLog 记录说明

本轮新增两类审计动作：

1. `reply_suggestion_generated`
2. `reply_suggestion_saved_as_followup`

metadata 记录：

1. `leadId`
2. `customerType`
3. `questionType`
4. `style`

取舍说明：

1. 不记录企业微信密钥。
2. 不记录真实敏感配置。
3. 不把完整问题文本塞进审计日志，避免 metadata 过重。

## 11. 本轮优点

1. 不引入外部依赖，就把策略库真正变成了销售可直接使用的建议输出。
2. 和现有客户详情、资料包、跟进记录、审计日志形成了自然闭环。
3. 权限直接复用 `requireLeadAccess`，风险低。
4. 生成建议可复制也可保存，既能演示，也能保留业务过程。

## 12. 本轮缺点与代价

1. 当前是规则模板生成，灵活度不如真实模型。
2. 关键词分类仍然有限，复杂问题会回到“不明确类”。
3. 最新建议批次目前按“当前用户 + lead + createdAt”读取，便于隔离，但跨角色共享建议能力还没有做。
4. 建议保存为跟进记录时默认不修改客户阶段，也不自动创建新任务，仍需要人工判断下一步。

## 13. 验证与结果

本轮实际执行结果如下：

1. `git pull --ff-only`
   未通过，原因是当前 `master` 没有 upstream；按要求只记录，不配置远程。
2. `npm.cmd run prisma:generate`
   通过。
3. `npx.cmd tsc --noEmit`
   通过。
4. `npm.cmd run lint`
   通过。
5. `npm.cmd run build`
   通过。
6. `powershell.exe -ExecutionPolicy Bypass -File custom\experiments\run-v11-postgres-check.ps1`
   通过，临时 PostgreSQL、迁移、seed 和闭环校验均正常。
7. `npx.cmd playwright test tests/v15-smart-followup-assistant-e2e.spec.ts --workers=1 --reporter=list`
   通过，3/3 通过。

额外说明：

1. 首次执行 `npm run prisma:generate` 时因为 3000 端口上的 dev server 占用了 Prisma 引擎文件而失败。
2. 关闭本地 Node dev 进程后重新执行，`prisma generate` 恢复通过。
3. 首次 Playwright 失败不是业务缺陷，而是两个环境/测试问题：
   - 本地 `.env` 指向临时 PostgreSQL 端口，单独运行时数据库未常驻；
   - 第一版断言使用了会命中多张建议卡的宽泛文本定位。
4. 处理方式是：
   - 在同一个 PowerShell 会话中临时拉起 PostgreSQL、执行迁移、seed 并手动启动 dev server；
   - 把保存跟进后的断言改成“跟进记录数量加一”；
   - 把销售用例切换到明确由 `sales` 负责的样板客户 `demo-lead-002`。

## 14. 本轮结论

本轮最重要的结论是：

在现有策略库、资料包、任务和审计体系不变的情况下，完全可以先用规则模板把“销售辅助型智能回复建议”做成可演示、可审计、可复制、可保存的基础版。

被证实的判断：

1. 规则模板足以支撑 V1.5 第一版。
2. 现有 `requireLeadAccess` 足以承接建议生成权限。
3. `ReplySuggestion` 用轻量模型即可完成落库和批次读取。

## 15. 下一轮建议

1. 先完成本轮剩余 lint、build、数据库脚本和 Playwright 验证，确认 V1.5 基线稳定。
2. 如果后续要增强自然度，可以考虑在规则模板之上追加可选模型生成，但必须保留规则兜底。
3. 如果销售真实使用后反馈“建议生成后还要手工整理任务”，下一轮可以考虑加入“根据选中建议快速创建下一步任务”的轻量联动，而不是直接做自动发送。
