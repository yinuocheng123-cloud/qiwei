# 版本记录：v1.4.6-shareable-demo-link

## 1. 本轮目标

本轮要解决的问题不是新增业务功能，而是把当前本地演示环境进一步收口成“给一个链接就能测”的状态。  
约束保持不变：

- 不开发新功能；
- 不修改业务逻辑；
- 不改数据库结构；
- 不接企业微信 API；
- 不动权限体系；
- 不破坏现有测试基线。

## 2. 背景与上下文

本轮承接以下记录与文件：

- `AGENTS.md`
- `custom/notes/v1.4.5-local-demo-runbook.md`
- `README.md`
- `package.json`
- `.env.example`
- `src/lib/auth.ts`
- `src/lib/auth-actions.ts`

与当前任务最相关的历史结论有三点：

1. 项目已经具备本地演示所需的 seed 数据和账号，但启动前仍依赖 `.env`、PostgreSQL、migrate 和 seed。
2. V1.4.5 已把本地运行前置条件整理成手册，但还没有把“直接给别人链接测试”这一步做成可执行入口。
3. 当前 `package.json` 只有 `next dev`，默认更偏本机调试，没有明确提供局域网可访问的启动方式，也没有公网测试链接方案。

## 3. 问题分析

当前“发链接测试”之所以不顺手，核心不是页面逻辑，而是启动方式不对：

1. 默认 `npm run dev` 更适合自己机器本地调试，不适合作为明确的分享入口。
2. 即使应用本身能跑，用户也不容易快速拿到一个可直接发出去的测试地址。
3. 如果机器上没有公网 tunnel 工具，仓库里也缺少一层明确提示，导致使用者不知道现在能否发局域网链接、能否发公网链接。

## 4. 候选方案比较

### 方案一：只修改 README，不改脚本

优点：

- 改动最少；
- 没有新增可执行脚本。

缺点：

- 仍然需要人工记忆 `next dev -H 0.0.0.0`；
- 仍然要手动判断局域网地址；
- 仍然缺少“公网 tunnel 是否可用”的自动提示。

放弃原因：

只能改善说明，不能真正把“给链接测试”变成一条固定动作。

### 方案二：补充可分享启动脚本和 npm 入口

优点：

- 一条命令就能启动局域网可访问的 dev server；
- 能自动打印可直接分享的局域网测试链接；
- 机器装了 `cloudflared` 时，还能顺手给出公网测试链接；
- 不改业务逻辑，只改启动工具层。

缺点：

- 增加了一个 PowerShell 辅助脚本；
- 依然不能绕开 `.env` 和数据库前置条件；
- 如果机器没装 `cloudflared`，公网链接仍然不可用。

最终选择原因：

这是当前最小、最稳、最符合“直接发链接测试”目标的方案。

## 5. 最终决策

本轮采用“局域网分享启动 + 可选 cloudflared 公网 tunnel”的方案：

1. 在 `package.json` 中增加 `dev:lan`、`start:lan` 和 `demo:link`；
2. 新增 `custom/experiments/start-demo-link.ps1`；
3. 在 README 中补充“直接给链接测试”的使用说明；
4. 更新 `AGENTS.md` 最新一期路径到本记录。

## 6. 具体实现

本轮具体改动如下：

- `package.json`
  增加：
  - `dev:lan`：以 `0.0.0.0:3000` 启动开发服务器；
  - `start:lan`：以 `0.0.0.0:3000` 启动生产模式服务；
  - `demo:link`：执行一键分享链接脚本。

- `custom/experiments/start-demo-link.ps1`
  实现：
  - 检查 `.env` 是否存在；
  - 检查 `DATABASE_URL` 和 `SESSION_SECRET` 是否为空；
  - 检查 3000 端口是否已被占用；
  - 自动打印 `127.0.0.1` 和局域网 IPv4 登录链接；
  - 启动 `npm run dev:lan`；
  - 若检测到 `cloudflared`，自动尝试生成 `trycloudflare.com` 公网测试链接。

- `README.md`
  增加最短使用入口，说明如何执行 `npm run demo:link`。

- `AGENTS.md`
  更新最新一期路径。

## 7. 本轮优点

1. 不改业务代码就把“给链接测试”变成了一条固定命令。
2. 局域网分享现在有明确支持，不再依赖人工记忆参数。
3. 公网 tunnel 变成“有工具就自动给链接，没有工具就明确提示”，使用路径更清楚。
4. 对现有登录、RBAC、多租户、任务和 seed 基线没有影响。

## 8. 本轮缺点与代价

1. 这仍然不是部署方案，只是本地分享测试方案。
2. `.env`、数据库、migrate 和 seed 仍然是前置条件，脚本只是把失败原因提前暴露出来。
3. 如果机器没装 `cloudflared`，当前仍只能直接分享局域网链接。
4. 脚本会启动后台 dev server 和可选 tunnel，使用者仍需要在测试结束后手动关闭对应进程。

## 9. 验证与结果

本轮计划执行以下验证：

- `powershell.exe -ExecutionPolicy Bypass -File custom\experiments\start-demo-link.ps1 -DryRun`
- `npm run prisma:generate`
- `npx tsc --noEmit`
- `npm run lint`
- `npm run build`

其中 `DryRun` 用来验证脚本结构和提示逻辑，不真正启动后台服务，避免因为当前机器未准备 `.env` 和数据库而把验证混成环境问题。

## 10. 本轮结论

当前项目已经从“只能自己本机调试”推进到“具备明确的分享测试入口”。  
后续默认应继承的结论是：

1. 如果只在自己电脑看，用 `npm run dev` 即可；
2. 如果要把链接发给同局域网的人测试，用 `npm run demo:link`；
3. 如果还要发公网链接，机器上要先准备 `cloudflared`；
4. 无论哪种方式，`.env` 和数据库前置条件都不能跳过。

## 11. 下一轮建议

1. 如果你确定后续经常要给公网链接，可以单独补一份 `cloudflared` 安装说明或一键安装脚本。
2. 如果要进一步降低操作门槛，可以再补一个停止脚本，用来清理 dev server 和 tunnel 进程。
3. 如果未来进入真正对外联调阶段，应考虑独立测试环境，而不是长期依赖本机 tunnel。
