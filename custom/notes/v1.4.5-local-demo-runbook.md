# 版本记录：v1.4.5-local-demo-runbook

## 1. 本轮目标

本轮不开发新功能，不修改业务逻辑，不接企业微信 API，不改数据库结构，只补齐一份可直接复用的本地演示环境启动手册。  
这份手册用于统一后续演示、测试和开发前的准备动作，解决当前项目依赖 `.env`、PostgreSQL 和 seed 前置条件，导致“代码在仓库里，但本地打不开”的启动落差。

## 2. 背景与上下文

本轮承接以下资料：

- `AGENTS.md`
- `README.md`
- `custom/notes/v1.4.4-local-full-test.md`
- `custom/experiments/run-v11-postgres-check.ps1`
- `.env.example`
- `package.json`
- `prisma/seed.ts`

与当前任务最相关的历史结论如下：

1. 项目运行并不是“只执行 `npm run dev` 即可”，还依赖有效的 `.env`、可连接的 PostgreSQL、Prisma 迁移和 seed 数据。
2. `zhengmu-demo` 样板企业、四类客户路径、销售任务和演示账号都已经在 `prisma/seed.ts` 中准备好，但前提是数据库初始化成功。
3. `custom/experiments/run-v11-postgres-check.ps1` 适合做一次性数据库闭环验证，但它使用的是临时 PostgreSQL 验证环境，不等同于长期驻留的本地开发数据库。
4. `custom/notes/v1.4.4-local-full-test.md` 已完成完整测试记录，后续测试和演示建议继续沿用“单 spec、单独 reset database、单独 seed、`workers=1`”的思路，不要跨版本并行混跑。

## 3. 问题分析

当前阻塞本地演示和联调的核心问题，不是功能缺失，而是启动条件没有被整理成统一步骤：

1. 新接手的人容易直接执行 `npm run dev`，但忽略 `.env` 和数据库前置条件。
2. 看到验证脚本能跑通后，容易误以为 dev server 也能长期依赖这套临时 PostgreSQL 环境。
3. 演示路径、演示账号和启动前检查点分散在 README、测试记录和 seed 文件里，不利于销售、测试和开发快速复用。

## 4. 候选方案比较

### 方案一：只在 README 里追加一段启动说明

优点：

- 改动最少；
- 入口明显。

缺点：

- README 已经承担项目说明、功能清单和测试说明，继续堆叠会越来越长；
- 无法完整承载演示账号、演示路径、排障清单和测试建议；
- 后续版本演进时不便保留阶段性结论。

放弃原因：

无法满足“统一演示、测试、开发启动手册”的目标。

### 方案二：新增独立 runbook，并在 README 留一个简短入口

优点：

- 信息结构清晰，适合直接给测试、销售或演示同事使用；
- 可以完整记录环境前置条件、演示路径、排障办法和风险提醒；
- 保持 README 简洁，同时符合仓库要求的正式记录沉淀方式。

缺点：

- 需要额外维护一份文档；
- 入口分成 README 与 `custom/notes/` 两处。

最终选择原因：

这是当前最稳妥的最小改动方案，既不影响业务代码，又能补齐可复用的本地演示启动基线。

## 5. 最终决策

本轮采用“独立 runbook + README 入口 + AGENTS 最新路径更新”的方案：

1. 新增 `custom/notes/v1.4.5-local-demo-runbook.md` 作为正式手册；
2. 在 `README.md` 增加一个简短入口，避免重复粘贴全文；
3. 更新 `AGENTS.md` 的“最新一期路径”，便于后续任务先读到这份手册。

## 6. 具体实现

本轮文件改动如下：

- `custom/notes/v1.4.5-local-demo-runbook.md`：新增本地演示环境启动手册。
- `AGENTS.md`：把最新一期路径更新到本文件。
- `README.md`：补一个 runbook 入口。

## 7. 本轮优点

1. 把 `.env`、PostgreSQL、Prisma、seed、演示路径、测试建议和排障方法收敛到一处。
2. 后续无论是本地演示、销售试讲、Playwright 验证还是开发联调，都能按同一套步骤启动。
3. 没有修改业务代码、数据库结构和测试逻辑，风险很低。

## 8. 本轮缺点与代价

1. 这仍然是一份本地手册，不是生产部署文档。
2. 文档只能降低“不会启动”的概率，不能替代真实环境检查。
3. 如果后续 `.env.example`、seed 账号或脚本命令发生变化，这份手册也需要同步维护。

## 9. 验证与结果

本轮新增的是说明文档，但仍执行以下基础验证命令：

- `npm run prisma:generate`
- `npx tsc --noEmit`
- `npm run lint`
- `npm run build`

验证结果见本文件第 12 节与本轮最终输出。

## 10. 本轮结论

当前项目已经具备稳定的本地演示条件，但前提不是“代码在”，而是“环境先准备正确”。  
后续最值得默认继承的结论是：

1. 本地启动必须先检查 `.env` 与 PostgreSQL；
2. 数据展示依赖 migrate 和 seed；
3. 演示和测试都应围绕 `zhengmu-demo` 统一路径；
4. Playwright 不要跨版本并行混跑。

## 11. 下一轮建议

1. 如后续还有新的本地联调问题，可在本手册里继续补充“常见问题排查”，而不是把说明分散到聊天记录里。
2. 如果后续需要交付给非开发同事使用，可再补一版“面向销售/演示同事”的更短启动清单。
3. 若未来进入真实部署阶段，应单独新增生产部署手册，不要继续复用这份本地 runbook。

### 三、本地运行前置条件

开始前请准备以下条件：

1. Node.js：用于安装依赖、运行 Next.js、Prisma 和构建命令。
2. npm：用于执行项目脚本。
3. PostgreSQL：用于承载本地演示和开发数据库。
4. `.env`：项目运行时必需的本地环境变量文件。
5. Prisma：负责生成客户端、执行迁移和 seed。
6. 浏览器：用于访问本地页面和手动演示。
7. Windows PowerShell：本仓库已有验证脚本基于 PowerShell，Windows 环境下建议优先按 PowerShell 命令执行。

补充说明：

- 不要把任何个人机器路径写死到配置或文档里。
- 本地演示建议使用 `127.0.0.1:3000` 或 `localhost:3000`，避免不同机器的局域网地址差异带来误解。

### 四、`.env` 配置说明

建议步骤：

1. 复制 `.env.example` 为 `.env`。
2. 配置 `DATABASE_URL`。
3. 配置 `SESSION_SECRET`。如果后续项目引入了 `AUTH_SECRET`，也应按项目实际字段配置；当前以仓库现状为准。
4. `APP_URL` 建议使用 `http://127.0.0.1:3000` 或 `http://localhost:3000`。
5. `.env` 不要提交到 Git。
6. 当前本地演示不需要填写企业微信真实 `corpId`、`agentId`、`secret`、`token`、`encodingAESKey` 等配置。

当前 `.env.example` 可参考以下字段：

```env
DATABASE_URL=""
SESSION_SECRET=""
APP_URL="http://localhost:3000"
```

Windows PowerShell 复制方式：

```powershell
Copy-Item .env.example .env
```

### 五、PostgreSQL 启动说明

#### 方式一：使用本机已安装 PostgreSQL

这是日常开发和长时间演示更推荐的方式。

建议步骤：

1. 在本机 PostgreSQL 中创建一个空数据库。
2. 在 `.env` 中填写对应的 `DATABASE_URL`。
3. 生成 Prisma Client。
4. 执行数据库迁移。
5. 执行 seed，写入演示租户、账号、策略、资料包、任务模板和样板客户。

示例流程：

```bash
npm run prisma:generate
npm run prisma:migrate
npm run prisma:seed
```

#### 方式二：使用现有验证脚本

适合做一次性数据库闭环验证：

```powershell
powershell.exe -ExecutionPolicy Bypass -File custom\experiments\run-v11-postgres-check.ps1
```

说明：

1. 该脚本会启动临时 PostgreSQL 验证环境。
2. 脚本会执行迁移、seed 和验证脚本。
3. 这适合做“当前仓库能不能闭环跑通”的检查。
4. 这不等同于长期 dev server 的数据库驻留环境，正式本地开发和持续演示仍建议准备本机 PostgreSQL。

### 十一、常见问题排查

#### 1. `npm run dev` 启动失败

优先检查：

- 依赖是否已安装；
- `.env` 是否存在；
- `DATABASE_URL` 是否可用；
- 终端里是否已有更早的报错信息。

#### 2. `DATABASE_URL` 无法连接

优先检查：

- PostgreSQL 服务是否真的启动；
- 数据库名、端口、用户名、密码是否正确；
- 本地防火墙或端口占用是否导致连接失败。

#### 3. 登录失败

优先检查：

- 是否已成功 seed；
- 登录邮箱和密码是否使用了本地演示账号；
- `SESSION_SECRET` 是否配置；
- 数据库里是否已有演示账号数据。

#### 4. seed 后没有演示数据

优先检查：

- `npm run prisma:seed` 是否执行成功；
- `DATABASE_URL` 是否指向了正确数据库；
- 是否误连到了空库或旧库；
- `zhengmu-demo` 是否存在。

#### 5. 页面 500

优先检查：

- 终端里的 Next.js 报错；
- Prisma 查询是否因为数据库未初始化而失败；
- `.env` 是否缺字段；
- 是否存在迁移未执行完的情况。

#### 6. 权限跳转到 `/forbidden`

优先检查：

- 当前登录角色是否正确；
- 是否访问了不属于本租户的页面；
- 是否用租户角色误进了 `/admin`；
- 是否跨租户访问了别的 `tenantSlug`。

#### 7. Playwright strict mode 文本重复

优先检查：

- 断言是否用了过于宽泛的文本选择器；
- 页面里是否存在重复标题或重复按钮文案；
- 是否应该改成更稳定的角色、区域或精确文案定位。

说明：

这类问题通常属于测试定位不稳定，不代表业务逻辑一定有 bug。

#### 8. 3000 端口被占用

优先检查：

- 是否已有旧的 `npm run dev` 进程残留；
- 是否有别的本地服务占用了 3000；
- 先清理旧进程，再重新启动 dev server。

#### 9. PostgreSQL 进程残留

优先检查：

- 是否有旧测试脚本启动的 PostgreSQL 还未退出；
- 是否有临时验证环境占着端口；
- 清理后再重新执行 migrate、seed 和 dev server。

#### 10. Windows PowerShell 脚本执行策略问题

如出现脚本执行被拦截，可按当前项目已有方式显式带上执行策略：

```powershell

```
