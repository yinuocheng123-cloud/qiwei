# 版本记录：v1.2-sales-todo-strategy-materials

## 1. 本轮目标

本轮目标是在 V1.1.1 已完成真实登录、RBAC、多租户隔离、middleware 路径拦截、AuditLog 和浏览器端 E2E 的基础上，进入“业务可用增强版”。

本轮优先解决销售、运营、企业管理员日常使用中的闭环问题：客户分配、销售待办、今日待跟进、超时未跟进、高意向提醒、客户详情推荐资料和话术、资料包绑定、销售跟进概览、审计日志查询，以及对应的浏览器端 E2E 回归。

本轮仍然明确不做企业微信 API 真实接入、不做智能客服、不做复杂 AI 推荐、不做财务、人事、行政、审批、OA，也不做大规模页面重构。

## 2. 背景与上下文

本轮承接 `custom/notes/v1.1.1-security-middleware-audit-e2e.md`。上一轮已经把后台安全边界推进到 middleware，并保留页面和 Server Actions 的数据库权限校验作为最终防线，同时新增了 AuditLog 基础写入和 V1.1.1 Playwright 测试。

V1.1.1 的主要不足是：系统已经安全可登录，但销售每天该看什么、企业管理员如何分配客户、运营如何维护资料包并服务客户类型策略、老板如何看销售跟进概览，还没有形成足够日常可用的业务工作台。

本轮继续沿用 V1.1.1 的会话模型、RBAC 工具函数、`tenantId` 隔离、`ownerId` 销售隔离和 AuditLog 写入方式，不替换认证架构，不移除 middleware，不改变产品定位。

## 3. 问题分析

表面问题是页面功能不足：客户列表只能看，客户详情只有基础策略展示，资料包只能新增，销售没有待办入口，审计日志没有查询页。

核心矛盾是 V1.0/V1.1 的系统更像“安全的数据底座”，还没有把“客户该由谁跟、今天该跟谁、该发什么资料、跟进后老板怎么看”这些业务动作串起来。

主要瓶颈有三类：

- 客户归属没有可操作入口，销售隔离虽然存在，但管理员无法方便地把线索分配给销售。
- 客户类型策略库已有，但没有和资料包、详情页跟进动作形成足够明确的使用闭环。
- AuditLog 已写入，但缺少租户内查询页面，无法用来验证关键业务动作是否被记录。

次要问题是页面仍然保持轻量表格和卡片，暂时没有复杂交互组件；这符合 V1.2 的“业务可用增强”目标，不需要引入新 UI 框架或大规模重构。

## 4. 候选方案比较

### 方案 A：继续基于现有 Server Components 和 Server Actions 增量增强

核心思路是在现有页面和 `src/lib/actions.ts` 上增加分配、资料编辑、策略审计、待办查询和审计日志查询。

优点：改动最小，完全复用 V1.1.1 的权限边界；服务端查询天然可继续使用 `tenantId` 和 `ownerId` 过滤；不引入新的状态管理或 API 层。

缺点：页面交互以表单提交和刷新为主，体验不如客户端交互细腻；待办规则集中在服务端工具函数里，后续若做提醒队列可能需要抽成更正式的服务层。

最终选择该方案，因为本轮目标是业务闭环和权限稳定，不是复杂前端体验。

### 方案 B：新增 REST/API 层和客户端组件实现更强交互

核心思路是为分配、待办、资料编辑、审计日志筛选新增 API routes，页面改成客户端组件。

优点：交互体验更好，局部刷新更容易，后续可做批量操作。

缺点：本轮会扩大权限校验面，API routes 需要重复 RBAC 和 tenantId 校验；也会带来较多页面重构，违背“不做大规模页面重构”的要求。

最终放弃该方案，留到未来批量分配、销售工作台实时交互时再考虑。

## 5. 最终决策

最终采用“现有架构增量增强”的方案：

- 客户分配放在客户详情页，由 `assignLeadOwner` Server Action 处理。
- 待办规则集中在 `src/lib/dashboard.ts` 的 `todoWhere` 中，dashboard 和 todos 页面复用。
- 客户详情页继续用 `requireLeadAccess`，销售只能进入自己负责的客户详情。
- 资料包继续使用 `Material.customerType` 绑定客户类型，新增 `updateMaterial` 支持编辑。
- 策略库页面按角色切换编辑/只读状态，销售只读。
- 审计日志查询页使用 `AuditLog` 现有模型，不新增复杂审计后台。
- E2E 新增 V1.2 专项测试，不替换 V1.1.1 测试。

## 7. 本轮优点

本轮把“客户类型策略库”从静态内容推进到实际销售动作：销售能在详情页看到推荐资料、推荐话术和下一步动作，并能在跟进记录中沿用推荐动作。

客户分配、待办、销售概览和审计日志查询让企业管理员能看到销售跟进状态，运营也能维护策略和资料包。相比 V1.1.1，系统从“安全可登录”推进到“日常可用”。

权限边界继续保持清晰：管理员和运营看本租户全量，销售只看自己负责的客户；所有关键查询仍基于 `tenantId`，销售详情仍基于 `ownerId` 拦截。

审计日志从只写入变成可查询，能验证客户分配、跟进、资料编辑等关键动作是否被记录。

## 8. 本轮缺点与代价

页面仍然以服务端表单提交为主，体验比较朴素，没有做批量分配、拖拽待办、实时提醒或 toast 反馈。

待办规则目前是查询级规则，不是独立任务表；如果后续要做消息提醒、企业微信应用消息或定时提醒，需要新增任务/提醒模型，不能直接把当前页面查询当成长期提醒系统。

审计日志查询页只做了租户内列表和基础筛选，没有做平台总后台审计日志中心，也没有做导出、详情展开或敏感操作风险等级。

资料包绑定仍然是一个资料包绑定一个客户类型；如果未来要支持多客户类型复用，需要调整模型为多对多关系。

## 10. 本轮结论

V1.2 的核心结论是：在不接入企业微信 API、不引入复杂 AI 的前提下，系统已经可以围绕“客户从哪里来、属于哪类、谁负责、今天该跟谁、该发什么资料、老板怎么看”形成基础日常闭环。

V1.1.1 的权限和审计基础可以继续继承，本轮没有推翻认证、RBAC、middleware 或多租户隔离方案。

## 11. 下一轮建议

1. 优先做销售待办的批量处理和提醒任务模型，为企业微信应用消息提醒预留更稳的调度边界。
2. 增加审计日志平台总后台视图和高风险操作筛选，便于平台方排查跨租户、导出、停用等敏感动作。
3. 如果要进入 V1.3，可考虑客户分配规则、销售跟进 SLA、运营内容计划，但仍建议暂缓企业微信 API 深度接入，先把业务工作台打磨稳定。
