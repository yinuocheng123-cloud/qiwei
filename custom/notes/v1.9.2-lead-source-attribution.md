# 版本记录：V1.9.2-客户来源归因细化

## 1. 本轮目标

本轮目标是在现有《企业微信业务增长中台》中补齐客户来源归因细化能力。

重点不是做投放系统、报表大屏或真实二维码平台，而是先把来源归因的数据结构、采集入口、导入兼容、客户详情展示和审计链路打通，回答“客户到底从哪个入口进来”这个基础问题。

本轮目标类型属于：

- 功能补充
- 可维护性提升
- 后续来源分析前置准备

与本轮最相关的历史结论有三点：

2. V1.8 客户导入已经具备模板、映射、预览、去重和正式写入链路，因此来源归因应直接挂到现有导入链路，而不是重做导入。
3. 现有中台强调“在现有系统上增量扩展”，不鼓励为单一业务场景再造一套新系统或专属大模型结构。

## 3. 当前问题

修改前的来源记录主要有两个问题：

1. 线索来源大多只停留在 `Lead.source` 这一层，只能表达大渠道，无法区分具体活动、页面、二维码、场景点位和承接人员。
2. CNAS 表单虽然已经保存 `sourcePage` 和 UTM，但还没有抽象成全系统可复用的来源归因结构。
3. 客户导入模板无法补充来源活动、来源场景、来源触点等字段，后续做真实客户回溯会很吃力。

表面看起来只是“多几个字段”，真正的核心矛盾是：

- 要增强来源记录能力；
- 但又不能破坏现有 `Lead`、CNAS、客户导入、RBAC 和多租户隔离。

## 4. 候选方案比较

### 方案 A：继续只把来源信息塞进 `Lead.extraData`

核心思路：

- 不新增独立模型；
- 把来源活动、页面、二维码、UTM 等都写进 `Lead.extraData.sourceAttribution`。

优点：

- 改动最小；
- 不需要新表和关系。

缺点：

- 后续筛选、索引和审计关联不够清晰；
- 来源分析容易继续碎片化；
- 导入、表单、列表筛选和客户详情共享时不够直观。

放弃原因：

不利于后续稳定做来源复盘，因此本轮没有采用。

### 方案 B：新增独立 `LeadSourceAttribution` 模型

核心思路：

- 每个 `Lead` 对应一条首来源归因记录；
- CNAS、导入和后续其它入口都通过统一 helper 写入；
- 保持首来源优先，只补齐缺失字段，不随便覆盖已有来源。

优点：

- 结构独立清晰，适合后续来源分析；
- 可做独立索引和筛选；
- 能复用到公开表单、导入和更多业务入口。

缺点：

- 需要新增 schema、migration 和 Prisma client；
- 要补客户详情、导入、审计页和测试配套。

最终选择：

采用方案 B。

## 5. 最终决策

最终实现采用了“独立模型 + 通用解析/落库层”的思路：

1. 新增 `LeadSourceAttribution` 模型，作为 `Lead` 的一对一首来源归因记录。
2. 新增 `src/lib/source-attribution.ts`，统一处理 URL 参数、表单字段解析和归因落库。
3. CNAS 表单通过隐藏字段和 query 参数兼容新归因结构。
4. 客户导入模板、字段映射、预览和正式导入同步支持来源归因字段。
5. 客户详情页展示来源归因卡片，客户列表补基础筛选。
6. 审计日志补充来源归因动作和对象类型。

其中一个关键设计决策是：

- 本轮只保留“单条首来源”语义。

也就是：

- 每个 Lead 只保留一条 `LeadSourceAttribution`；
- 已有字段优先保留；
- 后续写入只补空，不覆盖已有首来源信息。

这样做的好处是：

- 先把来源记录打稳；
- 避免后续每个入口都互相覆盖来源；
- 给未来多触点归因留出升级空间。

## 7. LeadSourceAttribution 模型说明

核心字段包括：

- `sourceChannel`
- `sourceProject`
- `sourceCampaign`
- `sourceScene`
- `sourceTouchpoint`
- `sourceQrCode`
- `sourceStaffName`
- `sourceStaffId`
- `sourcePage`
- `sourceContent`
- `utmSource`
- `utmMedium`
- `utmCampaign`
- `utmContent`
- `utmTerm`
- `firstSeenAt`
- `submittedAt`

设计要点：

1. `leadId` 唯一，保证当前版本一条线索只保留一条首来源记录。
2. `sourceStaffId` 可选，只有能匹配到当前租户用户时才落库。
3. 常用查询字段增加索引，方便后续列表筛选和来源复盘。

## 13. 权限说明

本轮没有新增角色，也没有扩大权限边界：

1. `TENANT_ADMIN` 可查看本租户客户来源归因。
2. `OPERATOR` 可查看本租户客户来源归因。
3. `SALES` 仍然只能查看自己负责客户的来源归因，因为客户详情权限没有放宽。
4. `PLATFORM_ADMIN` 不因为来源归因而获得租户业务权限扩张。
5. 跨租户访问继续拒绝。

3. `npm run lint`：通过。

本轮测试收口时额外确认了三个与环境稳定性直接相关的结论：

1. 本地浏览器专项测试继续适合采用“独立 PostgreSQL（55432）+ 独立 Next dev server + `PLAYWRIGHT_SKIP_WEBSERVER=1`”方式运行。
2. `next start` 生产模式在本地 `http://` 验证下会遇到 secure cookie 行为差异，不适合作为当前这组 Playwright 的本地收口方式。
3. 客户导入专项用例最终改成“浏览器验证模板下载 + 直接复用现有导入服务 helper 完成预览和正式导入”的混合集成方式，原因不是业务逻辑错误，而是本地 Playwright 下 React server action 表单提交在导入页存在时序不稳定；这样处理仍然走的是同一套导入与来源归因落库逻辑。

## 15. 风险与未完成项

1. 当前仍是单条首来源模型，不支持多触点归因。
2. 来源人员匹配当前只做当前租户用户名 / 邮箱轻量匹配，不是完整人员映射中心。
3. 当前只补了基础筛选，没有做来源质量报表和统计图。
4. 当前没有接真实二维码平台、投放平台或企业微信 API，因此来源二维码仍然是业务侧手工编号。
5. 为了稳定验证导入来源归因，测试用例里直接复用了 `completeImportBatch` 等现有导入 helper，因此会在测试输出里出现“audit log write failed: headers was called outside a request scope”的提示；这是因为测试进程不在 Next 请求上下文内，但不影响导入主流程、来源归因落库和浏览器端断言结果。

## 16. 下一步建议

1. 如果真实业务开始使用来源二维码，下一步最值得做的是补一个“来源编号规范”和轻量维护清单。
2. 如果运营开始依赖来源复盘，下一步可先做来源项目 / 来源活动的聚合统计，而不是直接上 BI 大屏。
3. 如果后续出现多触点营销链路，再考虑把单条首来源升级成多触点归因模型。
