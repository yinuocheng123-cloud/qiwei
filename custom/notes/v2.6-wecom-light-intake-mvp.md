# 版本记录：v2.6-wecom-light-intake-mvp

## 1. 本轮目标

本轮目标是规划 V2.6-V2.8 三阶段，并优先完成 V2.6 企业微信轻承接 MVP。V2.6 要让 CNAS 客户可以从企业微信手工/模拟承接到 MarketClaw，进入销售可跟进、可记录、可发资料、可设下一步动作的主流程。

目标类型：功能补充、边界收口、试点流程打通。

## 2. 背景与上下文

本轮承接 `custom/notes/v2.5-marketclaw-platform-boundary.md`。V2.5 已明确 MarketClaw 是平台底座，CNAS 是试点模板。历史上 V2.1.3 已有 `WeComConfig`、`UserWecomBinding`、`WecomNotificationLog` 和 `/wecom` 内部提醒配置页，V1.9.2 已有 `LeadSourceAttribution` 来源归因模型。

因此 V2.6 不需要新增聊天、会话、Agent 或深度 API 模型，应该复用现有租户、成员、来源、客户、任务和 CNAS 模板能力。

## 3. 问题分析

当前缺口不是“没有企微全量集成”，而是“企微客户如何先安全进入销售跟进流程”。如果一步到位做聊天同步、自动回复或会话存档，会立刻引入合规、权限、数据范围、客户告知和 AI 边界风险。

更稳妥的路径是先做轻承接：由管理员或运营在系统里手工/模拟录入企微客户，绑定承接成员，写入来源归因，并把 CNAS 模板客户转成可跟进任务。

## 4. 候选方案比较

方案 A：直接做企微全量 API 集成。

优点是自动化程度高；缺点是范围过大，包含聊天同步、客户资料授权、会话存档、自动动作和合规告知等复杂问题。本轮明确禁止。

方案 B：完全复用 CSV 导入。

优点是已有导入能力；缺点是无法体现成员绑定、企微承接配置和单客户测试路径，也不利于 CNAS 试点快速验证。本轮放弃作为唯一方案。

方案 C：新增企微轻承接测试台。

优点是改动小，复用现有模型，能完成配置、成员绑定、来源记录、手工/模拟导入和 CNAS 跟进任务；缺点是还不是自动化 API 接入，需要人工录入或模拟。本轮选择。

## 5. 最终决策

采用方案 C。V2.6 只做轻承接 MVP，不做聊天同步、不做自动回复、不做 AI Agent、不做会话存档、不做深度企微 API。

V2.6-V2.8 规划：

- V2.6：轻承接 MVP，手工/模拟客户进入 MarketClaw。
- V2.7：轻量承接治理，补异常、批次和复盘，不碰聊天。
- V2.8：在合规确认后评估极小范围基础资料 API，仍不做自动回复和会话存档。

## 6. 具体实现

- `src/lib/wecom-light-intake.ts`：新增企业微信轻承接服务端动作，负责手工/模拟导入客户、写入来源归因、打标签、创建任务和审计日志。
- `src/app/app/[tenantSlug]/wecom/light-intake/page.tsx`：新增企业微信轻承接测试台，展示配置状态、成员绑定、三阶段规划、模拟导入表单和最近承接客户。
- `src/components/Shell.tsx`：在管理员/运营的设置更多入口增加“企微轻承接”。
- `custom/demo/wecom-light-intake-roadmap.md`：沉淀 V2.6-V2.8 三阶段规划。
- `AGENTS.md`：更新最新一期路径和 V2.6 边界。

## 7. 本轮优点

本轮没有破坏平台化边界：客户仍进入 `Lead`，来源仍进入 `LeadSourceAttribution`，跟进仍进入 `FollowTask`，CNAS 仍作为模板语境存在。管理员和运营可以验证企微轻承接，销售仍只面对客户详情、资料、跟进和任务。

## 8. 本轮缺点与代价

当前仍是手工/模拟导入，不会自动从企业微信拉取客户。企微外部联系人 ID 只作为模拟标识记录，不具备真实 API 校验。V2.6 也没有批次治理、异常汇总和重复处理专页，这些应留到 V2.7。

## 9. 验证与结果

已完成验证：

- `npm.cmd run typecheck`：通过。
- `npm.cmd run lint`：通过。
- `npm.cmd run build`：通过。
- `npx.cmd playwright test tests/v26-wecom-light-intake-smoke-e2e.spec.ts --workers=1 --reporter=list`：2 个用例通过，覆盖管理员模拟导入 CNAS 企微客户、写入来源归因、生成 CNAS 跟进任务，以及销售不可访问轻承接测试台。
- `npx.cmd playwright test tests/v22-pilot-workbench-smoke-e2e.spec.ts --workers=1 --reporter=list`：2 个用例通过，确认销售主路径与后台入口边界未被破坏。
- `npx.cmd playwright test tests/v221-hide-ai-complexity-smoke-e2e.spec.ts --workers=1 --reporter=list`：3 个用例通过，确认复杂 AI 治理入口仍对销售隐藏。
- `npx.cmd playwright test tests/v224-stability-smoke-e2e.spec.ts --workers=1 --reporter=list`：3 个用例通过，确认工作台、客户详情和设置页稳定。
- `npx.cmd playwright test tests/v227-materials-checklist-smoke-e2e.spec.ts --workers=1 --reporter=list`：3 个用例通过，确认资料清单主路径未受影响。

验证过程中曾遇到两类非业务失败：一是测试断言对“来源归因”“企业微信轻承接”和 CNAS 跟进关键词匹配过宽，命中页面多个区域；二是在 dev 服务运行时执行 `next build` 会覆盖 `.next`，导致后续 Playwright 登录页短暂 500。前者已通过收紧测试定位修复，后者通过 `scripts/stop-local.ps1` 与 `scripts/start-local.ps1` 清理重启后复跑通过。

## 10. 本轮结论

企业微信承接的第一步应该是“轻承接”，而不是全量集成。只要 CNAS 客户能稳定进入 MarketClaw 的客户、来源、任务和跟进链路，就已经满足 V2.6 的试点目标。

## 11. 下一轮建议

1. V2.7 优先补轻承接记录复盘、重复客户提示和未绑定成员提示。
2. V2.8 前必须先确认企业微信 API 权限、客户告知和合规范围。
3. 在任何阶段都不要让 AI 自动回复客户或替销售做最终动作。
