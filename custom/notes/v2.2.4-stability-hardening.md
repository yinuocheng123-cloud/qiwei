# 版本记录：v2.2.4-stability-hardening

## 1. 本轮目标

本轮进入 V2.2.4「稳定性收口」，目标不是新增业务功能，而是让试点工作台在局部数据读取异常时仍能保持可用。

本轮重点处理 dashboard、客户详情页 AI 推荐回复区域、后台治理页的统计和列表查询容错，避免某个 count、findMany、复盘数据或 AI 推荐辅助数据失败时拖垮整页。

## 2. 背景与上下文

本轮承接 V2.2.1「隐藏复杂度与 AI 后台化」和 V2.2.3「Docker Desktop E2E 恢复」。V2.2.1 已经明确销售只看工作，AI 治理进入后台；V2.2.3 已经让本机 PostgreSQL fallback 跑通 Prisma、Seed、build 和 V2.2 / V2.2.1 smoke。

测试过程中曾出现 dashboard 查询 Prisma 连接失败日志，虽然后续 smoke 已通过，但说明工作台统计读取缺少 graceful fallback。

## 3. 问题分析

核心问题不是业务逻辑错误，而是页面数据读取耦合过紧。多个 Prisma 查询放在同一个 `Promise.all` 中时，任意一个查询失败都会让整页渲染失败。

对试点工作台来说，这个代价过高：销售需要先能看到客户、今日动作和手工跟进入口。某个统计数、复盘列表或 AI 推荐辅助数据暂不可用时，不应阻断销售继续工作。

## 4. 候选方案比较

方案一：全局捕获页面错误。

优点是改动少。缺点是只能显示整页错误或 fallback，无法保留工作台结构，也无法区分哪个统计失败。本轮未采用。

方案二：把所有查询串行化并逐个 try/catch。

优点是最直观。缺点是会降低页面加载效率，也让页面代码更长。本轮未采用。

方案三：保留并发读取，但每个统计或列表用安全读取函数包裹。

优点是保留并发性能，同时让单个查询失败只回退该查询的数据。数字回退为 0，列表回退为 []，页面显示业务化提示。本轮采用。

## 5. 最终决策

本轮采用「局部安全读取 + 业务化兜底提示」方案：

- dashboard 统计和列表独立 fallback。
- 客户详情页 AI 推荐辅助数据独立 fallback。
- 后台治理页统计、训练、回复记录和复盘读取独立 fallback。
- 不改变权限边界，不恢复销售后台入口。
- 不暴露 Prisma、Provider、Prompt、向量等技术词。

## 7. 本轮优点

dashboard 不再因为单个统计查询失败而整页崩溃。销售仍能进入工作台、客户列表、客户详情和 AI 推荐回复区域。

AI 推荐回复区域即使辅助数据不可用，也会用业务化文案提示销售先手工记录跟进。

后台治理页仍然可访问，但复盘、训练和记录数据失败时不会暴露技术错误。

## 8. 本轮缺点与代价

本轮没有新增统一的错误观测或日志聚合，只在页面层做了局部容错。这样可以快速稳定试点体验，但后续如果要排查长期异常，还需要补充服务端日志或监控。

部分 fallback 会把失败数据展示为 0 或空列表，适合试点期保证页面可用，但不适合作为长期数据质量判断依据。

V2.2.4 smoke 首次失败点是测试选择器过宽：`今日待跟进客户` 同时命中统计卡和模块标题。已将断言收窄到 heading 后通过。

## 10. 本轮结论

V2.2.4 的核心结论是：试点工作台应该优先保证销售主流程可用，统计和后台治理数据可以局部降级。稳定性收口不等于隐藏真实问题，而是避免局部数据异常把销售工作入口一起带崩。

## 11. 下一轮建议

1. 继续观察 dashboard 和客户详情页是否还有未包裹的辅助查询。
2. 若试点客户开始真实使用，可补充轻量服务端错误日志，区分数据库、权限、数据缺失和页面断言问题。
3. Docker Desktop / WSL2 仍建议后续单独修复，但当前本机 PostgreSQL fallback 可作为稳定测试路径。
