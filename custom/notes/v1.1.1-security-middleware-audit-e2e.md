# 版本记录：v1.1.1-security-middleware-audit-e2e

## 1. 本轮目标

本轮目标是在 V1.1 已完成真实登录、RBAC、多租户隔离和 PostgreSQL 验证的基础上，补强后台路径安全拦截、审计日志基础模型和浏览器端 E2E 自动化测试。

本轮目标类型：安全边界补强、可测试性提升、可维护性提升。

本轮明确不做企业微信 API 真实接入、不做智能客服、不做复杂页面美化、不做 V1.2 的客户分配和销售待办，也不做财务、人事、行政、审批、OA 等无关模块。

## 2. 背景与上下文

本轮开始前尝试执行 `git pull --ff-only`，但当前仓库没有 remote tracking 信息，无法拉取远端。随后读取了 `AGENTS.md` 和 `custom/notes/v1.1-auth-rbac-postgres-e2e.md`。

V1.1 的关键结论是：登录、RBAC 和多租户隔离已经从开发态模拟升级为数据库 Session、httpOnly cookie 和服务端权限校验，但仍缺少 middleware 级早期拦截、审计日志和浏览器端 E2E。

本轮延续 V1.1 的数据库 Session 和 Server Actions 权限校验，不用 middleware 替代原有数据库校验。

## 3. 问题分析

V1.1 已能在页面和 Server Actions 层阻断越权，但请求会先进入页面逻辑。V1.1.1 的核心矛盾是：需要在路径层更早拦截明显的未登录和跨租户访问，同时不能在 Edge middleware 中直接依赖 Prisma。

主要约束：

- Next.js middleware 运行在 Edge 环境，不适合直接读取 Prisma。
- 现有 session cookie 是随机 token，middleware 无法仅凭 token 判断角色和租户。
- 审计日志不能影响主业务流程，写入失败不应导致登录、表单或导出失败。
- 浏览器 E2E 需要常驻 PostgreSQL 和 dev server；当前工具环境中 PostgreSQL 更适合在单次脚本内临时运行。

## 4. 候选方案比较

方案一：middleware 直接查数据库 Session。

- 优点：权限信息始终最新。
- 缺点：Edge middleware 不适合使用 Prisma，部署兼容性差。
- 风险：破坏构建或运行时稳定性。
- 结论：放弃。

方案二：登录时写入一个签名的 httpOnly 权限提示 cookie，middleware 校验签名后做路径层基础拦截。

- 优点：Edge 可运行，不需要数据库连接；能拦截未登录、非平台访问 `/admin`、跨租户访问 `/app/[tenantSlug]`。
- 缺点：cookie 中角色和租户信息在 session 生命周期内可能短暂滞后。
- 风险：必须继续保留数据库权限校验作为最终防线。
- 结论：采用。

方案三：只做页面和 Server Actions 权限，不做 middleware。

- 优点：实现最简单。
- 缺点：不满足本轮路径层拦截目标。
- 结论：放弃。

## 5. 最终决策

最终采用方案二。

关键决策：

- 新增 `growthhub_auth_context` httpOnly cookie，内容为签名后的 `userId`、`role`、`tenantSlug`、`expiresAt`。
- middleware 只匹配 `/admin/:path*` 和 `/app/:path*`。
- 未登录或签名无效时重定向 `/login?next=...`。
- 非 `PLATFORM_ADMIN` 访问 `/admin` 时重定向 `/forbidden`。
- 企业角色访问 `/app/[tenantSlug]` 时，必须满足 cookie 中 `tenantSlug` 与路径一致。
- 页面和 Server Actions 的 `requirePlatformAdmin`、`requireTenantAccess`、`requireLeadAccess` 继续保留。

## 7. middleware 拦截规则

当前 matcher：

- `/admin/:path*`
- `/app/:path*`

拦截规则：

- 未登录访问 `/admin` 和 `/app/*`：跳转 `/login?next=原路径`。
- 已登录但非 `PLATFORM_ADMIN` 访问 `/admin`：跳转 `/forbidden`。
- 企业角色访问 `/app/[tenantSlug]`：必须满足当前登录上下文中的 `tenantSlug` 等于路径中的 `tenantSlug`。
- 公开表单 `/t/[tenantSlug]/diagnosis` 和 `/t/[tenantSlug]/material` 不在 matcher 中，仍可匿名访问。
- `/login`、`/logout`、`/forbidden`、首页和静态资源不在 matcher 中，不会被误拦截。

## 11. 风险与未完成项

已知风险：

- middleware 使用签名权限提示 cookie，不直接查数据库；如果用户角色或租户绑定在 session 生命周期内被后台修改，middleware 可能短暂滞后，但页面和 Server Actions 的数据库校验仍会拦截。
- 审计日志写入采用 `safeWriteAuditLog`，失败时会记录错误但不阻断主流程。
- Playwright 浏览器端 E2E 需要常驻 PostgreSQL、已迁移数据库、seed 数据和浏览器二进制；当前工具环境不一定能完整跑通浏览器。

未完成项：

- 暂无审计日志查询页面。
- 暂无 CI 中的 Playwright 数据库准备流程。
- 暂无 middleware 级审计记录。

## 12. 下一轮建议

1. 增加审计日志查询页面，支持平台按租户、用户、动作、时间筛选。
2. 将 Playwright E2E 接入 CI，并在 CI 中启动 PostgreSQL 服务。
3. 为角色变更、租户停用、导出下载等高风险动作增加更细的审计 metadata。
