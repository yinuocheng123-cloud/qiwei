# 版本记录：v1.7.1-role-based-navigation-permissions

## 1. 本轮目标

本轮目标是在 V1.7“业务线／产品管理”基础上，对后台做一次角色化导航与权限收口。

重点不是新增业务功能，而是把不同角色在系统里看到的菜单、可访问入口和高风险页面权限收紧到更符合真实使用场景的范围。

本轮优先级属于：

- 可维护性提升
- 权限边界收口
- 演示与真实使用体验修正

## 2. 背景与上下文

本轮承接以下两期记录：

- `custom/notes/v1.6-zhengmu-platform-workbench.md`
- `custom/notes/v1.7-business-line-product-management.md`

V1.6 已经形成 `zhengmu-demo` 与 `zhengmu-platform` 双租户演示基线。
V1.7 已经形成 `BusinessLine` 模型、业务线列表页以及和智能跟进助手、智能标签建议的联动能力。

但上一轮完成后，后台仍有几个现实问题：

- 菜单虽然越来越多，但不同角色看到的入口还没有明显区分。
- 有些高风险页面只是“理论上不建议销售进入”，但仍可通过直接访问 URL 进入。
- 业务线页虽然已有销售只读模式，但运营仍然能通过状态字段绕过按钮限制进入归档。
- 企业微信配置页虽然不展示 `secret` 明文，但 `token` 与 `EncodingAESKey` 仍会回填历史值。
- demo-guide 主要按租户区分，还缺少按角色区分的说明重心。

## 3. 问题分析

表面现象是“菜单显示不够精细”，但核心矛盾并不只是导航显示，而是以下两层没有完全对齐：

- 前端菜单展示层
- 服务端页面与 action 的真实权限层

如果只隐藏菜单，不补页面级权限校验，销售或运营仍可以通过直接输入 URL 或伪造请求进入高风险路径。

本轮真正需要解决的是：

- 哪些角色该看到哪些菜单；
- 哪些角色即使知道 URL 也必须被拒绝；
- 哪些状态操作必须在按钮层和服务端层同时限制；
- 哪些敏感字段必须避免回显历史值。

## 4. 候选方案比较

### 方案 A：只做菜单隐藏

核心思路：

- 仅在导航组件里按角色隐藏入口；
- 页面本身尽量保持原样。

优点：

- 改动最少；
- 前端演示层看起来会立刻更干净。

缺点：

- 不能真正阻止直接访问 URL；
- 不能阻止通过提交表单或 server action 进行越权写入；
- 高风险入口只是“看不见”，不是“进不去”。

放弃原因：

- 不符合本轮“权限收口”的目标，只能算视觉收口，不是实际收口。

### 方案 B：菜单隐藏 + 页面级权限 + 服务端 action 双重收口

核心思路：

- 导航层按角色精简菜单；
- 高风险页面直接基于角色拒绝访问；
- 对业务线状态、企微配置等写操作再补一层服务端角色校验。

优点：

- 菜单、页面和写入行为三层一致；
- 能覆盖“知道 URL 直接访问”和“伪造提交”两类风险；
- 后续继续扩角色时更容易沿用同一套思路。

缺点：

- 需要跨多个页面、导航和 action 同步修改；
- 测试覆盖也要跟着扩展。

最终选择：

- 采用方案 B。

## 5. 最终决策

本轮采用以下权限策略：

- `PLATFORM_ADMIN` 只看平台级入口，不默认看到租户日常销售菜单。
- `TENANT_ADMIN` 看到完整租户业务管理入口。
- `OPERATOR` 看到业务资产维护入口，但隐藏审计、导出和企微敏感配置。
- `SALES` 只保留日常跟进路径，不显示全局配置和编辑入口。

关键设计决策：

1. 业务线保留销售只读访问，但只显示 `ACTIVE` 状态。
2. 业务线归档只允许 `TENANT_ADMIN`，运营不能通过按钮或状态字段绕过。
3. 租户审计日志只开放给 `TENANT_ADMIN`。
4. 租户企微配置只开放给 `TENANT_ADMIN`，且不回显敏感历史值。
5. demo-guide 保留租户差异，同时增加角色化说明，避免破坏 V1.6 两套演示路径。

## 6. 具体实现

本轮主要改动如下：

- `src/components/Shell.tsx`
  - 重写租户与平台导航，按角色输出不同菜单。

- `src/lib/auth.ts`
  - 新增租户业务线、审计日志、企微配置、导出等权限辅助函数，统一角色判断语义。

- `src/app/app/[tenantSlug]/audit-logs/page.tsx`
  - 从“管理员/运营/销售可访问”收紧为仅 `TENANT_ADMIN` 可访问；
  - 同步补充业务线相关审计动作筛选项。

- `src/app/app/[tenantSlug]/wecom/page.tsx`
  - 收紧为仅 `TENANT_ADMIN` 可访问；
  - 不再回显 `secret`、`token`、`EncodingAESKey` 历史值。

- `src/app/app/[tenantSlug]/strategies/page.tsx`
  - 收紧为仅 `TENANT_ADMIN` 与 `OPERATOR` 可访问和编辑；
  - 移除销售只读直访模式。

- `src/app/app/[tenantSlug]/business-lines/page.tsx`
  - 销售模式仅显示启用中的业务线；
  - 销售不显示新增、编辑、暂停、归档入口；
  - 运营不再显示归档按钮；
  - 编辑表单里的状态选项也同步去掉运营的 `ARCHIVED`。

- `src/lib/actions.ts`
  - `createBusinessLine`、`updateBusinessLine`、`updateBusinessLineStatus` 增加运营不可归档的服务端校验；
  - `upsertWeComConfig` 收紧为仅 `TENANT_ADMIN` 可写。

- `src/app/app/[tenantSlug]/demo-guide/page.tsx`
  - 在保留 `zhengmu-demo` / `zhengmu-platform` 内容的前提下，新增按角色显示的说明卡片；
  - 快捷入口改为按角色输出，避免平台管理员或销售看到自己进不去的路径。

- `src/app/admin/page.tsx`
  - 移除平台管理员误导性的租户后台/导出直达按钮；
  - 改为进入租户 `demo-guide` 查看演示说明。

- `README.md`
  - 新增 V1.7.1 角色化导航与权限收口说明，并修正 V1.7 中运营的业务线权限描述。

- `tests/v171-role-navigation-permissions-e2e.spec.ts`
  - 新增角色化导航与权限收口回归测试。

## 7. 本轮优点

- 菜单显示和真实权限开始对齐，不再只是“把按钮藏起来”。
- 高风险入口边界更明确，销售和运营更难误入敏感页面。
- 业务线状态收口从 UI 层延伸到服务端，降低绕过风险。
- demo-guide 更适合给不同角色讲不同重点，演示路径更贴近真实使用。

## 8. 本轮缺点与代价

- 目前仍然主要依赖页面和 action 级校验，没有抽成统一的权限矩阵配置。
- `materials`、`task-templates` 等页面虽然权限已较窄，但整体权限策略仍分散在多个页面和 action 中。
- 平台管理员对租户的访问仍是特例式 demo-guide 入口，而不是更系统的平台代理视角。
- 本轮没有新增更细粒度的审计拒绝记录，被拒绝访问本身默认不写入 AuditLog。

验证结果：

- `npx tsc --noEmit`：通过。
- `npm run lint`：通过。
- `npm run build`：通过。
- `powershell.exe -ExecutionPolicy Bypass -File custom\\experiments\\run-v11-postgres-check.ps1`：通过。
- `npx.cmd playwright test tests/v171-role-navigation-permissions-e2e.spec.ts --workers=1 --reporter=list`：6/6 通过。

Playwright 过程中本轮只修了测试定位器，没有因为真实业务 bug 改业务逻辑：

- 第一次失败：`状态` 相关 locator 过宽，触发 strict mode。
- 第二次失败：`已暂停` 文本命中多个元素，仍属于 strict mode。
- 最终处理：把断言收窄到业务线卡片内的明确控件或更稳定的角色链路结果。

最终确认通过的验收点包括：

- `TENANT_ADMIN` 能看到完整企业后台菜单。
- `OPERATOR` 能看到业务资产入口，但不能进入高风险平台/审计入口。
- `SALES` 只看到日常跟进入口，能访问自己的任务和客户详情。
- `SALES` 直接访问租户审计日志会被拒绝。
- `SALES` 直接访问业务线页时只看到 `ACTIVE` 业务线，且伪造暂停请求无效。
- `TENANT_ADMIN` 可以暂停业务线，暂停后 `SALES` 不再看到该业务线。
- `PLATFORM_ADMIN` 仍可访问平台审计日志，并在 demo-guide 中看到平台维护说明。

## 10. 本轮结论

当前最重要的结论是：

- 权限收口不能只做导航隐藏，必须同时覆盖页面访问和服务端写入。
- 业务线状态这种“看起来只有一个按钮”的能力，实际上还要补表单字段与 action 两层约束，才能避免绕过。
- demo-guide 继续按租户保留内容是必要的，但角色化说明也必须同步加上，否则同一个页面会对不同角色说错重点。
- Playwright 对这类后台页面很容易遇到 strict mode 文本重复问题，优先收窄 locator，比为了配合测试去改业务文案更稳。

## 11. 下一轮建议

1. 在功能继续扩张前，可以把当前零散的角色判断收拢为统一的角色能力表或权限矩阵。
2. 如果后续继续扩后台模块，可以优先复用本轮的“导航隐藏 + 页面拒绝 + action 拒绝”三层模式。
3. 后续若进入真实试用阶段，可考虑对被拒绝的高风险写入尝试增加更明确的安全审计记录。
