# 版本记录：v1.1-auth-rbac-postgres-e2e

## 1. 本轮目标

本轮目标是把 V1.0 的开发态身份模拟升级为真实可运行的登录、会话、RBAC 权限、多租户隔离和 PostgreSQL 端到端验证版本。

本轮目标类型：功能补充、Bug 修复、安全边界补强、可维护性提升。

本轮不做企业微信 API 真实接入，不做复杂页面美化，不做 AI 智能客服、投流、财务、人事、行政、审批或 OA 模块。

## 2. 背景与上下文

本轮开始前尝试执行 `git pull --ff-only`，但当前目录不是 Git 仓库，无法拉取远端。随后读取了 `AGENTS.md` 和 `custom/notes/v1.0-growth-hub-foundation.md`。

V1.0 的主要结论是：系统核心不是普通 CRM，而是“渠道来源 + 客户类型 + 转化策略 + 销售跟进 + 老板看板”的增长闭环。V1.0 已建立 Prisma 模型、页面路由和策略库闭环，但明确留下真实登录、RBAC、PostgreSQL 端到端验证作为下一轮优先任务。

本轮延续 V1.0 的 Server Actions、Prisma 模型和 `tenantId` 查询隔离思路，不改产品定位。

## 3. 问题分析

V1.0 的表面问题是后台页面可以直接访问；核心问题是没有真实身份边界，企业角色、销售角色和平台角色之间缺少可执行的权限隔离。

主要风险：

- 未登录用户可访问后台页面。
- 非平台管理员可能访问平台总后台。
- 销售可能看到非本人负责的线索。
- 不同租户之间若只依赖 `tenantSlug`，容易出现越权查询。
- 没有真实数据库验证时，迁移、seed 和表单写入闭环无法确认。

## 4. 候选方案比较

方案一：NextAuth/Auth.js + Credentials Provider + Prisma Adapter。

- 优点：生态成熟，后续可扩展 OAuth。
- 缺点：本轮只需要轻量账号密码登录，引入 Adapter 与表结构会扩大改动面。
- 风险：需要补充 NextAuth 约定页面、回调和 session 映射，短期成本偏高。
- 结论：本轮放弃，后续如果要接入更多身份提供方可重新评估。

方案二：自建轻量登录，使用 bcryptjs + 数据库 Session + httpOnly cookie。

- 优点：改动可控，符合当前模型，能快速落地真实登录和 RBAC。
- 缺点：没有 NextAuth 的生态能力，需要后续自行补审计、刷新策略和安全细节。
- 风险：需要明确 cookie、session 过期和生产环境 `SESSION_SECRET`。
- 结论：采用。

## 5. 最终决策

最终采用方案二。

关键决策：

- 新增 `Session` 模型，保存 `tokenHash`、`userId`、`expiresAt`。
- 登录成功后生成随机 token，仅把原始 token 写入 httpOnly cookie，数据库只保存 HMAC hash。
- `SESSION_SECRET` 用于 token hash；生产环境缺失时抛错。
- `/admin` 使用 `requirePlatformAdmin()` 保护。
- `/app/[tenantSlug]` 页面使用 `requireTenantAccess()` 保护，必须登录、角色符合、`user.tenantId === tenant.id`。
- 客户详情和跟进写入使用 `requireLeadAccess()`，销售必须满足 `lead.ownerId === user.id`。
- 公开表单继续匿名访问，但写入时仍以 `tenantSlug` 解析 `tenantId` 并只写当前租户。

## 7. 本轮优点

当前方案把 V1.0 的“能看页面”推进到“有真实身份边界”。

改进点：

- 密码不再是演示态说明，而是通过 bcrypt hash 存储和校验。
- session cookie 为 httpOnly，降低前端脚本读取风险。
- 数据库只保存 token hash，不保存原始 session token。
- `/admin` 和企业后台均有服务端权限保护。
- 销售权限落到查询条件和详情访问校验，不只依赖页面展示。
- 第二租户 seed 为后续隔离测试提供固定样本。
- PostgreSQL 迁移和 seed 在本地实验数据库中实际执行通过。

## 8. 本轮缺点与代价

当前方案仍然不是完整生产身份系统。

已知缺点：

- 没有登录失败次数限制、验证码、二次验证或设备管理。
- 没有 middleware 级早期拦截，当前主要在页面和 Server Action 层校验。
- 没有权限审计日志。
- session 没有滑动续期，默认 7 天过期。
- 实验验证脚本模拟了公开表单写入逻辑，但没有通过浏览器真实点击表单提交，因为临时 PostgreSQL 服务在当前工具环境中难以跨命令持续驻留。
- 企业微信配置页仍是占位，不做真实 API 调用。

暂时接受的妥协：

- 先使用轻量自建认证满足 V1.1 核心闭环，后续如需第三方登录再评估 Auth.js。
- 先用服务端页面和动作保护，下一轮再补 middleware 和自动化浏览器测试。

## 10. 本轮结论

本轮最重要的结论是：V1.1 已经把 V1.0 的开发态身份模拟升级为真实账号密码、httpOnly session 和 RBAC 服务端校验，多租户隔离从“约定”变成了页面查询和写入动作中的强制条件。

被证实的假设：

- 自建 bcrypt + Session + httpOnly cookie 足以支撑当前 V1.1 登录与权限闭环。
- `tenantId` + `ownerId` 双层过滤能满足企业隔离和销售隔离。
- 双租户 seed 能有效支撑隔离验证。

后续应默认继承：

- 所有后台页面必须先调用权限校验。
- 所有写入动作必须重新校验权限，不能只相信页面入口。
- 销售相关查询必须附加 `ownerId`。
- 公开表单可以匿名访问，但写入必须通过 `tenantSlug` 解析出合法 active tenant。

## 11. 下一轮建议

1. 增加 middleware 级别的后台路径拦截和权限审计日志，让未登录和越权请求更早被处理。
2. 增加 Playwright 或等价浏览器自动化测试，覆盖登录、公开表单提交、客户详情、跟进、导出和销售隔离。
3. 开始企业微信 API 适配层草案，只做客户联系、外部联系人、客户标签同步与回调安全，不碰违规群发和聊天抓取。
