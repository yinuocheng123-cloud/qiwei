# 版本记录：v1.5.1-smart-tag-suggestion

## 1. 本轮目标

本轮目标是在已经完成的 V1.5“智能跟进助手基础版”上，补齐“智能标签建议”能力。

优先级高的原因有三点：

1. V1.5 已经能根据客户问题生成三条建议回复，但销售仍然要自己判断“这类客户该补什么标签”。
2. 当前系统已经具备客户详情、标签、策略库、资料包、跟进记录和审计能力，适合继续做一层轻量的人工确认式标签辅助。
3. 用户明确要求本轮不要做自动打标签，不做企业微信 API，不做复杂 AI，因此最合适的方案是规则推荐加人工确认，不额外扩权限边界。

本轮目标类型属于：功能补充、可用性增强。

本次迭代与上一轮的关系是“延续和补强”，不是推翻重写。

## 3. 问题分析

表面现象是：系统能帮销售生成建议回复，但销售仍然要手工判断标签。

真正的核心问题不是“没有更多 AI”，而是“系统里已有的客户类型、问题线索和阶段信息，还没有沉淀成可以直接辅助打标签的可操作建议”。

当前瓶颈主要有四个：

1. `ReplySuggestion` 只承载回复建议，没有承载和本次问题绑定的标签建议。
2. 客户详情页只能展示回复建议，无法把“本次建议标签”与“客户已有标签”并排呈现给销售判断。
3. 现有标签入库结构使用 `LeadTag` + `TagGroup` 固定枚举，不能直接把页面展示用的中文标签分组原样落库。
4. 没有单独的审计动作区分“生成了标签建议”和“人工确认添加了标签”。

## 4. 候选方案比较

### 方案一：新增 SuggestedLeadTag 独立模型

核心思路：
为每次标签建议新建独立表，保存建议内容、确认状态和确认时间，再由确认动作同步到 `LeadTag`。

优点：

1. 数据语义最清晰。
2. 后续如果要做“建议历史”或“撤销确认”会更方便。

缺点：

1. 本轮目标只是补齐基础能力，这会引入新的数据模型、迁移和更多查询关系。
2. 页面、动作和测试都会随之变复杂。
3. 超出了“优先把基础系统能力做扎实”的范围。

放弃原因：
对当前版本目标来说过重，不符合最小改动原则。

### 方案二：扩展 ReplySuggestion，使用 Json 保存 suggestedTags

核心思路：
继续沿用 V1.5 的 `ReplySuggestion` 作为一次问题建议批次的承载体，在其中新增 `suggestedTags Json` 字段。展示时读取 Json，确认时再写入 `LeadTag`。

优点：

1. 直接延续 V1.5 数据链路，改动集中。
2. 不引入新表，数据库变更成本低。
3. 便于把“回复建议”和“标签建议”保持同一批次上下文。

缺点：

1. Json 字段在数据库层缺少更强约束。
2. 后续如果需要复杂统计，读取成本会高于独立表。

最终选择原因：
这是当前最小、最稳、最符合版本边界的实现方案。

## 5. 最终决策

本轮最终采用以下实现思路：

1. 在 `ReplySuggestion` 上新增 `suggestedTags Json?` 字段。
2. 每次生成建议回复时，同时生成一份标签建议数组，并把它写入三条同批次 `ReplySuggestion` 记录。
3. 标签建议只展示，不自动写入 `LeadTag`。
4. 客户详情页新增“智能标签建议”区域，使用服务端表单勾选并确认。
5. 确认添加时，按页面展示分组映射到现有 `TagGroup` 枚举，再写入 `LeadTag`。
6. 已存在的同名标签不重复添加。
7. 审计动作拆成两类：
   - `reply_tag_suggested`
   - `reply_tag_confirmed`

关键设计取舍如下：

1. 页面展示分组使用中文，例如“需求标签”“业务标签”“阶段标签”，因为这对销售更易读。
2. 实际入库仍映射到现有 `TagGroup`，例如“需求标签”映射到 `NEED`，“阶段标签”映射到 `STAGE`，其余无法直接对应的业务/风险类统一映射到 `CUSTOM`，以避免本轮扩大数据库枚举范围。
3. “销售不能给非自己负责客户确认添加标签”直接沿用 `requireLeadAccess`，不新增权限分叉。

## 7. 本轮优点

1. 沿用了 V1.5 的 `ReplySuggestion` 主链，没有新造复杂模型。
2. 推荐标签与建议回复属于同一次问题批次，销售理解成本低。
3. 通过“展示分组”和“入库分组”解耦，避免为了本轮功能改动更广的数据库结构。
4. 人工确认后才入库，严格符合“不自动打标签”的产品边界。
5. 审计日志能区分“系统建议了什么”和“人工最终确认了什么”。

## 8. 本轮缺点与代价

1. `suggestedTags` 保存在 Json 字段里，数据库层约束弱于独立表。
2. “业务标签”“风险标签”这类展示分组入库时统一映射为 `CUSTOM`，数据表达不如新增枚举精细。
3. 当前“客户已有标签”去重只按同名标签处理，没有进一步细分完全同名但不同业务上下文的情况。
4. 本轮仍然是规则模板，不具备更灵活的自然语言理解能力。
5. 页面目前采用服务端表单刷新式交互，稳定但不算最轻快。

1. Playwright 运行期间 Next.js dev server 会提示 `allowedDevOrigins` 的未来兼容警告，但这不影响本轮测试结果。
2. 当前 E2E 仍依赖临时 PostgreSQL 会话和重建 seed 数据，后续如要提高验证效率，可考虑把这套单 spec 数据准备再做一层统一脚本封装。

## 10. 本轮结论

本轮最重要的结论是：

在不改权限体系、不引入外部模型、不新增复杂数据模型的前提下，完全可以先把“智能标签建议”做成规则推荐加人工确认的基础版，并与 V1.5 的建议回复链路合并成一个完整闭环。

被进一步证实的判断有三点：

1. `ReplySuggestion` 适合作为“本次问题建议批次”的统一承载体。
2. `requireLeadAccess` 足以覆盖标签确认动作的权限边界。
3. 展示层中文分组与存储层枚举分组分离，是当前最稳妥的兼容方案。
4. V1.5.1 的 Playwright 失败主要来自页面上多个相似区域导致的定位器过宽，而不是标签写入逻辑本身异常。

## 11. 下一轮建议

1. 如果 V1.5.1 验证稳定，可以下一轮再考虑把“标签建议确认后自动带出下一步任务模板”做成轻量联动，但仍不要做自动发送。
2. 如果销售实际使用后认为标签建议不够细，可继续扩展规则词库，而不急着上外部模型。
3. 如果后续确实需要统计“标签建议命中率”或“建议被采纳率”，再考虑把建议标签从 Json 升级为独立模型。
