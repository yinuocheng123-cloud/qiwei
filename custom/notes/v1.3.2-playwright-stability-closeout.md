# 版本记录：v1.3.2-playwright-stability-closeout

## 1. 本轮目标

本轮目标是进入 V1.3.1 收口阶段，只处理测试稳定化和验证修复，不继续开发新功能，不提交、不推送，也不接入企业微信 API。

本轮优先级高的原因是：V1.3.1 已经完成任务去重、手动任务、任务模板和提醒队列的业务闭环，但浏览器端回归在跨版本串跑时容易被 seed 数据互相污染，且 V1.3.1 第一条专项链路存在卡住风险。如果不先把测试基线收稳，后续任何继续迭代都会缺少可信回归保护。

本轮属于 Bug 修复、测试稳定化和可维护性提升。

## 2. 背景与上下文

本轮承接 `custom/notes/v1.3.1-task-dedupe-template-reminder.md`，也回看了 `custom/notes/v1.3-task-workbench-bulk-audit.md` 和 `custom/notes/v1.2-sales-todo-strategy-materials.md`。

延续的旧思路有三点：

1. 继续保留 V1.3/V1.3.1 的任务驱动主线，不修改任务服务边界。
2. 继续保持最小改动，不为了测试问题大改页面结构。
3. 继续接受“Playwright 必须依赖可用 PostgreSQL、迁移、seed 和 dev server”这个现实约束。

本轮没有发现 `custom/notes/experiments/` 目录；与本轮最相关的实验脚本仍是 `custom/experiments/run-v11-postgres-check.ps1`，所以沿用它作为数据库闭环验证基线。

## 3. 问题分析

本轮一开始暴露出两类问题：

1. 测试执行层不稳定：如果直接依赖 Playwright 内置 `webServer` 和临时后台 job，容易在 Windows 环境里出现收尾卡住或数据库连接中断，难以判断到底是业务 bug 还是测试基建抖动。
2. 测试断言和页面演进脱节：V1.3.1 新增了任务模板、任务表单和工作台筛选区后，旧测试中大量“按文本查找”“按裸 name 查找表单元素”的定位变脆，容易命中多个元素。

进一步排查后，V1.3.1 并不只是测试定位问题，还存在一个真实业务 bug：

- 客户详情页“创建任务”表单里的 `type` 和 `priority` 选择框默认值分别是 `CUSTOM` / `NORMAL`。
- 当用户选择任务模板但不手动修改这两个下拉时，表单会把默认值直接提交给 Server Action。
- `createManualTask` 里 `text(formData, "type") ?? template?.type` 和 `text(formData, "priority") ?? template?.priority` 因此永远优先拿到表单默认值，模板里的类型和优先级被静默覆盖。
- 这会导致模板任务不是按模板类型创建，也会让 V1.3.1 “按模板类型筛选后应看到一条去重任务”的专项用例失败。

## 4. 候选方案比较

### 方案 A：只修测试断言，不改业务实现

核心思路是把 V1.3.1 的测试改成不依赖模板类型，或者把筛选改成 `CUSTOM`，从而绕过真实 bug。

优点是改动最小，能更快把测试跑通。

缺点是会掩盖“模板类型/优先级被默认表单值覆盖”的真实问题，和 V1.3.1 设计目标不一致。最终放弃。

### 方案 B：保留页面结构，只让空白选择真正回落到模板默认值

核心思路是在客户详情页的手动任务表单里，为“任务类型”和“优先级”增加空值选项，默认选中空值。这样：

- 未使用模板时，服务端仍会回退到 `CUSTOM` / `NORMAL`；
- 使用模板且用户未主动改下拉时，会回落到模板的 `type` / `priority`；
- 用户如果明确改了下拉，仍然以用户选择为准。

优点是业务修复最小，和现有 `createManualTask` 的回退逻辑天然兼容，不需要引入新的客户端状态管理。最终选择该方案。

### 方案 C：为 Playwright 增加仓库内自动化总控脚本，统一负责 reset DB、起停 dev server、执行所有 spec

优点是可减少手工重复命令。

缺点是本轮目标是收口而不是扩张测试基建；新增脚本会增加维护面，而且 README 已经足够承载“按版本顺序单独运行”的约束。最终暂不采用，只在文档中明确执行方式。

## 5. 最终决策

本轮最终采用“真实 bug 最小修复 + 测试定位稳定化 + 文档明确顺序执行”的组合方案：

- 修复客户详情页创建任务表单，让模板 `type` / `priority` 不再被默认表单值覆盖。
- 收窄 V1.3.1、V1.2 Playwright 断言范围，避免标题、容器、重复卡片和同名下拉造成严格模式冲突。
- 在 README 中明确：`v11`、`v12`、`v13`、`v131` 必须按版本顺序单独执行，每个 spec 前都要 reset 数据库并重新 seed，不要并行混跑。

## 6. 具体实现

- `src/app/app/[tenantSlug]/leads/[id]/page.tsx`
  - 为“任务类型”“优先级”新增“沿用模板默认类型 / 优先级”的空值选项。
  - 默认值改为空字符串，让服务端现有回退逻辑在使用模板时真正生效。

- `tests/v131-task-template-reminder-e2e.spec.ts`
  - 修复“创建任务”后等待条件，改为进入工作台验证筛选结果，而不是使用会命中标题和按钮的模糊文本断言。
  - 增加更精确的 section / task card 辅助定位，避免同一任务在“筛选结果”“高优先级任务”等多个板块重复展示时被误判成多条。
  - 修复取消任务用例，避免因大容器文本匹配导致一次命中多个“取消”按钮。

- `tests/v12-business-e2e.spec.ts`
  - 将客户分配相关断言收窄到“保存分配”所在表单。
  - 避免 V1.3.1 新增手动任务负责人下拉后，旧回归测试的 `select[name="ownerId"]` 命中两个元素。

- `README.md`
  - 在 Playwright 说明里明确“按版本顺序单独运行、每次先 reset DB + seed、使用 `--workers=1`”。
  - 为 V1.2、V1.3、V1.3.1 的专项测试段补充单 spec 命令示例。

- `AGENTS.md`
  - 更新最新一期记录路径到本文件。

## 7. 本轮优点

这轮修复保住了 V1.3.1 原始业务承诺：模板选择后，模板类型和优先级不再被默认表单值静默覆盖。

V1.3.1 专项测试不再依赖脆弱的裸文本匹配，而是改成围绕具体卡片和筛选区验证，能更贴近真实业务结果。

V1.2 回归也同步消除了“同名表单字段扩展后旧测试失效”的问题，为后续继续在客户详情页扩展表单留下了更稳的测试写法示例。

文档已经明确禁止跨版本 Playwright 并行混跑，后续接手者不需要再重复踩“seed 数据互相污染”的坑。

## 8. 本轮缺点与代价

当前还没有把“每个 spec 独立 reset 数据库、独立 seed”的流程沉淀成仓库内脚本；本轮只是通过 README 明确执行约束，并在本次验证中用外部命令串行完成。

V1.3.1 和 V1.2 的稳定性修复仍然主要发生在测试层，说明页面继续演进时，测试若继续使用宽泛文本匹配，后面仍可能再出现类似的严格模式冲突。

Playwright 运行仍依赖本地可用 PostgreSQL、浏览器二进制和 dev server；这轮没有把它改造成 CI 级的一键流水线。

## 9. 验证与结果

### 进程与端口清理

- 开始前检查了 dev server、Node、PostgreSQL 进程和常用端口。

## 10. 本轮结论

本轮最重要的结论有三条：

1. V1.3.1 第一条链路最初卡住并不只是一处问题，而是“测试断言过宽 + 模板默认值被表单默认值覆盖”的叠加。
2. V1.3.1 的真实业务 bug 已经修掉：模板任务现在会按模板默认类型和优先级创建，去重链路与专项筛选断言一致。
3. 当前仓库的 Playwright 基线已经可以稳定执行，但前提是按版本顺序单独运行，并在每个 spec 前 reset 数据库和 seed。

后续默认应继承的经验是：

- 不要把跨版本 spec 并行混跑。
- 在客户详情页和工作台这种复合页面里，Playwright 应优先围绕具体表单、具体 section、具体 card 做定位，少用宽泛 `getByText(...)`。

## 11. 下一轮建议

1. 如果后续还要继续扩展 Playwright，优先把“单 spec reset DB + seed + 启停服务”固化为仓库脚本，减少重复命令和人工误差。
2. 如果客户详情页未来继续增加更多表单，建议同步给关键表单增加更稳定的测试锚点，避免再次出现同名字段冲突。
3. 在真正引入 CI 前，继续维持“V1.3.1 -> V1.1.1 -> V1.2 -> V1.3”的单独回归顺序，作为当前本地最可信的收口流程。
