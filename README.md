## 本地演示一键启动

如果你只是想把本地演示环境稳定拉起，推荐直接执行：

```powershell
powershell.exe -ExecutionPolicy Bypass -File custom\experiments\start-local-demo.ps1
```

这个脚本会自动完成以下动作：

1. 检查项目目录和 PostgreSQL 可执行文件。
2. 检查或初始化 `custom/experiments/postgres-data` 数据目录。
3. 启动本地 PostgreSQL，并等待 `127.0.0.1:55432` 可用。
4. 设置当前进程的 `DATABASE_URL`。
5. 执行 Prisma generate、migrate deploy 和 seed。
6. 启动 Next.js dev server。

如果登录页报错：

`Can't reach database server at 127.0.0.1:55432`

说明本地 PostgreSQL 没有成功常驻，应该优先使用上面的脚本，而不是单独执行 `npm run dev`。

默认登录地址：

- `http://127.0.0.1:3000/login`

推荐测试账号：

- `platform-boss@zhengmu.local / 123456`
- `platform-operator@zhengmu.local / 123456`

## V2.0.3 导航与信息架构收口

V2.0.3 不继续扩业务功能，而是先把租户侧后台入口按用户任务重新归类，避免左侧导航继续堆成“功能清单”。本轮的重点不是增加新模块，而是让销售、运营、企业管理员在进入系统后更快找到自己真正要做的事。

### 为什么要收口导航

- 一级导航过去堆了过多技术模块，销售会被很多后台维护入口打扰。
- 客户导入、来源归因、标签视图、表单线索本质上都属于客户管理。
- 业务线、资料包、策略库、任务模板、企微配置、合规配置本质上都属于业务配置。
- Market Claw 已经形成知识、训练、回复记录和客户详情页使用闭环，适合独立成为清晰模块。

### 新的 6 个一级入口

租户侧一级导航收口为最多 6 个：

- 首页
- 客户管理
- 跟进工作台
- Market Claw
- 业务配置
- 系统管理

其中：

- 销售只看到：首页、客户管理、跟进工作台、Market Claw
- 运营看到：首页、客户管理、跟进工作台、Market Claw、业务配置
- 企业管理员看到完整 6 个入口
- 平台管理员不混入租户业务导航，仍以平台后台和演示说明为主

### 客户管理归类

客户相关能力统一收口在 `/app/[tenantSlug]/leads`：

- 客户列表
- 客户导入
- 来源归因
- 标签视图
- 表单线索

本轮优先做总览式归类和内部入口，不强行重写全部独立页面。

### 跟进工作台归类

跟进工作台统一收口在 `/app/[tenantSlug]/todos`：

- 今日待办
- 逾期任务
- 已完成
- 任务模板

复杂任务继续在页面内部用卡片和区块承接，而不是挂成多条一级导航。

### Market Claw 归类

Market Claw 继续保留为独立模块，统一入口为 `/app/[tenantSlug]/market-claw`。

- 管理员和运营看到：知识库、回复训练场、回复记录、使用反馈
- 销售看到：我的回复记录、去客户列表使用 Market Claw
- 客户详情页中的“Market Claw 智能回复”仍是销售的实际工作入口

### 业务配置归类

业务配置统一收口在 `/app/[tenantSlug]/business-lines`，并以“业务配置总览”承接：

- 产品总览
- 资料包
- 策略库
- 任务模板
- 企微配置
- 合规配置

本轮不做粗暴重构，而是优先让这些入口先归到一个清晰总览页里。

### 产品总览 → 产品详情

“业务线／产品”不再做成长表单页面，而是改成：

- 产品总览：卡片式展示产品名称、状态、分类、适合客户类型、推荐标签数量、关联资料数量、关联任务模板数量、最近更新时间
- 产品详情：在 `/app/[tenantSlug]/business-lines/[id]` 中继续用 Tab 承接基础信息、适合客户、推荐标签、关联资料、任务模板、Market Claw 知识、跟进 SOP、风险边界、操作记录

同时继续保持：

- 不做物理删除
- 只做启用、暂停、归档
- 销售只查看启用产品
- 历史客户、标签、任务和回复记录不因产品归档而断裂

### 系统管理入口

系统管理只给高权限角色展示，优先承接：

- 权限说明
- 审计日志
- 演示说明

这样既不放松现有服务端权限校验，也不会让普通销售在导航上看到一堆后台管理能力。

## V2.0.4 页面体验细节与角色使用路径优化

### 为什么这一轮不继续加功能

这一轮不是继续堆新功能，而是在 V2.0.3 已经完成导航收口后，把页面内部路径、层级提示和角色引导补清楚，让人工演示和真实使用都更顺手。

### 本轮重点

- 增加页内 Tab 高亮和当前状态提示
- 在总览页、详情页和子页面之间补轻量层级提示
- 继续收口产品详情页的信息层级
- 让 Market Claw 总览页更像产品入口
- 让客户管理和跟进工作台减少“一打开就很复杂”的感觉
- 让销售角色更快看到“今天该跟谁、客户问了怎么回、下一步做什么”

### 页面体验调整

- 产品详情页增加“业务配置 / 产品总览 / 产品名”层级提示

## V2.0.5 销售自我训练与训练审核机制

### 为什么要把集中训练和销售自我训练结合

Market Claw 如果只靠后台集中训练，会错过一线销售每天遇到的真实问题；但如果让销售的临时回复直接进入企业知识库，又会把边界搞乱。所以这一轮把“销售自己先练、管理侧再审核、优秀话术再升级”为团队或企业标准，补成完整闭环。

### 为什么训练要按部门和业务线分层

- 企业训练：适合通用边界、统一口径、不能承诺事项
- 部门训练：适合部门内复用的沟通方式和协作话术
- 业务线训练：适合产品、项目或专项业务的专属回复
- 我的训练：适合销售个人沉淀常用话术，不直接污染企业标准

### 本轮补齐的路径

- SALES 可以进入“我的训练”，输入客户真实问题，生成三版回复
- SALES 可以把训练结果保存为个人常用话术，也可以提交给上级审核
- 客户详情页生成回复后，也可以保存为个人话术或提交为训练样本
- TENANT_ADMIN / OPERATOR 可以进入“训练审核”，查看提交人、业务线、部门、销售修改版本、风险提醒与审核状态
- 审核通过后，可采纳为团队标准或企业标准；驳回时会保留原因

### 仍然保持的边界

- 不能承诺事项仍然是最高优先级
- 销售个人话术不会覆盖企业禁止表达
- 不接企业微信上下文
- 不自动发送客户消息
- 不接电话录音和 ASR
- 不开发 AI provider

## V2.0.6 Market Claw 资料投喂与候选知识生成

### 为什么这一轮先做资料投喂

到 V2.0.5 为止，Market Claw 已经有知识库、训练场、销售自我训练和训练审核，但企业里原本已经存在的 FAQ、案例说明、价格边界和服务资料，还是需要人工一条条搬进知识库，效率不够高。这一轮先补“资料投喂 -> 候选知识 -> 人工审核 -> 采纳入库”的中间层，让管理员和运营能先把现成资料快速整理成候选知识。

### 当前资料投喂入口

- 页面入口：`/app/[tenantSlug]/market-claw/ingestion`
- 角色范围：`TENANT_ADMIN`、`OPERATOR`
- `SALES` 不显示资料投喂入口，直接访问会被拒绝

### 本轮资料投喂流程

1. 先填写资料标题、业务线和资料类型
2. 支持粘贴文本，也支持补充 TXT / Markdown / CSV 文件
3. 系统用规则版拆解器生成候选知识
4. 候选知识进入待审核池
5. 管理员或运营决定采纳、修改后采纳、驳回或标记合并
6. 只有人工采纳后，才会生成 `MarketClawKnowledgeItem`

### 规则拆解当前覆盖什么

- FAQ：支持从“问：/答：”“问题：/回答：”“Q:/A:”中提取
- 价格边界：识别价格、费用、报价、预算等内容
- 风险提醒与不能承诺事项：识别保证、一定、排名、名额、效果等内容
- 案例素材：识别案例、客户、项目、合作、落地等内容
- 交付流程：识别流程、步骤、周期、准备、交付、启动等内容
- 客户异议处理：识别太贵、没预算、再看看、别人也能做、没效果等内容

系统会为每条候选项补齐：

- 标题
- 类型
- 建议关键词
- 建议不能承诺事项
- 风险提醒
- 简短微信版
- 专业说明版
- 推进成交版

### 为什么候选知识不能直接入库

这轮仍然保持 Market Claw 的核心边界：

- 资料投喂不是 AI 自动入库
- 候选知识不是企业标准知识
- 价格边界、不能承诺事项、风险提醒必须人工确认
- 销售个人话术不会因为资料投喂被直接覆盖

也就是说，系统可以先帮忙“拆”，但不能替企业“定”。

### 审核与入库说明

- 采纳后会创建 `MarketClawKnowledgeItem`
- 知识条目会记录来源批次和来源候选项
- 支持采纳为企业级、部门级、业务线级知识
- 如果候选内容需要并入已有口径，可以先标记为“已合并”，不单独入库
- 驳回时只记录结构化审核信息，不记录完整原始资料正文到审计日志

- 不接企业微信 API

## V2.0.7 Market Claw 候选知识去重与合并体验优化

### 为什么资料投喂后还要继续做去重和合并

V2.0.6 解决了“企业资料怎么先变成候选知识”的问题，但候选知识一多，就会出现三个新问题：

1. 相似 FAQ、风险提醒和价格边界会重复出现；
2. 审核人看不到候选知识和已有知识之间的关系，容易越审越散；
3. 知识库如果只会新增，不会合并，就会越用越乱。

所以这一轮不再追求“多生成一些候选”，而是先补齐“看相似、做合并、留来源”的治理体验。

### 什么是相似候选知识

本轮先用轻量规则匹配，不引入复杂语义模型和向量检索。相似判断主要参考：

- 同一租户、同一业务线
- 知识类型相同或接近
- 标题关键词重合
- 正文关键词重合
- 建议关键词重合
- 风险提醒相似

系统会把相似程度提示为 `HIGH`、`MEDIUM`、`LOW`，并展示命中原因，但这些提示只用于辅助审核，不会自动改写知识库。

### 如何处理候选知识

资料投喂页 `/app/[tenantSlug]/market-claw/ingestion` 现在支持以下几种审核动作：

1. 采纳为新知识
2. 合并到已有知识
3. 作为已有知识的补充追加
4. 修改后合并
5. 标记为重复并驳回
6. 普通驳回

这意味着审核人既可以继续保留独立知识条目，也可以把相似候选整理进已有口径，而不是被迫不停新增。

### 合并、追加与重复驳回的边界

- 合并到已有知识：用候选内容补强原知识正文，并记录合并原因、目标知识和操作人
- 作为补充追加：不覆盖原知识主体，只把候选内容作为补充说明追加进去
- 标记为重复并驳回：不入库，只记录重复原因和可选的目标知识

无论哪种路径，都仍然保持人工审核。候选知识不会因为被系统判定相似，就自动进入正式知识库。

### 知识来源怎么回看

知识库页 `/app/[tenantSlug]/market-claw/knowledge` 现在会补充轻量来源提示：

- 是否来自资料投喂
- 是否来自候选知识采纳
- 是否由多个候选合并
- 来源批次数量
- 来源候选数量
- 最近合并时间

这样做的目的不是上复杂版本系统，而是先让团队知道“这条知识从哪来、是不是被合并过、现在是否已经变得过于分散”。

### 本轮继续保持的边界

- 仍然保持人工审核，不让候选内容直接成为企业标准
- 不引入复杂知识版本系统
- 不引入复杂语义模型或向量检索
- 不接企业微信上下文
- 不自动发送客户消息

### 如何本地启动演示

推荐直接执行：

```powershell
D:
cd D:\ceshi\qiwei
powershell.exe -ExecutionPolicy Bypass -File custom\experiments\start-local-demo.ps1
```

脚本会自动检查项目目录、本地 PostgreSQL、数据目录、数据库端口，并依次执行：

1. `npm.cmd run prisma:generate`
2. `npx.cmd prisma migrate deploy`
3. `npm.cmd run prisma:seed`
4. `npm.cmd run dev`

### 当前适合进入什么阶段

本轮目标不是正式生产部署，也不是正式 SaaS 商业交付，而是：

1. 内部真实自用
2. 熟客共创试点
3. 小范围人工演示
4. 角色体验验收

如果要进入下一阶段，建议先完成：

- 一轮人工验收
- 一轮熟客试点
- 一轮文档与演示口径收敛
